# Local coding workflow alternatives for the SpecFlow library

Scope: the local skills/workflow library, **not .NET SpecFlow**. All sources below were accessed **October 28, 2026**. Local interactive/headless coding, testing, and agent review are in scope; hosted issue-to-PR and hosted PR-review automation are not. “Local” describes the checkout/execution workflow, not a claim that model inference is offline. Findings distinguish current main-branch documentation from published releases where they differ.

## What do the alternatives actually require, and what is optional?

### Takeaway

There is no single progression from “heavy SpecFlow” to “light alternative.” These systems optimize different things: durable specifications, change deltas, product planning, disciplined execution, or cross-session orchestration. Several now offer small-change paths, but those paths do not erase the underlying process or maintenance cost. This is an inference from the documented flows below, not a measured productivity result.

### Cited Findings

#### Compact comparison

Burden assessments in the last column are research judgments about the documented default path, not benchmarks.

|---|---|---|---|

Bug fixing and idea assessment are independent, opt-in extensions, **not** compulsory preliminary phases. Other processes can be composed. | Durable feature artifacts and a reusable process/toolkit ecosystem; still multiple artifacts and explicit stages, plus CLI/config/extension maintenance. [README](https://github.com/github/spec-kit/blob/main/README.md), [command reference](https://github.github.io/spec-kit/reference/agentic-sdd.html) |
| **OpenSpec** | Default `propose → apply → archive`, with optional `explore`; proposal produces proposal, specs, design, and tasks. | The default profile includes explore/propose/apply/archive. Expanded new/continue/ff/verify/bulk-archive/onboard are opt-in. Artifacts remain editable at any time; fewer commands do **not** mean fewer default artifact types. | Current behavior versus proposed change deltas, then archive/spec synchronization; useful for brownfield evolution. Still four artifact types and an archive lifecycle. [README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md), [customization](https://openspec.dev/docs/customize) |

| **Superpowers** | Brainstorm/design agreement → isolated workspace → detailed plan → inline execution **or** per-task subagents → verification/review → finish branch. | Skills are intended as mandatory when applicable. A short spec or plan is added when ambiguity or handoff warrants it. Hard rules use native permissions/hooks rather than prose alone. | Lowest additional process surface; puts responsibility for sufficient requirements, verification, and review scope on the team. #### Important operational details

- **Spec Kit is now a composable toolkit, not only a fixed SDD pipeline.** Its current README explicitly separates SDD, bug fixing, idea assessment, and bring-your-own process; offers integrations, extensions, presets, workflows, overlays, bundles, and catalogs; and warns catalog listings are not audits or endorsements. Do not repeat OpenSpec’s competitive description of Spec Kit as if it independently establishes current rigidity. [Spec Kit README](https://github.com/github/spec-kit/blob/main/README.md); compare [OpenSpec README’s marketing comparison](https://github.com/Fission-AI/OpenSpec/blob/main/README.md).
- **Spec Kit’s convergence is not an automatic code-fixing reviewer.** It assesses against spec/plan/tasks, reports severity, and only appends remaining tasks; it does not edit code. The user then runs implement again. Its reference says tests in generated task lists are included **when requested**; do not claim universal strict TDD. Optional artifact consistency analysis is read-only. [SDD command reference](https://github.github.io/spec-kit/reference/agentic-sdd.html).
- **OpenSpec’s fluidity concerns iteration and commands, not document elimination.** Its example creates `proposal.md`, `specs/`, `design.md`, and `tasks.md`; archiving updates specs. Requirement deltas use headings such as ADDED Requirements and WHEN/THEN scenarios. This is Markdown scenario writing, not a requirement to adopt executable Gherkin or a BDD runner. [README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md).
- **OpenSpec customization has two materially different costs.** Project configuration can add instructions such as “tasks always include tests”; dropping a design doc or renaming artifacts requires forking a schema with its own artifacts, order, and templates. Thus “we will just configure away the ceremony” can become maintaining another custom workflow. [Customization overview](https://openspec.dev/docs/customize).
- **Stable BMAD already has a small-change route.** The stable tagged guide says the route is chosen after investigation, not by requiring the user to classify work upfront. A design clean on intent gaps, irreversibility, and footprint takes a minimal-spec implementation path in the same session; flagged work gets a full plan with open questions and approval. It explicitly separates `bmad-build` (one unit) from backlog/orchestration and broader project planning. Passing tests are promised conditionally on a project having a suite; generated API/E2E coverage is a separate documented activity. [Stable build guide](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md).
- **Superpowers’ cheaper inline option is real in the released tag.** Its v7.0.1 execution skill has one current-session implementer, task briefs, test evidence, a progress/rulings ledger, and one final whole-branch review. A fresh reviewer is mandatory when a subagent tool exists; without one it explicitly records weaker self-review. Critical/Important findings get **one** test-verified fix pass; Minor findings are deferred, and it explicitly says not to dispatch re-review. This is materially different from an unbounded review-until-clean loop. [Tagged execution skill](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md).
- **GSD has genuine escape hatches.** `gsd-quick --full` adds discussion, research, plan checking, and verification; `--validate` adds just checking/verification; flags compose. `gsd-fast` is inline with no subagents or planning overhead for trivial tasks. Normal project initialization produces PROJECT, REQUIREMENTS, ROADMAP, STATE, configuration, and research artifacts. Phase planning produces research/plans/validation; execution produces summaries, commits, and verification. This makes “GSD is always a full milestone pipeline” false, but also makes “GSD removes planning bookkeeping” false. [Command reference, Quick/Fast and core commands](https://github.com/open-gsd/gsd-core/blob/main/docs/COMMANDS.md).

### Inferences

- Switching could reduce **human command count** while retaining or increasing **generated artifacts, inference calls, state transitions, and upgrade maintenance**. Compare those dimensions separately, rather than counting slash commands. [OpenSpec default example](https://github.com/Fission-AI/OpenSpec/blob/main/README.md), [Superpowers inline mechanics](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md), [GSD artifacts](https://github.com/open-gsd/gsd-core/blob/main/docs/COMMANDS.md).
- Adopt a framework for a missing capability: OpenSpec for maintained requirements/change history, Spec Kit for reusable organizational processes, BMAD for scope-adaptive delivery/product planning, Superpowers for imposed TDD/review discipline, GSD for phase/state orchestration. None is justified solely because it is fashionable or advertises less ceremony. These are fit assessments from the cited workflows, not comparative outcome evidence.

### Gaps

- Documentation establishes intended behavior, not that agents consistently obey it. No installation, trial implementation, cost measurement, or runtime-parity test was performed.
- No independent controlled evidence was found here that any option produces fewer defects or saves more time than a carefully scoped native loop. Repository popularity and author testimonials are not substitutes.

## What is released, and what maturity or license caveats matter?

### Takeaway

All five framework READMEs identify MIT licensing, but “MIT,” an active release stream, and marketplace distribution are not evidence of workflow reliability. Current docs are moving targets: BMAD’s v7 ETA is stale, Superpowers main and its released brainstorming rules differ, and GSD documentation contains inconsistent version labels.

### Inferences

- Pin a version for a pilot and evaluate that tag’s actual skills, not only main-branch marketing. BMAD and Superpowers provide concrete examples of why this matters. [BMAD release/main distinction](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/README.md), [Superpowers released brainstorming](https://github.com/obra/superpowers/blob/v7.0.1/skills/brainstorming/SKILL.md).
- A stable tag is a useful reproducibility boundary, not proof that a framework is low-risk or finished. Installer and parity fixes are maintenance signals, not disqualifiers or evidence of effectiveness. [BMAD release](https://github.com/bmad-code-org/BMAD-METHOD/releases/tag/v6.12.4), [GSD release](https://github.com/open-gsd/gsd-core/releases/tag/v1.19.0).

### Gaps

- No full license/dependency/security audit was performed; no long-term support commitments were established.
- Release retrieval establishes the latest stable release observed, not that no prerelease or unpublished development exists.
- No commit-pinned snapshot of mutable main docs is preserved here. For an implementation decision, retain the selected tag/commit and rerun the comparison after upgrades.

## When should SpecFlow retain a layer, switch frameworks, or use only a native loop?

### Takeaway

Use the minimal native loop as the control condition. Keep or adopt an additional layer only when it supplies project-specific knowledge, persistent coordination, or a measurable quality gate that the native agent and ordinary tests do not already provide. This is a recommendation, not an empirically established winner.

### Cited Findings

- Native Claude Code guidance now recommends writing down only information the agent cannot cheaply discover, keeping standing instructions short, moving procedures into on-demand skills, giving the agent executable pass/fail checks, and using a fresh reviewer for correctness rather than endless stylistic findings. It explicitly distinguishes model-read prompts/skills from harness-enforced command hooks, permissions, tests, and budget caps. [Native best practices](https://code.claude.com/docs/en/best-practices).
- The same native guidance says subagents are useful for independent work, noisy output isolation, constrained tools, and fresh review, but cost tokens and can be slower because they gather context again. Delegating to the same model does not itself produce a smarter answer. It also cautions against writing extensive repo layout/architecture descriptions the agent can read itself. These are vendor recommendations and should not be mistaken for independent performance studies. [Native best practices](https://code.claude.com/docs/en/best-practices).
- Native guidance already supports an optional written SPEC followed by a fresh implementation session, exact test/typecheck commands, local diff review in a fresh subagent, targeted reviewer prompts, bounded unattended execution, and deterministic hooks for non-negotiable checks. These capabilities directly overlap much generic workflow-library content. Hosted scheduling and cloud workflows mentioned on that page are excluded here. [Native best practices](https://code.claude.com/docs/en/best-practices).

### Inferences

#### Proposed baseline, not another mandatory pipeline

1. **One bounded intent:** goal, non-goals, important constraints, concrete acceptance checks. Keep it in the prompt for obvious work; use one small durable note for ambiguity or handoff. Basis: [native prompt/spec guidance](https://code.claude.com/docs/en/best-practices).
2. **Repo-first execution:** inspect existing patterns, make a short plan only if useful, implement with a regression test for behavior changes, run the project’s actual tests/typecheck/lint. A regression test should prove the intended failure/fix; do not invent universal strict TDD for every document/config/prototype task. Basis: [native verification guidance](https://code.claude.com/docs/en/best-practices); contrast [Superpowers’ stronger mandatory TDD policy](https://github.com/obra/superpowers/blob/main/README.md).
3. **Risk-sized local review:** for meaningful changes, one fresh reviewer compares the diff to acceptance criteria, prioritizing correctness, security, regressions, missing behavior, and test gaps; skip style and unrelated refactors. Fix material findings and rerun checks; escalate unresolved issues instead of looping indefinitely. Basis: [native reviewer guidance](https://code.claude.com/docs/en/best-practices), [Superpowers bounded final fix policy](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md).
4. **Evidence and sign-off:** report commands/results, unresolved risks, and changed scope; keep human approval for merge, push, destructive actions, or release. Add deterministic checks only for rules that cannot tolerate exceptions. Basis: [native enforcement and unattended-run guidance](https://code.claude.com/docs/en/best-practices).

#### Decision criteria for the reassessment

- **Do not replace generic ceremony with different generic ceremony.** A four-artifact OpenSpec change, a Superpowers ledger/brief/review flow, or a GSD phase system may be worthwhile, but none automatically solves excessive SpecFlow stages. Adopt the smallest path that delivers a needed outcome. [OpenSpec artifacts](https://github.com/Fission-AI/OpenSpec/blob/main/README.md), [Superpowers execution](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md), [GSD quick/full distinction](https://github.com/open-gsd/gsd-core/blob/main/docs/COMMANDS.md).
- **Native-only is a valid result.** If the library merely restates “read code, make plan, test, review,” its incremental benefit must be demonstrated against native capabilities, not assumed. Retain narrower domain, architectural, regulatory, or project-specific skills where they encode otherwise unavailable knowledge. [Native on-demand skill/standing-context guidance](https://code.claude.com/docs/en/best-practices).
- **Avoid stacking complete methods initially.** Combining a full spec framework, execution framework, and custom SpecFlow loops risks duplicate planning, review, and state. First test one native baseline and one smallest-fit alternative on comparable changes; add a second layer only for a concrete missing contract. This is a design-risk inference from the overlapping documented flows, not a claim that every combination fails.
- **Measure outcomes and total burden:** human clarification/review minutes; wall time and inference cost; artifact files/lines maintained; intervention count; rework; actual test evidence; correctness defects found before and after review; upgrade friction. Use the same model/harness, repo, task class, and acceptance rubric where practical. No numerical threshold or superiority claim is supported by this desk research.

### Gaps

- The report coordinator must connect these alternatives to the existing SpecFlow library’s actual pain points and unique knowledge. This subtask did not audit local skills or prescribe deletions.
- Native examples above are concretely documented for Claude Code; analogous features and permission/review semantics must be checked in the team’s chosen OpenCode/Codex/other harness rather than assumed identical.
- A fair pilot is still needed. Documentation alone cannot decide whether saved human attention offsets generated artifacts, inference cost, or the risk of silently skipped gates.
