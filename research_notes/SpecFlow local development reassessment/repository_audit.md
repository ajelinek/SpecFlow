# SpecFlow local-development repository audit — 28 October 2026

## 1. What is mandatory versus optional, and what is worth keeping?

### Takeaway

Keep SpecFlow as a selectively used library of local-development practices; simplify its delivery workflow rather than discarding its accumulated knowledge. Its advertised minimal path is genuinely smaller than the whole catalog, but invoking `301` still opts into considerable preparation, delegation, test execution, and separate cleanup—not just implementation.

### Cited Findings

- **Scope and evidence:** audited the local repository at `/Users/ajelinek/code/skills/SpecFlow`, HEAD `3dfc0662dd317d4a772af005259ce87af1a600b5`. This is the AI-workflow skill library, not .NET SpecFlow. README calls it an actively developing, lightweight, spec-driven workflow. Findings below describe checked-in instructions, not demonstrated agent behavior. [README lines 3–22](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L3-L22)
- **Public minimum:** README recommends `201 → 202 → 301 → 401`, explicitly including source cleanup and another test-cleanup invocation “if needed.” Tiny isolated edits are not the intended `301` use case. [README lines 121–134](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L121-L134), [lines 346–354](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L346-L354)
- **100-series is optional, not a mandatory prerequisite chain.** README says project setup/planning skills are helpful but not required for every project. Individual selected skills do impose their own requirements: `100` requires live research unless the user explicitly requests a lightweight known-context draft; `101`/`102` use `gap-check`; UI `106`, `107`, and `108` require three candidate directions, including “even for simple pages” in `108`. [README lines 163–178](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L163-L178), [100 lines 54–59](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/100-domain-knowledge/SKILL.md#L54-L59), [101 lines 35–40](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/101-project-overview/SKILL.md#L35-L40), [102 lines 44–48](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/102-system-architecture/SKILL.md#L44-L48), [106 lines 42–52](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/106-ui-design/SKILL.md#L42-L52), [107 lines 42–52](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/107-ui-experience/SKILL.md#L42-L52), [108 lines 43–54](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/108-ui-page-design/SKILL.md#L43-L54)
- **200-series captures useful distinct decisions.** `201` limits scope and journey, permits missing project context, and blocks silent scope growth. `202` asks for coverage level; extends existing scenarios rather than automatically multiplying them; prefers end-to-end business outcomes, observable behavior, and business-context modules. `203` requires codebase exploration, concrete reuse candidates, and justification for new files/dependencies. `204` checks cross-artifact consistency and requires evidence plus the smallest fix. [201 lines 47–77](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/201-high-level-design/SKILL.md#L47-L77), [202 lines 24–31, 44–78](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/202-spec-design/SKILL.md#L24-L78), [203 lines 62–76](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/203-implementation-design/SKILL.md#L62-L76), [204 lines 58–78](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/204-feature-validation/SKILL.md#L58-L78)
- **The minimal path hides planning work, not necessarily planning files.** `301` checks for overview, specs, and implementation artifacts and synthesizes missing ones in order through `201`, `202`, `203`, `204`; synthesized artifacts stay in memory unless persistence is requested. Consequently skipping standalone `203`/`204` does not necessarily skip those activities. Exact wording does **not** establish that every existing-artifact run must rerun every upstream skill; do not overstate this as “always recreate all four.” [301 lines 18–20, 65–76](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/301-spec-implementation/SKILL.md#L18-L76)
- **Inside `301`, delegation and phase separation are mandatory.** All edits go through coder/general agent, all test/lint/build execution through validator. Baseline test/lint/build precedes coding; red tests precede minimum production code; separate test and production cleanup each receive validation; full test/lint/build closes the run. High-impact changes still warrant human review. [301 lines 40–59, 89–138](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/301-spec-implementation/SKILL.md#L40-L138)
- **Worker installation is called optional, but contracts depend on workers.** README says the main installation installs skills only and worker agents are optional. `301` explicitly gives coder a general-agent fallback but names validator as the sole execution authority without a corresponding explicit fallback; `401`, `302`, and `402` also depend on validator. This is an onboarding/portability ambiguity, not evidence they always fail. [README lines 83–117](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L83-L117), [301 lines 42–45](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/301-spec-implementation/SKILL.md#L42-L45), [401 lines 39–49](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/401-cleanup/SKILL.md#L39-L49), [302 lines 39–43](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/302-test-implementation/SKILL.md#L39-L43), [402 lines 38–43](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/402-test-correction/SKILL.md#L38-L43)
- **The strongest transferable practices are concrete.** Reuse ladder includes no change/configure/delete before new code, and explicit approval before a new dependency. `301` hands workers exact file/scenario slices rather than full transcripts. Validator must capture real stdout/stderr and exit status without modifying code. `402` explicitly distinguishes test defect, source defect, and ambiguous product intent, and forbids weakening business assertions just to pass. [engineering-principles lines 19–54](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/engineering-principles/SKILL.md#L19-L54), [301 lines 47–59](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/301-spec-implementation/SKILL.md#L47-L59), [validator lines 21–27, 43–68](https://github.com/ajelinek/SpecFlow/blob/3dfc066/agents/validator.md#L21-L68), [402 lines 47–57, 90–108](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/402-test-correction/SKILL.md#L47-L108)
- **Independent local review remains valuable and separable.** `900` requires completed work, explicit review criteria and fix scope; uses fresh isolated reviewer/fixer contexts; defaults to five fix pairs; stops on ambiguous verdicts and escalates at its cap. Reviewer must name location/problem/failed criterion, not generic taste. It is user-invoked, not mandatory for the README minimum. [README lines 331–344](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L331-L344), [900 lines 14–63](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/900-feedback-loop/SKILL.md#L14-L63), [reviewer lines 20–45](https://github.com/ajelinek/SpecFlow/blob/3dfc066/agents/reviewer.md#L20-L45)

### Inferences

- **Keep:** reuse-first guidance; short outcome/scope/spec artifacts when useful; failure classification; real test outputs; bounded, criteria-driven independent local review. Those are useful even without adopting the numbered pipeline.
- **Simplify:** one human-led local change can preserve these safeguards without requiring dedicated subagents for every code and command pass. This is a recommendation to reduce fixed overhead, not an assertion that delegation never helps.
- **Do not replace one framework project with another.** Stop invoking unnecessary layers first; existing docs/skills can remain on disk. No migration, rename campaign, rewritten orchestrator, or new platform is necessary to use the useful pieces.

### Gaps

- No measured productivity, defect-rate, review-quality, token-cost, or cycle-time comparison was established. Good instructions are not proof of good outcomes. No feature loop was executed in this audit.
- “Optional workers” needs a documented supported execution fallback before claiming portability across coding harnesses; model aliases and agent discovery are harness-dependent.

## 2. Where do orchestration and autonomy create disproportionate burdens or correctness risks?

### Takeaway

`901` is optional and openly expensive, but its local autonomy and nested choreography make it a poor default for ordinary development. Retiring it from routine use is justified without claiming that full BDD, local independent review, or all SpecFlow skills should be retired.

### Cited Findings

- **Cost is acknowledged by the repository itself:** README says `901` may take a hundred or more subagent invocations for several scenarios across two coverage rounds. `901` defaults round two to balanced, performs a full `301` for each scenario, then module checks, aggregate source/test cleanup, round checks, and final checks. [README lines 337–344](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L337-L344), [901 lines 15–21, 33–38](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L15-L38), [901 lines 93–136, 213–268](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L93-L268)
- **Real duplication remains despite module-level optimizations.** Module checks are narrower than full e2e and commits are per module, which reduces some overhead. But each scenario still runs `301`'s own baseline, test/production cleanup, and full final validation; `901` then adds aggregate cleanup and round validation. README's separate `401` after `301` likewise overlaps cleanup already inside `301`. [901 lines 113–118, 213–233](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L113-L233), [301 lines 89–135](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/301-spec-implementation/SKILL.md#L89-L135), [README lines 123–127](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L123-L127)
- **No explicit run-wide spend/time/tool-call budget is declared in `901`.** It has local feedback caps, staged fallback rules, cheaper-model routing, and terminal reports, but not a global dollar/token/time ceiling. `900` even says not to override `CHANGES_REQUIRED` merely because another pass is costly; its iteration cap bounds cycles, not total spend. [901 execution/checkpoint protocols](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L42-L138), [900 lines 30–32, 49–63](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/900-feedback-loop/SKILL.md#L30-L63)
- **All blocking questions become model decisions in `901`.** It never asks the user: “stop and confirm” becomes consult-and-continue. Dirty tree options are commit or `git stash push -u` (default stash); final cleanup pre-authorizes scope expansion; merge conflicts default to direct resolution favoring feature branch. Git operations stay local and never push, but these still affect the user's working tree and base branch. [901 lines 44–49, 80–87, 171–173, 246–268](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L44-L268)
- **The decider is not a human-approval equivalent.** One consult spawns three Opus sub-calls with progress/caution/neutral stances and resolves by vote; its output makes unanimity “always high” confidence. It is read-only itself, but `901` acts immediately on its choice. Agreement among model calls is not independently established correctness or authorization. [decider lines 13–24, 41–81, 93–108](https://github.com/ajelinek/SpecFlow/blob/3dfc066/agents/decider.md#L13-L108), [901 lines 80–87](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L80-L87)
- **Terminal-state wording is internally inconsistent.** `901` says only Steps 2 and 19 can end without merge, but Step 3 explicitly permits a terminal report; module fallback and merge-conflict paths also allow termination. This matters for resume/terminal reporting, without proving a runtime failure. [901 lines 120–123, 179–188, 257–268](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L120-L268)
- **Important compatibility correction: current Claude Code supports nested agents, not unlimited nesting.** Current official documentation says the default limit is three layers below main, configurable via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`. Thus “subagents cannot spawn subagents” is no longer an accurate blanket objection. Nevertheless, the literal path `901(fork) → 900(fork) → Apply-Fix agent → 401(fork) → coder/validator` exceeds three layers; `901 → 301 → 204 → explore` is another potential deep path. Repo `901` explicitly asks Apply-Fix to invoke real `401`. This is a default-depth compatibility risk requiring a configured-version smoke test, **not** an observed failure. [Official nested-agent documentation](https://code.claude.com/docs/en/sub-agents#let-subagents-spawn-their-own-subagents), [901 frontmatter and lines 125–136](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L1-L136), [900 frontmatter and lines 41–58](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/900-feedback-loop/SKILL.md#L1-L58), [401 frontmatter and execution protocol](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/401-cleanup/SKILL.md#L1-L49)

### Inferences

- **Retire from routine use:** the headless whole-feature `901` chain and multi-model decider; retain only as an explicitly chosen experiment for sufficiently large, well-scoped local work, if the owner actually values it. No need to delete the library.
- **Keep independent review, but bound the entire local run.** A short review brief, one fresh reviewer, a focused fix pass, and verification are separable from branch/commit/merge automation. A cap on iterations is useful; a human-visible stop on repeated/new low-value findings is preferable to treating model convergence as the objective.
- **Autonomy recommendation:** human approval should remain the boundary for ambiguous product intent, dirty-tree handling, scope widening, and merge conflicts. Local-only does not make these consequence-free.
- **The avoidable burden is composition, not Gherkin alone.** Even the implementation-first path invokes phase-separated agents and checks; removing only persisted planning files will not remove that fixed orchestration cost.

### Gaps

- Did not execute workflows, measure latency/spend, or test nesting against an installed Claude Code version. Current official pages were fetched on this audit date and are live documents, not a pinned historical release snapshot.
- Did not audit external permission settings/hooks. Workflow markdown describes desired behavior, not technically enforced sandbox boundaries; official Claude documentation itself distinguishes instruction context from enforcement. [Official memory documentation](https://code.claude.com/docs/en/memory#claude-md-vs-auto-memory)

### Inferences

- **Overall recommendation: keep the knowledge, simplify the default, stop routine orchestration.** Preserve the small reusable skills and repository conventions; use only the artifacts that resolve real uncertainty; retain independent local review/test loops; avoid `901` unless a specific feature justifies its overhead and autonomy is expressly wanted.
