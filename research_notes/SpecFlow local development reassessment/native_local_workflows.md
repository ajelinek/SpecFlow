# Native local coding-agent workflows as of October 28, 2026

## 1. Which parts of a local development workflow are already native?

### Takeaway

Claude Code, Codex, and Cursor already provide most of the execution machinery that a generic workflow library might otherwise orchestrate: planning, editing, running checks, local diff review, context management, tools, skills, and isolated parallel work. This supports questioning a mandatory procedural layer, not claiming that native agents guarantee correct software. [Claude Code](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices); [Cursor](https://cursor.com/blog/agent-best-practices)

### Cited Findings

#### Claude Code

- **Default local loop:** the current best-practices page explicitly says that “in most cases, your first plain prompt in a fresh session already does the right thing.” It documents automatic delegation and compaction, and auto permission mode for new terminal and VS Code sessions. These are current vendor claims about defaults, not an independent quality evaluation. [Source](https://code.claude.com/docs/en/best-practices)
- **Requirements and plans:** a plain-language request can have Claude interview the user, write `SPEC.md`, and then implement from that spec in a fresh session. The recommendation is not a compulsory sequence of architecture documents for every task. [Source](https://code.claude.com/docs/en/best-practices)
- **Tests and local review:** the page recommends runnable pass/fail checks, actual command output, and screenshots as evidence. `/code-review` reviews the local diff in a fresh subagent; `/verify` builds/runs the application and inspects the result. A custom reviewer can compare changes against `SPEC.md`, including test coverage of listed edge cases. [Source](https://code.claude.com/docs/en/best-practices)
- **Continuation:** `/goal` supplies a condition evaluated by another model; a command-based `Stop` hook can send the agent back when a check fails. These differ: the goal evaluator is model judgment, whereas running a configured command is enforced by the application. Even Stop blocking has documented limits, so this is not an unconditional completion guarantee. [Source](https://code.claude.com/docs/en/best-practices)
- **Instructions and skills:** keep `CLAUDE.md` short; include non-obvious decisions, exact validation commands, misleading legacy patterns, and repeatedly corrected mistakes. Use path-filtered `.claude/rules/` for local conventions and `.claude/skills/<name>/SKILL.md` for team procedures loaded on demand. `disable-model-invocation: true` prevents automatic invocation of a side-effecting skill. [Source](https://code.claude.com/docs/en/best-practices)
- **Context and isolation:** automatic compaction, focused `/compact`, clear/resume/rename, checkpoint rewind, and native `claude -w` worktrees cover much context and branch bookkeeping. Worktrees still need dependencies and ignored configuration; checkpoints do not restore every change made through shell commands. The aggregate `claude agents` view is explicitly a research preview, not a required foundation for these established primitives. [Source](https://code.claude.com/docs/en/best-practices)
- **Permissions:** prompt instructions, skills, and auto mode’s classifier are not hard boundaries. Deny rules, sandboxing, managed settings, and command/HTTP hooks are the enforcement mechanisms. Rules match particular tool paths; the page documents bypass edges and recommends sandboxing for OS-level restrictions. Model-evaluated hooks remain nondeterministic. [Source](https://code.claude.com/docs/en/best-practices)

#### Codex local CLI and desktop app

- **Prompt and planning:** OpenAI recommends goal, context, constraints, and “done when.” `/plan` or Shift+Tab supports exploration and clarifying questions before implementation. Execution-plan templates are an advanced option for longer work, not a universal prerequisite. [Source](https://learn.chatgpt.com/guides/best-practices)
- **Local verification and review:** the agent can create/update tests, run checks, inspect behavior, and review changes. `/review` supports uncommitted changes, commits, and custom instructions; desktop diff comments become feedback for the next turn. Only these local review uses are relevant here, not hosted PR review. [Source](https://learn.chatgpt.com/guides/best-practices)
- **Scoped knowledge:** global, repository, and nested `AGENTS.md` files provide durable guidance. OpenAI recommends short, practical files that grow from repeated mistakes. Task-specific documents and single-job skills carry the longer material; personal and shared skill locations include `~/.agents/skills` and repository `.agents/skills`. [Source](https://learn.chatgpt.com/guides/best-practices)
- **Context and subagents:** automatic compaction, `/compact`, `/resume`, `/fork`, and bounded subagent delegation are documented. OpenAI advises one chat per coherent outcome and not forking merely because a task continues. [Source](https://learn.chatgpt.com/guides/best-practices)
- **Worktrees:** the February 2 app launch already included isolated worktrees, multiple project threads, shared CLI/IDE session configuration, and local diff feedback. Current guidance still recommends worktrees to prevent simultaneous tasks editing the same files. This is local checkout isolation, not evidence that merges or integration are conflict-free in general. [Launch announcement](https://openai.com/index/introducing-the-codex-app/); [current guidance](https://learn.chatgpt.com/guides/best-practices)
- **Browser feedback is now a desktop capability:** the current built-in browser can open local apps, inspect rendered state, click/type, take screenshots, and receive visual annotations. Developer mode offers explicitly approved CDP access for console/network/DOM/performance inspection. The docs give a `localhost:3000/settings` reproduction-and-fix example. Do not infer that every local CLI session has this desktop browser capability. [Source](https://developers.openai.com/codex/browser)
- **Hooks are not merely a missing-feature workaround:** current local Codex hooks include tool, permission, stop, session, subagent, and pre/post-compaction events. They can run commands or MCP tools. Non-managed definitions must be reviewed and trusted; changed hashes require renewed trust. Project hooks require a trusted project. [Source](https://developers.openai.com/codex/hooks)
- **Important hook limitations:** background hooks cannot gate the initiating operation; hosted tools do not follow the local function-tool hook path; specialized paths may opt out. MCP callback errors do not necessarily block. `prompt` and `agent` hook handlers are parsed but skipped in the documented release behavior. Hooks are a guardrail, not a complete enforcement boundary. [Source](https://developers.openai.com/codex/hooks)
- **Permissions and maturity:** current configuration documents OS-level sandbox/approval controls, permission profiles, trusted project configuration, and organization-enforced constraints. Its feature table explicitly marks `hooks`, `goals`, and `multi_agent` as **Stable**, enabled by default; `memories` remains **Experimental**, disabled by default. These are the vendor’s current labels, not claims about their status in January. [Source](https://developers.openai.com/codex/config-basic)

#### Cursor editor and CLI

- **Planning without an external spec generator:** Plan Mode searches the repo, asks clarifying questions, generates a file/code-referenced Markdown plan, and waits for approval. Plans can be saved under `.cursor/plans/`. The January guide explicitly says quick/familiar changes do not all need detailed plans. [Source](https://cursor.com/blog/agent-best-practices)
- **Tests, debugging, and local review:** the same guide gives a full red/green TDD prompt sequence, a separate local Agent Review/Find Issues pass, browser-driven screenshot/testing, and Debug Mode’s hypothesis → instrumentation → reproduction → evidence → fix loop. These are vendor-supported local patterns, not capabilities uniquely introduced by a custom workflow library. [Source](https://cursor.com/blog/agent-best-practices)
- **Parallel work:** the guide documents managed local git worktrees and applying finished changes back to the working branch. It also recommends new conversations at task boundaries and selective reference to past chats rather than duplicating whole histories. [Source](https://cursor.com/blog/agent-best-practices)
- **Released skills and subagents:** the January 22 Cursor 2.4 release explicitly added skills in both editor and CLI, with automatic discovery and slash invocation, alongside parallel subagents with their own context. February 17’s 2.5 release added asynchronous subagents and granular sandbox network/filesystem controls. These dated releases supersede the January 9 article’s nightly-only skills caveat. [Dated release log](https://cursor.com/changelog/page/12)
- **Current skill scope is richer:** current docs describe progressive loading, project/user `.agents/skills` and `.cursor/skills`, compatibility with Claude/Codex skill directories, `paths` filters, automatic scoping for nested project skill directories, and explicit-only invocation. A skill may also be pinned as a Custom Mode for the session. These are current documented features; no exact introduction date was established for each. [Source](https://cursor.com/docs/skills)
- **Hooks and enforcement:** current hooks can observe/block/modify supported tool operations, manage subagent events, inject session context, observe compaction, run formatters, and continue work through stop follow-ups. The default stop-loop limit is five; configuration can change it. Command hook failures generally fail open unless `failClosed` is set; prompt hooks use a model and should not be represented as deterministic policy. [Source](https://cursor.com/docs/hooks)

### Inferences

- **High overlap in generic orchestration:** “understand → plan if needed → edit → run tests → inspect/review → fix” is already supported across all three. A skill that only restates this loop needs evidence of improved outcomes to justify mandatory invocation. This is an assessment, not a measured finding. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices); [Cursor](https://cursor.com/blog/agent-best-practices)
- **The tools do not supply project intent:** native review can compare code to a spec, but somebody must still provide the right requirements, constraints, fixtures, and acceptance criteria. Replacing a workflow should preserve these inputs rather than merely remove documents. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices)
- **Local means local execution, not offline inference:** this assessment concerns agents operating a developer’s checkout/tools and local app. It does not establish that models or connected services run offline. The cited vendors distinguish local environments from cloud execution, and desktop browser capabilities from CLI capabilities. [Codex](https://learn.chatgpt.com/guides/best-practices); [browser](https://developers.openai.com/codex/browser); [Cursor release log](https://cursor.com/changelog/page/12)

### Gaps

- No tools were installed or exercised. Capability findings describe first-party documentation, not this machine’s installed versions, account entitlements, organization policies, or observed reliability.
- No claim of identical browser, permissions, hooks, or skill semantics across clients. Compatibility with a skill directory does not prove every vendor-specific frontmatter field works everywhere.
- OpenCode and Gemini were optional and omitted to keep the investigation focused. No OpenCode V1 or V2 claims are made.

## 2. How current and strong is the evidence?

### Takeaway

The strongest evidence is dated feature releases plus current documentation that names supported behavior and maturity. Most workflow advice is vendor guidance or an engineering case study, not controlled evidence that a native workflow outperforms SpecFlow. [Cursor releases](https://cursor.com/changelog/page/12); [Codex maturity definitions](https://developers.openai.com/codex/feature-maturity); [OpenAI case study](https://openai.com/index/harness-engineering/)

### Cited Findings

- **Newer dated evidence matters:** the Codex changelog has an October 27 CLI release and October worktree/approval fixes; July 30 documents browser improvements and local multi-repository review; August 11 documents importing setup, skills, and recent work from other agents. These show a moving product, not a frozen early-2026 baseline. They do not date every current best-practice recommendation. [Source](https://developers.openai.com/codex/changelog)
- **Cursor’s status conflict has a specific resolution:** retain January 9’s workflow guidance where relevant, but replace its nightly-only availability statement with January 22’s released support. Do not infer local capabilities from the separate February cloud computer-use or long-running-agent announcements appearing on the same release-log page. [January guide](https://cursor.com/blog/agent-best-practices); [release log](https://cursor.com/changelog/page/12)
- **Current Claude advice is unusually explicit:** its “What you can stop doing” section retires aggressive manual context management, generic “keep going” prompting, redundant architecture/file-layout descriptions, and delegation just to obtain a supposedly better answer. It still endorses independent review, actual checks, non-inferable context, and team-specific skills. This is the vendor’s current recommendation, not a universal empirical result. [Source](https://code.claude.com/docs/en/best-practices)
- **The advice is not identical across vendors:** Claude says leave readily inferable repository layout out; Codex’s guide still lists layout among reasonable `AGENTS.md` contents. Both recommend concise, practical instructions. The defensible common rule is to remove low-value duplication and keep useful pointers, not impose one vendor’s line-by-line policy everywhere. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices)
- **The OpenAI case study argues for configured environments, not just better prompts:** the team made apps bootable per worktree, connected CDP, wrote browser skills, exposed local logs/metrics/traces, maintained a short `AGENTS.md` map to versioned knowledge, and enforced architecture through custom linters and structural tests. It explicitly warns that its end-to-end behavior depends on that repository’s investment and should not be assumed to generalize. [Source](https://openai.com/index/harness-engineering/)
- **Do not turn the case study into a benchmark:** the reported roughly one-tenth development time is the team’s estimate from a constrained internal experiment, not a randomized comparison with SpecFlow or representative local development. The article also reports drift and ongoing cleanup needs. [Source](https://openai.com/index/harness-engineering/)

### Inferences

- Native planning, subagents, worktrees, local review, and hooks are no longer defensible as missing primitives in a blanket argument for SpecFlow. Their availability does not prove that any particular methodology or artifact is unnecessary. [Cursor releases](https://cursor.com/changelog/page/12); [Codex configuration](https://developers.openai.com/codex/config-basic); [Claude](https://code.claude.com/docs/en/best-practices)
- The case study is evidence against both extremes: neither a giant procedural manual nor an unconfigured “just prompt it” environment is its reported recipe. The useful investment is task-relevant knowledge, observable outcomes, and mechanically checked constraints. [Source](https://openai.com/index/harness-engineering/)

### Gaps

- No controlled study comparing native-only local workflows against this SpecFlow library was found in the selected sources. No effect size, defect-rate reduction, or token/time advantage should be attributed to either approach.
- The January Cursor article references a study about developer planning behavior. That study was not separately examined; its mention is not evidence that planning causes higher productivity or that a multi-artifact pipeline helps every task.
- Live pages can change without an accessible update date. This report establishes an October 28 observation, not the first shipping date of every current feature. Features explicitly labeled preview/experimental are not promoted to GA by implication.

## 3. What residual value can custom SpecFlow skills retain?

### Takeaway

The strongest remaining case is a smaller, optional library of project/domain knowledge, explicit acceptance contracts, specialized verification, and repeatable team policy. Generic reminders and mandatory ceremony should be treated as candidates for removal or compression, with any claimed benefit tested against a native baseline. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices); [Cursor skills](https://cursor.com/docs/skills)

### Cited Findings

- All three vendors explicitly retain custom skills as an extension mechanism. Claude recommends non-inferable team procedures; OpenAI recommends narrow skills with concrete use cases/inputs/outputs; Cursor describes portable packages of domain knowledge, workflows, scripts, templates, and references. Native skill support is a distribution/execution substrate, not evidence that custom skill contents are redundant. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices); [Cursor](https://cursor.com/docs/skills)
- Native verification still needs the right oracle: commands, fixtures, expected behavior, screenshots, and acceptance criteria. A model’s completion statement is weaker evidence than the observable result. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices)
- Repository-local plans and domain documentation remain useful in the OpenAI case study, especially for complex work and continuity. The rejected approach is dumping everything into the always-loaded instruction file, not maintaining a knowledge base. [Source](https://openai.com/index/harness-engineering/)
- Prompt instructions are not a policy boundary. Configured checks and sandboxes can enforce particular constraints, but their coverage and failure modes must be understood. Cursor’s default fail-open hooks and Codex’s unsupported/fail-open paths make this especially important for portable workflows. [Claude](https://code.claude.com/docs/en/best-practices); [Cursor](https://cursor.com/docs/hooks); [Codex](https://developers.openai.com/codex/hooks)

### Inferences

These are recommendations for the coordinator’s assessment, not findings from a file-by-file audit of SpecFlow:

| Workflow content | Suggested disposition | Reason |
| --- | --- | --- |
| Generic planning/implementation/review/testing reminders | Compress or retire as mandatory steps | Already documented native patterns; compare outcomes before preserving orchestration overhead. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices) |
| Several design documents for every small change | Make optional and risk-sized | Codex and Cursor recommend detailed planning for difficult tasks, not every edit. [Codex](https://learn.chatgpt.com/guides/best-practices); [Cursor](https://cursor.com/blog/agent-best-practices) |
| Business rules, stakeholder decisions, terminology, regulatory interpretation and required evidence | Retain as focused knowledge/acceptance contracts | Agents cannot infer absent organizational intent. Interpretations still need qualified human ownership. [Claude](https://code.claude.com/docs/en/best-practices); [OpenAI case study](https://openai.com/index/harness-engineering/) |
| Framework/repo-specific conventions and known traps | Keep narrowly scoped and evidence-driven | Native discovery does not identify intentionally deprecated patterns or decisions made outside code. Prefer examples and pointers over copied manuals. [Claude](https://code.claude.com/docs/en/best-practices); [Cursor](https://cursor.com/blog/agent-best-practices) |
| Feature specs/Gherkin/output schemas | Keep when a consumer or risk justifies them | Native plan mode does not establish the team’s chosen acceptance format. The artifact should serve verification/continuity, not exist merely to unlock the next skill. [Codex](https://learn.chatgpt.com/guides/best-practices); [OpenAI case study](https://openai.com/index/harness-engineering/) |
| Browser QA/reproduction procedures | Retain domain-specific journeys, fixtures and evidence contracts; reuse native browser/tools | Browser access is available, but which roles/states/flows matter remains task knowledge. [Codex browser](https://developers.openai.com/codex/browser); [Cursor](https://cursor.com/blog/agent-best-practices) |
| Review/fix convergence loops | Keep only added policy: scope, severity threshold, independent context, cap and escalation | Native local review and continuation exist. An unbounded demand to find/fix more issues can expand scope without improving correctness. [Claude](https://code.claude.com/docs/en/best-practices); [Cursor hooks](https://cursor.com/docs/hooks); [Codex hooks](https://developers.openai.com/codex/hooks) |
| Handoffs and context procedures | Reduce routine compaction ceremony; retain deliberate cross-session/team contracts | Native compaction/resume/fork cover continuity, while an intentionally portable decision/status record can serve a different purpose. [Codex](https://learn.chatgpt.com/guides/best-practices); [Claude](https://code.claude.com/docs/en/best-practices) |
| Safety and “must always run” rules | Move enforcement to tested commands, hooks, sandbox and managed configuration where supported | Text can express policy but cannot guarantee compliance. Preserve explicit capability/failure-mode differences between clients. [Claude](https://code.claude.com/docs/en/best-practices); [Codex hooks](https://developers.openai.com/codex/hooks); [Cursor hooks](https://cursor.com/docs/hooks) |

- **Suggested minimal local baseline:** a scoped task with a definition of done; short repo instructions naming exact checks and non-obvious constraints; plan only when complexity warrants it; execute/test/inspect; independent local review where risk warrants it; human acceptance of consequential changes. Use worktrees for concurrent edits and native compaction/resume for continuity. This is a synthesis of vendor guidance, not a validated universal process. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices); [Cursor](https://cursor.com/blog/agent-best-practices)
- **Suggested evaluation:** compare that baseline with selected SpecFlow skills on matched local tasks. Hold model/tool access, requirements, and acceptance checks constant. Track accepted correctness, escaped regressions, human interventions, elapsed time, tokens/cost, scope creep, and artifact usefulness. Require evidence that extra phases pay for themselves; do not count document volume or number of reviewers as success. This is a proposed experiment, not an existing study.

### Gaps

- A skill-by-skill retain/delete judgment requires inspection of actual SpecFlow content and local task results; this research alone does not authorize removing the library.
- Native features do not guarantee good requirements, adequate tests, secure hooks, faithful compaction, useful review, accessible interfaces, or sound business decisions. The selected sources document tools and advice, not universal quality guarantees.
- Hosted agents, issue-to-PR automation, cloud long-running agents, hosted PR reviews, and remote-worker workflows were excluded from the assessment even where source pages also describe them.
