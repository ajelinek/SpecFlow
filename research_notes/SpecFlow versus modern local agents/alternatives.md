# Alternatives to a homegrown local agent-development library

## 1. How do the current alternatives operate locally?

### Takeaway

The useful distinction is what each framework manages: OpenSpec manages durable behavior specifications and changes; Superpowers manages engineering behavior; GSD Core manages project state and fresh-context execution; Spec Kit supplies a configurable process platform; BMAD supplies right-sized product-to-delivery workflows; Kiro embeds spec workflows in its own agent product. None is simply “a better prompt.” Phase count alone is misleading because artifact dependencies, optional actions, and automated review loops differ substantially. Sources and qualifications follow.

Research checked on **October 28, 2026**. Repository release metadata was fetched directly from GitHub's API, not inferred from search snippets. “Local” here means working on a local checkout through a coding agent. It does **not** mean local/offline model inference. No framework was installed or benchmarked during this audit, and no source code was edited.

### Cited findings: GitHub Spec Kit

- **Local operation:** Python 3.11+, `uv`, and an existing supported coding agent. Install `specify-cli`, initialize a checkout, then invoke skills in that agent's chat. The toolkit installs scripts/templates and agent integrations; it is not itself a replacement coding model. [Pinned README](https://github.com/github/spec-kit/blob/v1.2.5/README.md).
- **Normal feature flow:** establish a constitution once, then **specify → plan → tasks → implement → converge** per feature. The README says invoke one at a time and review each result. Repeat implement/converge until the result is `Converged`. Clarify, checklist, and analysis are additional actions rather than required steps in that minimal sequence. [Pinned README](https://github.com/github/spec-kit/blob/v1.2.5/README.md), [quickstart](https://github.com/github/spec-kit/blob/v1.2.5/docs/quickstart.md).
- **Artifacts:** the core feature intent is `spec.md`, `plan.md`, and `tasks.md`, governed by the constitution. The tasks command explicitly calls `data-model.md`, `contracts/`, `research.md`, and `quickstart.md` **optional inputs**, not universal required files. It structures tasks into setup, foundations, independently testable user stories, and polish. [Tasks command](https://github.com/github/spec-kit/blob/v1.2.5/templates/commands/tasks.md).
- **Context/state:** active-feature resolution now uses `.specify/feature.json`, with `SPECIFY_FEATURE_DIRECTORY` override. It does **not** depend on the checked-out Git branch; numbered feature branches are an opt-in Git extension. Convergence uses progressive disclosure of the feature artifacts. This corrects a common launch-era description that every specification necessarily creates a feature branch. [Quickstart](https://github.com/github/spec-kit/blob/v1.2.5/docs/quickstart.md), [converge command](https://github.com/github/spec-kit/blob/v1.2.5/templates/commands/converge.md).
- **Tests:** the tasks command states: **“Tests are OPTIONAL: Only generate test tasks if explicitly requested in the feature specification or if user requests TDD approach.”** Do not equate Spec Kit adoption with compulsory automated tests. Constitution/preset policy can raise that bar. [Tasks command](https://github.com/github/spec-kit/blob/v1.2.5/templates/commands/tasks.md).
- **Convergence:** reads spec/plan/tasks as intent, inspects current code, and appends traceable tasks for missing, partial, contradictory, or unrequested implementation. It does not change application code or rewrite the spec. Checkbox completion is explicitly not evidence. Useful separation of assessment from repair, but the assessment is still model-mediated. [Converge source](https://github.com/github/spec-kit/blob/v1.2.5/templates/commands/converge.md).
- **Risk/size adaptation:** bug repair has its own optional extension, **assess → fix → test**, with `verified`, `partial`, or `failed` verdicts and `.specify/bugs/<slug>/` reports. It need not run through the feature workflow. Ideas have a separate assessment extension. Current mechanisms include presets, extensions, workflow definitions/overlays, custom steps, bundles, catalogs, and offline/local sources. These are real configurability mechanisms; they also create a substantial configuration surface. [Pinned README](https://github.com/github/spec-kit/blob/v1.2.5/README.md).

### Cited findings: OpenSpec

- **Local operation:** standalone binary or package-manager install, then `openspec init` in the checkout. It installs commands/skills for an existing agent. The standalone binary needs no Node runtime; the npm route requires Node 20.19+. Updates have two parts: upgrade the CLI and run `openspec update` to refresh each project's agent guidance. [README](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/README.md).
- **Default interaction:** optional **explore**, then **propose → apply → archive**. Propose generates proposal, behavior specs, design, and implementation tasks in one action; it is not three files total. Expanded/custom command selections expose incremental artifact creation and optional verification. The project describes this as **actions, not phases**: revising planning artifacts during implementation is expected. [README](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/README.md), [workflow documentation](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/docs/workflows.md).
- **Default artifact dependencies are real:** proposal precedes specs and design; tasks depend on specs and design; apply requires tasks. The default schema is not artifact-free despite the “fluid” positioning. Behavior-changing work needs capability delta specs with requirements and scenarios; **`skip_specs: true` is available only when no spec-level behavior changes**, such as pure refactoring, tooling, or docs. Missing delta specs otherwise fail validation. [Default schema](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/schemas/spec-driven/schema.yaml).
- **Brownfield differentiator:** durable capability specifications live under `openspec/specs/`; a change lives under `openspec/changes/<name>/` and expresses additions, modifications, removals, or renames. Archive incorporates deltas into the durable specs. This gives it a clearer spec-maintenance story than simply accumulating frozen per-feature plans. Its own repository exposes live specs and changes as inspectable dogfooding, not proof of better outcomes. [README](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/README.md), [default schema](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/schemas/spec-driven/schema.yaml).
- **Tests/checkpoints:** the current schema requires each task to state how completion is verified and requires each task group to carry its own necessary tests/docs, rather than postponing them all. That verification can be a command, observable behavior, or artifact, not necessarily an automated test. It does not impose Superpowers-style universal red/green TDD. The user reviews planning before applying; optional `/opsx:verify` is not a default mandatory gate. [Schema](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/schemas/spec-driven/schema.yaml), [workflow docs](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/docs/workflows.md).
- **Context/orchestration:** ordinary operation delegates to the user's agent; no default fleet of implementer/reviewer agents is necessary. README explicitly recommends clearing context before implementation. Beta “Stores” add cross-repo shared planning, but a solo single-repo user need not adopt that layer. CLI telemetry defaults on, with explicit opt-out. [README](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/README.md).
- **Vendor comparison caveat:** OpenSpec's README still calls Kiro IDE-locked and Claude-only. Current Kiro documentation/changelog show CLI support and non-Claude models, so that competitor description is stale. Do not repeat it as fact. [OpenSpec README](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/README.md), [Kiro current changelog](https://kiro.dev/changelog/).

### Cited findings: Superpowers

- **Local operation:** install a plugin/skill package into each coding harness separately, including OpenCode. An initial bootstrap causes automatic skill selection. This is the closest structural substitute for a homegrown reusable skill library, rather than primarily a spec CLI. [README](https://github.com/obra/superpowers/blob/v7.0.1/README.md).
- **Seven named workflow components, not seven mandatory documents:** brainstorming; worktrees; writing plans; execution; TDD; review; branch finishing. Some operate inside others. Normal substantive work gets a reviewed design and a task-level implementation plan with paths, code/verification guidance; default plans go under `docs/superpowers/plans/`. Worktree setup checks the test baseline; branch finishing verifies tests and offers merge/keep/etc. [README](https://github.com/obra/superpowers/blob/v7.0.1/README.md), [plan skill](https://github.com/obra/superpowers/blob/v7.0.1/skills/writing-plans/SKILL.md).
- **Right-sizing and human checkpoints:** v7.0.1 brainstorming permits doing an entirely clear trivial request directly. Nontrivial work requires alternatives, a short/full design, approval, and planning; the execution handoff lets the human choose the execution approach. The pinned skill is more specific than README shorthand that small work is “agreed in chat.” [Brainstorming skill](https://github.com/obra/superpowers/blob/v7.0.1/skills/brainstorming/SKILL.md), [plan skill](https://github.com/obra/superpowers/blob/v7.0.1/skills/writing-plans/SKILL.md).
- **Two execution modes matter:** subagent-driven execution pays for a fresh implementer and reviewer per task, then a branch review. **Native/inline execution** performs all tasks in the current session with one fresh branch review at the end. The inline skill explicitly explains the cost tradeoff and uses a ledger for continuity and recorded rulings. It runs continuously, not by asking “continue?” after every task. This is a genuine lower-orchestration alternative, not a claim that every Superpowers run needs many subagents. [Plan handoff](https://github.com/obra/superpowers/blob/v7.0.1/skills/writing-plans/SKILL.md), [inline execution source](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md).
- **Tests:** strict observed RED → GREEN → REFACTOR, minimal implementation and verification before completion are core policy. The README says code written before tests is deleted. These are agent instructions, not a proof that the model obeyed or that tests cover user intent. [README](https://github.com/obra/superpowers/blob/v7.0.1/README.md).
- **Context refresh:** fresh implementer/reviewer contexts in the expensive mode; ledger plus final review in inline mode. Startup/compaction bootstrap varies by harness; README specifically warns Hermes lacks a post-compaction hook. Version 7.0.1 moved material out of oversized skills because Claude Code reattached only the first 20,000 characters after compaction. [README](https://github.com/obra/superpowers/blob/v7.0.1/README.md), [release notes](https://github.com/obra/superpowers/blob/v7.0.1/RELEASE-NOTES.md).

### Cited findings: GSD / GSD Core

- **Identity/local setup:** use `npx @opengsd/gsd-core@latest`, selecting a runtime and local/global installation. The current project says not to copy `agents/` and `commands/` directly because installation translates for runtime compatibility. New projects use `/gsd-new-project`; existing repositories use `/gsd-onboard`. [Current README](https://github.com/open-gsd/gsd-core/blob/v1.19.0/README.md), [archived predecessor redirect](https://github.com/gsd-build/get-shit-done).
- **Five-step repeating phase loop:** **Discuss → Plan → Execute → Verify → Ship**, with optional UI design. Plan itself usually runs researcher → planner → plan-checker. Execute groups plans into dependency waves; fresh agents execute them and commit task-level work. Verification evaluates requirement/decision/goal coverage, writes findings and creates gap-fix plans. Ship includes a PR action, but the core development work is local; this report does not evaluate hosted automation. [Phase-loop design explanation](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/the-phase-loop.md).
- **Durable state is the product:** `.planning/` contains `STATE.md`, `ROADMAP.md`, config, per-phase `CONTEXT.md`, `RESEARCH.md`, `PLAN.md`, optional `UI-SPEC.md`, execution summaries and `VERIFICATION.md`. These support restarting sessions and passing bounded context to workers. The orchestrator is intentionally thin; heavy research/planning/implementation happens in fresh subagents. That is a clear design mechanism, not evidence that context degradation is “solved.” [Context-engineering explanation](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/context-engineering.md), [phase-loop explanation](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/the-phase-loop.md).
- **Risk/size controls:** documents explicitly warn that tiny phases make overhead dominate execution and suggest `/gsd-quick` below that threshold. The command reference includes tracer-first vertical slices, human checkpoints for one-way-door decisions, configurable plan-checking, TDD mode and planning granularity. The “five-step” summary therefore understates the available machinery. [Loop/scoping guidance](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/the-phase-loop.md), [command reference](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/COMMANDS.md).
- **Tests/checkpoints are configurable:** the configuration schema shows `mode: interactive`, `auto_advance: false`, `human_verify_mode: end-of-phase`, and **`tdd_mode: false`**. Research, plan checks, verifier, security enforcement, UI checks, code reviews and repair budgets add many knobs. `--tdd` is an opt-in red/green planning mode. Do not equate GSD with mandatory TDD. [Configuration](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/CONFIGURATION.md), [commands](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/COMMANDS.md).
- **Context claims require qualification:** official text repeatedly says “clean 200k-token context” and uses strong language about context rot being structurally prevented. That describes the design's assumptions, not a measured guarantee for every supported contemporary model or runtime. It also acknowledges the main orchestrator can fill and adds runtime lifecycle hooks to watch headroom. [Maintainer explanation](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/context-engineering.md).

### Cited findings: BMAD

- **Do not use the old “enterprise roles and mandatory PRD for everything” caricature.** The pinned v6.12.4 README already presents right-sized work, direct `bmad-build` for small changes, optional planning, existing-code support and independent specialist perspectives. Current live documentation goes further with trivial, one-session, epic and project paths. However, the live tutorial labels its workflow v7 preview alpha, so verify the installed version before relying on live instructions. [Pinned README](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/README.md), [live planning paths](https://docs.bmad-method.org/plan/choose-a-planning-path/), [preview warning](https://docs.bmad-method.org/start/build-your-first-change/).
- **Local operation:** stable installation is `npx bmad-method install`; pinned prerequisites include Node 20.12+, Python 3.10+, and `uv`. Agents/skills run inside the selected AI coding tool. Optional Builder, Test Architect and Loop modules are additional adoption choices, not prerequisites for a small change. [Pinned README](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/README.md).
- **One-session build from pinned docs:** start a fresh chat, give intent, investigate repository/upstream evidence, take the smallest safe path, implement, independently review, fix in-scope findings, commit locally, then let the human review the result. Clear, reversible, small-footprint designs can take a light path with a minimal spec; material intent gaps, irreversible actions or footprint concerns trigger a full written plan and approval. Passing existing tests is part of the expected outcome; generated API/E2E coverage is a separate action. This is not equivalent to universal tests-first implementation. [Pinned Build a Change](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md).
- **Not a universal phase count:** the current live planning guide explicitly calls brainstorming/research/brief/PRD/UX/architecture **independent tools, not stages**. Larger work adds shared decisions, requirements and ticket breakdowns, then repeats one-session Build units. It increases planning for high risk, uncertainty, broad architecture, cross-system effects and coordination, not merely LOC. Treat these as the documented direction during transition, not an assertion that every stable runtime installs exactly the live v7 set. [Planning paths](https://docs.bmad-method.org/plan/choose-a-planning-path/).
- **Brownfield/context:** live guidance says code already contains most implementation knowledge; redundant prose introduces contradiction and context bloat. It recommends archiving irrelevant greenfield context, optional verified `AGENTS.md` instructions, and reading actual code before planning changes. Pinned build guidance likewise starts from repository evidence and a fresh session. This is a significant correction to “document the whole project first.” [Existing-codebase guidance](https://docs.bmad-method.org/existing-codebases/start-in-an-existing-codebase/), [pinned build workflow](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md).
- **Orchestration:** attended Build handles one unit; `bmad-build-auto` handles one unattended unit but explicitly does not own the backlog or choose the next story. A separate orchestrator, potentially BMAD Loop, dispatches units. That boundary is useful, but adopting the entire ecosystem introduces more moving pieces than using only Build. [Pinned build docs](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md).

### Cited findings: Kiro

- **Local operation:** use Kiro's own IDE or CLI on a local repository. Current docs show Feature Specs, Bugfix Specs, Quick Spec and parallel execution across IDE/CLI/Web; correctness/property-based testing remains **IDE-only**. Kiro is no longer accurately described as IDE-only or Claude-only. Current changelog includes non-Claude models and CLI releases. [Specs overview, updated October 15, 2026](https://kiro.dev/docs/specs/), [changelog](https://kiro.dev/changelog/).
- **Three artifact phases plus implementation:** `requirements.md` (or `bugfix.md`) → `design.md` → `tasks.md`, saved under `.kiro/specs/`. Standard requirements-first includes user review/confirmation of requirements, then technical design, then task review and execution. EARS notation formalizes acceptance behavior. Design-first is an alternative for technically constrained work. [Overview](https://kiro.dev/docs/specs/), [requirements-first, updated September 25, 2026](https://kiro.dev/docs/specs/feature-specs/requirements-first/).
- **Actual lightweight option:** Quick Spec asks clarifying questions first, then generates the same three files in one pass **without intermediate approval gates**. Recommended for familiar features/prototyping; standard gates are recommended for unfamiliar, compliance-sensitive or high-stakes work. Vibe mode remains an unstructured alternative with no spec artifacts. [Quick Spec, updated August 4, 2026](https://kiro.dev/docs/specs/quick-spec/).
- **Tests:** IDE correctness tooling extracts properties from requirements and runs generated property-based tests. The documentation explicitly states these tests are **optional by default** and evidence, not formal proof. Weak/wrong invariants can pass while behavior remains wrong. Do not generalize this feature to CLI parity or call it mandatory TDD. [Correctness documentation, updated August 4, 2026](https://kiro.dev/docs/specs/correctness/).
- **Orchestration/context:** run tasks individually or all at once; all-at-once builds a dependency graph and executes concurrent waves. Long sessions use automatic compaction into summaries; CLI additionally offers `/compact`. It preserves selected goals/decisions/status, not verbatim history, and acknowledges details may need restating. Changelog shows memory introduced October 19 and defaulted Off October 20. [Specs overview](https://kiro.dev/docs/specs/), [compaction, updated September 17, 2026](https://kiro.dev/docs/compaction/), [changelog](https://kiro.dev/changelog/).

### Inferences

- **Lightest durable-spec candidate:** OpenSpec. Its main advantage is a small user-facing action set and explicit spec delta/archive model, not the absence of documents. It still asks a solo developer to maintain another representation of behavior. [Default schema](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/schemas/spec-driven/schema.yaml).
- **Closest skill-library replacement:** Superpowers, especially inline execution. It shifts value toward engineering discipline and executable verification rather than an extensive product-document taxonomy. Its automatic activation can also conflict with an existing library if both prescribe different compulsory workflows. [README](https://github.com/obra/superpowers/blob/v7.0.1/README.md), [inline skill](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md).
- **Most explicit project/context coordinator:** GSD Core. Strong fit when unattended multi-phase continuity is the problem; less attractive if the problem is too much framework administration. [Context design](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/context-engineering.md), [configuration](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/CONFIGURATION.md).
- **Process platform rather than minimal replacement:** current Spec Kit. It can host custom processes and import existing practices, but replacing a homegrown process library with presets/extensions/bundles may relocate rather than eliminate ownership. [README](https://github.com/github/spec-kit/blob/v1.2.5/README.md).
- **Broadest product/planning option:** BMAD, with surprisingly practical small-change and brownfield guidance. The current stable/preview documentation split is a concrete adoption risk. [Pinned build docs](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md), [preview warning](https://docs.bmad-method.org/start/build-your-first-change/).
- **Lowest framework assembly burden if changing agent products is acceptable:** Kiro. It bundles review UI, artifacts, parallel tasks and compaction; that convenience comes with a larger product/provider commitment than portable skills. [Specs](https://kiro.dev/docs/specs/), [changelog](https://kiro.dev/changelog/).

### Gaps

- No install smoke test established exact OpenCode behavior, permission prompts, model/runtime parity or migration friction for these versions.
- BMAD's tagged README/docs and live preview documentation are not a reliable substitute for inspecting the actual installed stable skill bundle. No claim here that v7 is generally available.
- No common operational definition of “phase” or “mandatory” spans these tools. The counts above describe documented default workflows, not immutable machine-enforced state transitions.

## 2. Which advantages and criticisms have credible evidence?

### Takeaway

The strongest evidence supports explicit intent, bounded contexts, repository grounding, and independent executable verification. It does not establish that one of these six brands consistently beats a good native agent workflow. There are credible, inspectable failures from over-documentation and orchestration, including failures acknowledged by maintainers; many sweeping effectiveness claims remain unmeasured.

### Cited findings

- **Independent hands-on critique, October 15, 2025:** Birgitta Böckeler tested Kiro, Spec Kit and Tessl, distinguishes **spec-first**, **spec-anchored**, and **spec-as-source**, and reports verbose/repetitive artifacts, oversized process for small changes, instructions ignored, and duplicated implementation despite prior code research. She explicitly says real evaluation requires different task sizes, brownfield/greenfield work, and serious review of intermediate artifacts. These are concrete observations, not a randomized benchmark. Her process descriptions are dated and must not override 2026 docs. [Full article](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html).
- **Inspectable practitioner example, November 12, 2025:** François Zaninotto points to a date-display change producing **eight files and about 1,300 lines** of Spec Kit material, links the actual change, and provides Kiro artifacts for a small CRM field addition. He reports a “verify implementation” checkbox marked complete without unit tests. This supports review-overload and weak verification concerns. His claims that SDD is broadly unusable in large brownfield systems, or that users spend 80% of time reading, are opinion/generalization, not controlled evidence. [Critique](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html), [linked example PR](https://github.com/adguernier/frequentito/pull/42/files).
- **Criticism remains current, but not unchanged:** in a May 28, 2026 discussion, Böckeler and AWS technologist Laura Tacho agree that workflow should vary by size and type, small feedback loops still matter, and framework use does not solve organizational alignment. They question whether humans really review all generated Markdown and describe spec maintenance as unresolved. Tacho reports positive team experience but does not supply a comparative dataset; she is also an AWS employee, relevant to interpreting Kiro-adjacent claims. [Transcript](https://www.thoughtworks.com/insights/podcasts/technology-podcasts/what-is-spec-driven-development).
- **Superpowers maintainer admits cost:** Jesse Vincent wrote June 15, 2026 that the most common user lament is token expense and that building with Superpowers is slower. He reports internal eval-driven improvements of **up to 50% runtime and 60% token cost versus earlier Superpowers**, not versus a native agent. He links public eval/autoresearch repositories and describes measurement bugs corrected during the work. These are more inspectable than testimonials, but still vendor/maintainer-reported and version/harness/task-specific. [Maintainer explanation](https://blog.fsck.com/2026/06/15/Superpowers-6/), [eval repository](https://github.com/prime-radiant-inc/superpowers-evals), [autoresearch repository](https://github.com/prime-radiant-inc/superpowers-autoresearch).
- **Recent demonstrated workflow failure:** Superpowers v7.0.1 notes users found brainstorming formulaic/annoying; one test scenario skipped the design document in **24/24 runs before the patch versus 3/24 after**. Another reported session lost the five-round repair cap after skill truncation and ran **18 fix rounds**. These are direct evidence of both prompt fragility and active improvement. They do not demonstrate a universal post-fix reliability rate. [October 21, 2026 release notes](https://github.com/obra/superpowers/blob/v7.0.1/RELEASE-NOTES.md).
- **Current BMAD acknowledges process cost:** its pinned Build documentation explicitly asks “Why Does This Take So Long? I Could Plan Mode and Code It in Ten Minutes,” explaining that independent review, triage and repair add time. It permits bypassing process for trivial/throwaway work. This acknowledges the tradeoff but does not measure net human-attention savings. [Pinned build docs](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md).
- **Current GSD acknowledges overhead:** official scoping guidance says excessively small phases create planning overhead that dwarfs execution cost; overly large phases stretch feedback cycles and discover mistakes late. That is a credible limitation because it appears in maintainer design guidance rather than a competitor comparison. [Phase-loop explanation](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/the-phase-loop.md).
- **Useful current empirical counterweight, October 13, 2026:** Naresh Jain compared a behavioral contract/test system against an unharnessed Codex workflow on **one greenfield Java service**, with **10 runs per condition per model** and **178 external acceptance checks**. GPT-6 Sol passed **10/10 with and without**, while adding the behavioral system used about **10.5× tokens**, nearly **3× time**, and about **7× estimated cost**. GPT-6 Luna passed **3/10 without versus 10/10 with**, and the supported Luna runs cost less than unsupported Sol in that sample. This is evidence that model capability and task matter, not evidence against specs: **both conditions received an unusually detailed application brief**. [Experiment and limitations](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html).
- **Important limits of that experiment:** Jain founded Specmatic, the tool used for the behavioral system; costs are API-equivalent estimates, not actual bills; authoring/maintaining the contracts was excluded; no brownfield condition; no direct evaluation of the six frameworks here; guides and tests were added together, so their effects cannot be isolated. He argues for independent verification even when a stronger model succeeds unaided. [Experiment](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html).

### Inferences

- The credible recurring complaint is **mis-sized process**, not “requirements are useless.” Four current alternatives explicitly respond with smaller paths: Kiro Quick Spec, Superpowers trivial/inline work, BMAD direct Build, and GSD Quick. Spec Kit adds an independent bug workflow. These changes undermine claims that launch-era three-/seven-step ceremonies are permanent. [Kiro](https://kiro.dev/docs/specs/quick-spec/), [Superpowers](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md), [BMAD](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md), [GSD](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/the-phase-loop.md), [Spec Kit](https://github.com/github/spec-kit/blob/v1.2.5/README.md).
- **More reviewers do not guarantee independent truth.** Fresh agents reduce shared conversational baggage, but if the same mistaken prose guides code, tests and reviewers, all can agree on the wrong outcome. A supplied acceptance check independent of the implementer's interpretation is stronger evidence than an LLM's `verified` label. [Jain's discussion of guides/sensors](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html), [Superpowers failure disclosures](https://github.com/obra/superpowers/blob/v7.0.1/RELEASE-NOTES.md).
- **Durable intent and durable transcripts are different needs.** Keeping a short behavior contract or decision rationale can help; retaining every plan, discovery note and greenfield PRD in active context can create false authority. OpenSpec's delta model and BMAD's advice to keep irrelevant old context out of ordinary changes offer different, plausible answers to that problem. Neither has been proven categorically better here. [OpenSpec schema](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/schemas/spec-driven/schema.yaml), [BMAD brownfield guidance](https://docs.bmad-method.org/existing-codebases/start-in-an-existing-codebase/).
- Vendor comparisons are especially unreliable in this fast-moving category. OpenSpec's current Kiro claim is already contradicted by primary Kiro evidence. Similar launch-era conclusions about required branches or compulsory enterprise documents should be rechecked before recommending retirement of an existing workflow. [OpenSpec README](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/README.md), [Kiro changelog](https://kiro.dev/changelog/), [Spec Kit quickstart](https://github.com/github/spec-kit/blob/v1.2.5/docs/quickstart.md).

### Gaps

- No reliable independent head-to-head evaluation was found that establishes the best of these six current versions for a solo developer's recurring brownfield work.
- No sourced quantitative estimate here for production defect reduction, long-term spec drift, net developer time saved, or break-even task size for any framework.
- Maintainer internal behavior tests establish something about instruction compliance in selected scenarios, not production software effectiveness. Stars, downloads and community size were deliberately excluded as outcome measures.
- The archived GSD repository and current GSD Core have different release histories. Research did not establish how old independent experience transfers to today's stable Core implementation.

## 3. Is spec-driven development obsolete, and what should a solo developer evaluate before retiring SpecFlow?

### Takeaway

**No evidence supports calling spec-driven development obsolete.** The active direction is smaller, iterative, risk-adaptive workflows with durable intent and stronger verification. What is increasingly hard to defend is a universal, document-heavy pipeline applied equally to a typo, a risky migration and a new product. The prudent alternative to maintaining an extensive homegrown library may be a native agent plus a few strong controls, not necessarily another full framework.

### Cited findings

- Böckeler's taxonomy separates the modest, useful practice of **spec-first** work from the much stronger aspiration of **spec-as-source** generation. Her article explicitly values crafting specifications while challenging elaborate implementations and maintenance assumptions. Rejecting the strongest claim does not invalidate the weaker one. [October 15, 2025 article](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html).
- Continued evolution is directly observable in 2026 releases: Spec Kit's process platform/convergence, Superpowers' inline execution and brainstorming retuning, OpenSpec's fluid action/schema model, GSD Core's stateful phase system, and Kiro's Quick Spec. Release activity proves ongoing development, **not superiority**. [Spec Kit](https://github.com/github/spec-kit/blob/v1.2.5/README.md), [Superpowers](https://github.com/obra/superpowers/blob/v7.0.1/RELEASE-NOTES.md), [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/docs/workflows.md), [GSD](https://github.com/open-gsd/gsd-core/blob/v1.19.0/README.md), [Kiro](https://kiro.dev/docs/specs/quick-spec/).
- Stronger models can eliminate the observed benefit of some extra in-loop machinery on a well-specified task, while weaker ones may benefit substantially. The October 2026 experiment explicitly leaves open different tasks, poor briefs, legacy code and final-gate-only checks. This supports **measuring the smallest sufficient process**, not assuming either “agents need all this” or “agents need none of this.” [Jain experiment](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html).

### Inferences: candid shortlist for a solo/local developer

These are recommendations from the mechanisms above, not a verdict on SpecFlow itself. A separate researcher is auditing that library.

| Actual pain to solve | First alternative to trial | Why / principal cost |
|---|---|---|
| Too much homegrown workflow maintenance; mostly bounded existing-code changes | **Native agent plan mode + concise repo guidance + independent test gate**, then **Superpowers inline** | Establish whether an additional framework earns its keep. Inline adds explicit TDD, execution memory and review without per-task worker fleets. [Inline design](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md), [conditional-overhead evidence](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html). |
| Requirements disappear between sessions, or behavior contracts drift | **OpenSpec** | Explicit capability specs and change deltas; comparatively little orchestration. Cost: ongoing spec/code reconciliation and archive discipline. [Schema](https://github.com/Fission-AI/OpenSpec/blob/v1.15.0/schemas/spec-driven/schema.yaml). |
| Native sessions get lost across a long roadmap; want longer unattended execution | **GSD Core** | Durable state, fresh bounded agents, dependency waves and verification/fix planning. Cost: `.planning/` state, commands/configuration, execution orchestration and token overhead. [Design](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/context-engineering.md). |
| Need broader discovery/product/architecture tools as well as coding | **BMAD**, with a pinned stable/preview decision | Direct Build for ordinary work and optional planning depth. Cost: broad ecosystem and current documentation/version transition. [Pinned Build](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md), [preview warning](https://docs.bmad-method.org/start/build-your-first-change/). |
| Want shared, customizable methodology infrastructure or to package existing practices | **Spec Kit** | Presets/extensions/workflows/bundles can replace custom distribution plumbing. Cost: may preserve most process ownership and introduce its own configuration maintenance. [README](https://github.com/github/spec-kit/blob/v1.2.5/README.md). |
| Prefer one integrated product over managing a skill/tool collection | **Kiro local IDE/CLI** | Spec review, task execution and compaction are integrated. Cost: product switching and feature differences between CLI and IDE. [Feature matrix](https://kiro.dev/docs/specs/). |

Suggested evaluation design, **not an externally proven recipe**:

1. Use three representative tasks from the developer's real work: a small bug, a medium brownfield feature, and a high-risk cross-cutting change. Run the same model and verification standard across native baseline and one or two shortlisted alternatives.
2. Record **human minutes**, wall time, inference cost/tokens, clarification turns, artifact volume actually reviewed, regressions, test quality, and any cleanup/recovery work. Count the cost of maintaining the framework and its generated documents, not just implementation runtime.
3. Test resumption after a fresh chat. Ask whether the next agent can discover intent and current state without following obsolete artifacts. Include a deliberate requirements change midway through implementation.
4. Require independent, behavior-focused acceptance checks. Distinguish “the framework told the model to test” from “a relevant failing test was observed and the external behavior now passes.”
5. Keep only practices that change an outcome or remove real effort. Do not install two overlapping automatic process controllers together during the initial comparison; that makes attribution and debugging harder.

This evaluation proposal follows the evidence limitations and task-size warnings above rather than asserting any framework wins by default. [Evaluation caveats](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), [model/task-dependent results](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html), [GSD scoping warning](https://github.com/open-gsd/gsd-core/blob/v1.19.0/docs/explanation/the-phase-loop.md).

### Gaps

- Retirement is premature to recommend solely from this alternatives audit. It depends on which SpecFlow capabilities the developer actually uses, their maintenance cost, and whether the native baseline or a smaller upstream package covers those needs.
- The sources do not demonstrate that generating more written artifacts raises reliability, that tests-first is always the most economical cadence for frontier models, or that all specs can safely replace source code as the maintained truth.
- This audit deliberately excludes PR bots, hosted repo automation and a giant catalog of similar projects. It prioritizes locally operable, differentiated choices and explicitly bounded evidence.
