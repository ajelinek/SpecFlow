## 1. What does this repository actually provide, and how much of it is design rather than coding?

### Takeaway

SpecFlow is primarily a **library of agent instructions, templates, and worker-role definitions**. It supplies a product/design documentation system and a prescribed development process; it does not supply a compiler, BDD test runner, scheduler, or deterministic workflow engine. Treat its planning library separately from its everyday coding machinery. [Packaging: `build.sh:1-30`](../../build.sh#L1-L30); [agent installation: `install/install-agents.sh:60-76`](../../install/install-agents.sh#L60-L76); [implementation operating model: `skills/301-spec-implementation/SKILL.md:40-59`](../../skills/301-spec-implementation/SKILL.md#L40-L59).

#### Adaptive selection versus mandatory behavior inside a selected skill

- **The entire 100-series is optional**, including for existing projects. The README says these are helpful rather than required and recommends the smallest workflow fitting the task. It says `301` is for substantial work, not tiny isolated edits. [`README.md:159-178,346-354`](../../README.md#L159-L354).
- Many design skills read upstream D-docs **when present**, record missing context, omit irrelevant concerns, and avoid guessing. For example, `105` explicitly requires optional sections to earn their place; `110` notes missing architecture docs rather than blocking. [`skills/105-frontend-architecture/SKILL.md:50-59`](../../skills/105-frontend-architecture/SKILL.md#L50-L59); [`skills/110-feature-overview/SKILL.md:29-33`](../../skills/110-feature-overview/SKILL.md#L29-L33).
- But once chosen, some design procedures are rigid: **106 must produce three alternatives even when the direction is obvious; 107 requires three UX directions; 108 requires three layouts even for simple pages**. Each normally uses three designer workers; a close result may trigger a fourth judging call. These are not adaptive “use alternatives if uncertainty warrants” rules. [`skills/106-ui-design/SKILL.md:42-58`](../../skills/106-ui-design/SKILL.md#L42-L58); [`skills/107-ui-experience/SKILL.md:42-57`](../../skills/107-ui-experience/SKILL.md#L42-L57); [`skills/108-ui-page-design/SKILL.md:43-59`](../../skills/108-ui-page-design/SKILL.md#L43-L59).
- `201` requires a stable F-ID before creating a feature folder, even without D10; `202` requires an explicit coverage level, stable TS/TSM numbering, module membership and lifecycle tags. `203` requires code exploration and evaluation of 2–3 structural approaches. These add administrative structure beyond plain scope/acceptance writing. [`skills/201-high-level-design/SKILL.md:32-50`](../../skills/201-high-level-design/SKILL.md#L32-L50); [`skills/202-spec-design/SKILL.md:24-31,41-78`](../../skills/202-spec-design/SKILL.md#L24-L78); [`skills/203-implementation-design/SKILL.md:62-76`](../../skills/203-implementation-design/SKILL.md#L62-L76).
- `gap-check` is adaptive about *whether* to ask: it must exhaust available context first. It is mandatory about *how*: `AskUserQuestion`, exactly one gap per call, never batching, no proceeding with an unresolved required input. [`skills/gap-check/SKILL.md:50-67`](../../skills/gap-check/SKILL.md#L50-L67).

### Inferences

- The most plausible lasting value is **externalizing decisions the agent cannot discover from code**: domain facts, product intent, exclusions, business rules, navigation/role decisions, and acceptance outcomes. File catalogs and language-default engineering advice have a weaker case. This follows the distinct artifacts above and matches current native guidance to document what the agent cannot infer, rather than narrate the repository. [Claude Code best practices, “Tell Claude what it can't see”](https://code.claude.com/docs/en/best-practices#tell-claude-what-it-cant-see).
- Retiring the routine implementation pipeline does **not** require retiring domain research, product framing, data-model exploration, or UI decision records. These solve a different problem from letting an agent edit, run tests, and inspect a diff. Their value depends on whether the decisions are genuinely unresolved, not on model weakness. [Design purposes: `skills/100-domain-knowledge/SKILL.md:14-18`](../../skills/100-domain-knowledge/SKILL.md#L14-L18); [`skills/101-project-overview/SKILL.md:12-15`](../../skills/101-project-overview/SKILL.md#L12-L15); [`skills/106-ui-design/SKILL.md:12-15`](../../skills/106-ui-design/SKILL.md#L12-L15).
- A blanket description such as “waterfall requiring all D01–D10 documents before every change” would be false. A blanket description such as “just a short optional checklist” would also be false. Selection is modular; selected implementation workflows contain strict orchestration and gates. [`README.md:159-178`](../../README.md#L159-L178); [`skills/301-spec-implementation/SKILL.md:14-16,40-59`](../../skills/301-spec-implementation/SKILL.md#L14-L59).

## 2. What is the actual everyday development loop, including orchestration, testing, cleanup, handoffs and Git policy?

### Takeaway

`301` is already a multi-agent, multi-validation workflow even without `901`. `901` multiplies that workflow per scenario, layers review/cleanup and headless voting on top, and owns branches, commits and merges. The procedures are instructions for an agent to interpret, not hard enforcement. [`skills/301-spec-implementation/SKILL.md:40-59,89-145`](../../skills/301-spec-implementation/SKILL.md#L40-L145); [`skills/901-feature-loop/SKILL.md:15-22,42-58,213-268`](../../skills/901-feature-loop/SKILL.md#L15-L268).

### Cited Findings

#### `301`: strict substantial-change path

1. **Preparation:** resolve feature/scope; inspect `overview.md`, `specs.feature`, `implementation.md`; synthesize missing artifacts in order via `201/202/203/204`; route scenario creation/material revision through `202`; load principles; build a reuse inventory with Explore; consult designer for user-facing changes; update feature status; establish tests/lint/build baseline. Missing scope, design conflicts and baseline failures return blocking decisions to the caller. [`skills/301-spec-implementation/SKILL.md:24-36,65-91`](../../skills/301-spec-implementation/SKILL.md#L24-L91).
2. **Red:** a test-only coder pass cannot edit production; new tests must be discovered and fail for missing behavior, not because of harness errors. Production code is prohibited before failing tests define the target. [`skills/301-spec-implementation/SKILL.md:93-101`](../../skills/301-spec-implementation/SKILL.md#L93-L101).
3. **Green:** a production-only coder pass cannot edit tests; it must make the tests pass with minimum changes, use existing reuse candidates, and justify new files/exports/dependencies. An unplanned dependency blocks advancement. [`skills/301-spec-implementation/SKILL.md:103-112`](../../skills/301-spec-implementation/SKILL.md#L103-L112).
4. **Test cleanup:** separate coder pass, exact test files only, preserving assertions and coverage; revalidate tests. [`skills/301-spec-implementation/SKILL.md:114-120`](../../skills/301-spec-implementation/SKILL.md#L114-L120).
5. **Production cleanup:** separate coder pass, never tests, first check duplication against existing owners; revalidate tests. [`skills/301-spec-implementation/SKILL.md:122-129`](../../skills/301-spec-implementation/SKILL.md#L122-L129).
6. **Final gate:** tests, lint and build must all be clean; focused repair then rerun all three. Non-convergence returns a blocker; high-risk changes get a human-review recommendation; only then mark the overview done and report evidence/reuse. [`skills/301-spec-implementation/SKILL.md:131-145`](../../skills/301-spec-implementation/SKILL.md#L131-L145).

- **All code edits are delegated to coder; all test/lint/build commands to validator.** The orchestrator retains scope, architecture and phase state; worker packets contain only scoped excerpts and files, not the full conversation. UI behavior changes go through designer first when available. [`skills/301-spec-implementation/SKILL.md:40-59`](../../skills/301-spec-implementation/SKILL.md#L40-L59).
- **A clean literal pass implies four coder calls and ten validator calls**, before discovery, UI consultation, artifact synthesis, repair or the `301` skill's own fork invocation. This is arithmetic from baseline test/lint/build (3), four intermediate test checks (4), final test/lint/build (3), and the four coding phases. It is a structural count, not a measured runtime/token total. [`skills/301-spec-implementation/SKILL.md:89-135`](../../skills/301-spec-implementation/SKILL.md#L89-L135).
- **The minimal README path understates this internal work.** It omits standalone `203/204`, but `301` can synthesize missing design work through them. It also recommends an external `401` after `301`, although `301` has already cleaned both tests and production. The FAQ explicitly says 401 is for an *extra* cleanup pass, while the README presents it in the minimum path. [`README.md:121-134`](../../README.md#L121-L134); [`skills/301-spec-implementation/SKILL.md:70-72,114-129`](../../skills/301-spec-implementation/SKILL.md#L70-L129); [`site/src/content/docs/faq.mdx:13-22,69-72`](../../site/src/content/docs/faq.mdx#L13-L72).

#### Focused alternatives

- **302 is not TDD for new behavior.** Existing implementation is its source of truth; tests may change but production normally cannot. A small accessible-label/name/role/stable-selector testability hook is the narrow exception. It baselines, writes tests, validates, records UX/API/test-fragility smells, optionally cleans tests, then validates again. If behavior is missing or contradictory, it stops rather than writing workaround assertions. [`skills/302-test-implementation/SKILL.md:13-17,60-94`](../../skills/302-test-implementation/SKILL.md#L13-L94).
- **401 is changed-scope cleanup, not feature delivery or coverage addition.** Source and tests must be separate runs; baseline integrity is mandatory; Explore classifies cleanup, obvious in-scope risk fixes and out-of-scope opportunities; boundary expansion requires approval unless preauthorized; coder edits and validator checks. It can fix clear in-scope robustness issues, so it is broader than purely cosmetic refactoring. [`skills/401-cleanup/SKILL.md:13-35,57-107`](../../skills/401-cleanup/SKILL.md#L13-L107).
- **402's three-way failure classification is substantive.** It reproduces, reads intent sources, reviews recent code movement, compares 2–3 neighboring tests, then classifies. A business-intent question stops both test and source edits. It explicitly prohibits weakening coverage to get green or relabeling a product regression as a test issue. [`skills/402-test-correction/SKILL.md:47-57,63-108`](../../skills/402-test-correction/SKILL.md#L47-L108).

#### `900`: bounded fresh-context review

- Default is five review/fix pairs, with reviewer judging and a general-purpose worker applying only concrete findings. Every review and fix worker is fresh; transcripts are not carried forward; subsequent reviews receive the prior fix summary. The reviewer alone determines whether work is clean; the orchestrator may not waive changes because another pass is slow/costly. At cap, it escalates rather than silently accepting. [`skills/900-feedback-loop/SKILL.md:25-35,41-63`](../../skills/900-feedback-loop/SKILL.md#L25-L63).
- This is scoped convergence, not open-ended “improve everything”: no artifacts of its own, no unrelated cleanup, and new files only when a finding requires them. [`skills/900-feedback-loop/SKILL.md:18-21,55-58`](../../skills/900-feedback-loop/SKILL.md#L18-L58).

#### `901`: full headless feature loop

- **Always:** green baseline; 201 and reviewed overview; happy-path 202 and reviewed specs; one full 301 per `@TS` grouped into TSM modules; module check and commit; aggregate source review/cleanup; aggregate test review/cleanup; round check; final validation; lifecycle updates; non-fast-forward merge back. **Default optional second round:** balanced coverage; can be `none` or comprehensive. This is not a requirement for ordinary use of SpecFlow. [`skills/901-feature-loop/SKILL.md:15-38,197-268`](../../skills/901-feature-loop/SKILL.md#L15-L268); [`README.md:331-344`](../../README.md#L331-L344).
- Every blocking question goes through a Decision Consult instead of a human. One consult calls decider, which itself makes three Opus subcalls. The headless run acts immediately on the chosen option or documented fallback. [`skills/901-feature-loop/SKILL.md:44-47,80-87`](../../skills/901-feature-loop/SKILL.md#L44-L87); [`agents/decider.md:41-81`](../../agents/decider.md#L41-L81).
- Green Check uses four validator calls: unit, integration/e2e, lint, build. Module Check uses two: module tests and lint. Failing tests route through 402; lint/build through focused coder repairs. Artifact review caps are one fix cycle; aggregate cleanup caps are two. Per-scenario 301 calls do not get their own 900 wrapper. [`skills/901-feature-loop/SKILL.md:91-138`](../../skills/901-feature-loop/SKILL.md#L91-L138).
- The README candidly warns that several scenarios across two rounds can involve **on the order of a hundred or more subagent invocations** and says this is “heavy by design.” This is the author's estimate, not a benchmark independently reproduced here. [`README.md:341-344`](../../README.md#L341-L344).

### Inferences

- **Good guardrails, expensive implementation:** scope packets, red/green evidence, a baseline and an intent-ambiguity escape hatch are valuable. Requiring separate workers for every edit and every simple shell check is an implementation choice, not a necessary consequence of those guardrails. Current native docs explicitly note that a new worker pays to reacquire context and can be slower than working in place. [`skills/301-spec-implementation/SKILL.md:40-59`](../../skills/301-spec-implementation/SKILL.md#L40-L59); [Claude Code best practices, “Know what subagents cost”](https://code.claude.com/docs/en/best-practices#know-what-subagents-cost).
- **Repeated cleanup and validation stack up:** 901 uses full 301 per scenario, so 301's internal test/source cleanup and full validation remain present; 901 then adds module checks, round cleanup, round/final checks. “No per-module cleanup” does not cancel 301's internal cleanup. The standalone README path also adds 401 after an already-cleaning 301. [`skills/301-spec-implementation/SKILL.md:114-135`](../../skills/301-spec-implementation/SKILL.md#L114-L135); [`skills/901-feature-loop/SKILL.md:213-233`](../../skills/901-feature-loop/SKILL.md#L213-L233); [`README.md:121-127`](../../README.md#L121-L127).
- **A feature-wide status can be misleading under scenario-level execution:** every 301 scope, including one scenario, marks the feature overview `done` after its own validation; 901 also marks whole-feature done only at Step 20. An interrupted run can therefore have a done overview with pending scenarios, while resume selection interprets done as follow-on/new-run. This is a source-contract conflict, not an observed failed run. [`skills/301-spec-implementation/SKILL.md:26-29,140`](../../skills/301-spec-implementation/SKILL.md#L26-L29); [`skills/901-feature-loop/SKILL.md:179-188,213-216,261-262`](../../skills/901-feature-loop/SKILL.md#L179-L262).
- **Headless safeguards replace the developer's judgment rather than preserve it.** A multi-vote agent cannot discover an unstated product preference just by agreeing with itself. Decider also converts unanimous votes to high confidence even if the per-vote method permitted low-confidence picks; unanimous correlated inference is not independent validation of business intent. [`agents/decider.md:43-65,93-97`](../../agents/decider.md#L43-L97); [`skills/901-feature-loop/SKILL.md:44-47`](../../skills/901-feature-loop/SKILL.md#L44-L47).
- **There are unattended-run safety/ownership costs:** baseline repair occurs before feature branching; dirty user work can be automatically stashed; the skill specifies no corresponding stash restoration step; final cleanup can expand scope via blanket preauthorization; conflict default favors feature changes. Those are poor defaults for a single developer juggling unrelated local edits unless deliberately accepted. They are not changes made in this audit. [`skills/901-feature-loop/SKILL.md:169-193,246-268`](../../skills/901-feature-loop/SKILL.md#L169-L268).
- **Resume logging is useful but underspecified:** step-complete records include a commit SHA, while the protocol requires those same log lines in that commit. Recording a commit's own final SHA inside that commit needs a different convention than stated. Resume also records top-level steps, not a formally specified transaction around every inner module. This is an implementation ambiguity in prompt text, not proof that logging fails in practice. [`skills/901-feature-loop/SKILL.md:50-54,144-161,213-222`](../../skills/901-feature-loop/SKILL.md#L50-L222).
- **Native portability is partial:** Markdown templates and principles move easily; `context: fork`, Claude-style agent frontmatter/model aliases, AskUserQuestion, and claude-in-chrome names are host-specific behavior. Native Claude docs explicitly distinguish open Agent Skills fields from Claude extensions. Nested cleanup can also exceed a host's default delegation depth: 901 fork → 900 fork → Apply-Fix worker → 401 fork → coder/validator is deeper than the documented current Claude default of three subagent layers. Source fidelity therefore depends on harness configuration or collapsing delegations, not merely installing the Markdown. [`skills/901-feature-loop/SKILL.md:125-136`](../../skills/901-feature-loop/SKILL.md#L125-L136); [`skills/900-feedback-loop/SKILL.md:41-58`](../../skills/900-feedback-loop/SKILL.md#L41-L58); [`skills/401-cleanup/SKILL.md:39-42`](../../skills/401-cleanup/SKILL.md#L39-L42); [Claude Code nested subagents](https://code.claude.com/docs/en/sub-agents#let-subagents-spawn-their-own-subagents); [skill frontmatter portability](https://code.claude.com/docs/en/skills#using-skill-frontmatter-outside-claude-code).

### Gaps

- No execution traces establish actual invocation counts, skip behavior, duration, or recovery behavior for 301/901. Structural counts assume literal compliance with the instructions; agents may deviate.
- No durable append writer, log validator, status reconciler, or workflow transaction implementation was identified in the inspected distribution. The ledger's guarantees are requested behavior. Packaging and the visualization are not such implementations. [`build.sh:13-24`](../../build.sh#L13-L24); [`site/src/lib/feature-loop-steps.ts:1-9`](../../site/src/lib/feature-loop-steps.ts#L1-L9).
- Effective tool permissions, nested-worker support, exact model alias resolution, and skill-fork behavior in the user's other installed harnesses were not tested. Do not report “this cannot run on modern agents” as an established finding.

## 3. What is distinctive versus duplicated native behavior, and what should a solo developer keep or retire?

### Takeaway

**Recommendation: retire SpecFlow as the default mandatory coding pipeline, not as a source of useful product/design habits.** Keep a small amount of persistent intent, repository-specific constraints, a concrete verification command, and optional independent review. Preserve selected design skills only where they save real thinking or communication; avoid retaining the numbering, status machinery and worker choreography just because they already exist. This is a reasoned recommendation, not a measured superiority claim. [Repository already recommends proportionality: `README.md:346-354`](../../README.md#L346-L354); [current native best-practice guidance](https://code.claude.com/docs/en/best-practices).

### Cited Findings

#### Native agents now provide the underlying mechanisms

These are claims from **live primary documentation retrieved on the audit date**, not assumed release dates, independent reliability measurements, or a claim that every installed version has them:

- Claude Code documents a self-contained default loop: with a runnable pass/fail check, it changes code, executes the check, reads failures and retries. The docs give a plain prompt requesting a failing reproduction test before a fix. They distinguish prompts/skills from deterministic hooks, permissions and sandboxes. [Best practices, “Give Claude a check to run”](https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run); [specific prompt examples](https://code.claude.com/docs/en/best-practices#write-a-specific-prompt); [deterministic versus non-deterministic instructions](https://code.claude.com/docs/en/best-practices#deterministic-and-non-deterministic-instructions).
- Native Explore, Plan and general-purpose subagents already offer separate context, custom tools, model routing, summaries and configurable nesting. The native docs explicitly describe costs: more requests/tokens, context reacquisition, and no inherent intelligence gain from sending the same task to another instance. [Native subagent guide](https://code.claude.com/docs/en/sub-agents#built-in-subagents); [best practices, subagent costs](https://code.claude.com/docs/en/best-practices#know-what-subagents-cost).
- Native guidance already recommends an independent reviewer against a written spec, with correctness-focused criteria and “skip style,” and warns that fixing every reviewer finding can create unnecessary abstractions and impossible-case tests. This directly overlaps 204/900/reviewer and argues for severity-aware stopping rather than any-open-item veto. [Review against your spec](https://code.claude.com/docs/en/best-practices#review-against-your-spec); [SpecFlow reviewer any-size veto: `agents/reviewer.md:35-40`](../../agents/reviewer.md#L35-L40).
- Native `/init` generates instruction guidance; current docs describe a more interactive optional init with discovery, gap questions and a proposal before writes. Native guidance already says keep instructions short and record what cannot be inferred from the code. Context-manager adds a particular curation policy, not a new capability category. [Claude memory setup](https://code.claude.com/docs/en/memory#set-up-a-project-claude-md); [short instruction guidance](https://code.claude.com/docs/en/best-practices#keep-claude-md-short); [`skills/context-manager/SKILL.md:89-105`](../../skills/context-manager/SKILL.md#L89-L105).
- Codex natively reads layered `AGENTS.md`, with global/project/local precedence and a documented byte limit; this is not a feature invented by SpecFlow. Current Claude documentation also supports direct AGENTS reading, but conditionally: default behavior can prefer existing CLAUDE files, and direct support has version/configuration requirements. Therefore context-manager's statement that all agents read AGENTS every session is directionally useful but too unconditional. [Codex AGENTS guide](https://developers.openai.com/codex/agent-configuration/agents-md); [Claude AGENTS rules](https://code.claude.com/docs/en/memory#agents-md); [`skills/context-manager/SKILL.md:20-26`](../../skills/context-manager/SKILL.md#L20-L26).
- Skills themselves are now a native extension mechanism; current Claude docs list bundled review/debug/verify procedures and explain that a saved procedure is appropriate when repeatedly pasting the same team-specific instructions. That supports keeping genuinely distinctive team procedures, not recreating generic engineering knowledge. [Claude skills introduction and bundled skills](https://code.claude.com/docs/en/skills); [team procedures guidance](https://code.claude.com/docs/en/best-practices#put-team-procedures-in-skills).
- Native context compaction, session resume, worktrees, and usage/budget controls already exist. SpecFlow's artifact ledger can still add a cross-session, version-controlled semantic audit trail, but separate contexts and resumability alone are no longer a sufficient reason to build a custom pipeline. [Keep cost and context down](https://code.claude.com/docs/en/best-practices#keep-cost-and-context-down); [steer/resume sessions](https://code.claude.com/docs/en/best-practices#steer-the-session); [parallel worktrees](https://code.claude.com/docs/en/best-practices#run-sessions-in-parallel); [SpecFlow semantic log: `skills/901-feature-loop/SKILL.md:142-163`](../../skills/901-feature-loop/SKILL.md#L142-L163).

#### Distinctive strengths worth preserving

- **Scope versus acceptance versus journey:** 201 explicitly rejects acceptance criteria that are renamed scope bullets and emphasizes where the feature changes the user flow versus unchanged internals. This is a useful editorial standard for a short brief. [`skills/201-high-level-design/SKILL.md:55-77`](../../skills/201-high-level-design/SKILL.md#L55-L77).
- **Reuse-first decisions grounded in concrete existing candidates:** principles require searching before writing, naming why an existing candidate cannot work, preferring config/delete/reuse/extension before new code, and approving dependencies. The especially useful parts are named reuse candidates and dependency approval, not the long list of familiar acronyms. [`skills/engineering-principles/SKILL.md:24-54,63-86`](../../skills/engineering-principles/SKILL.md#L24-L86).
- **Three-way failure triage and business-intent stop:** 402 protects against both weakening the test and “fixing” intentional behavior. This is clearer than an unqualified “make tests green.” [`skills/402-test-correction/SKILL.md:47-57,82-108`](../../skills/402-test-correction/SKILL.md#L47-L108).
- **Behavior specs favor complete outcomes and extending existing scenarios**, rather than producing one scenario per micro-step. This helps when scenarios are actually read or reused. TS/TSM IDs and status tags are a separate administrative choice. [`skills/202-spec-design/SKILL.md:44-73`](../../skills/202-spec-design/SKILL.md#L44-L73).
- **Evidence-backed context curation and snapshot isolation:** concise root instructions, justified overlays, linked rather than duplicated documentation, and warnings against stale sibling-feature snapshots form a coherent information policy. [`skills/context-manager/SKILL.md:30-46,89-112`](../../skills/context-manager/SKILL.md#L30-L112); [`skills/context-manager/examples/specflow-AGENTS.md:11-16`](../../skills/context-manager/examples/specflow-AGENTS.md#L11-L16).
- **Optional model/worker specialization is well-motivated in places:** cheap validators for noisy long output, fresh independent review, and explicit tool limits each have a recognizable purpose. What is not established is that *every* command/edit must use them. [`agents/validator.md:13-23`](../../agents/validator.md#L13-L23); [`agents/reviewer.md:20-26`](../../agents/reviewer.md#L20-L26); [native guidance on when subagents pay off](https://code.claude.com/docs/en/best-practices#know-what-subagents-cost).
- **103.5 offers actual tooling beyond prompt choreography** if a documentation-only domain model and visual diagram are useful. It is not production authorization/validation enforcement; those directives are modeling annotations. [`skills/103.5-common-data-model/SKILL.md:13-26,114-140,208-223`](../../skills/103.5-common-data-model/SKILL.md#L13-L223).

### Inferences

#### Keep / shrink / retire recommendations for one developer

These are recommendations derived from the cited contracts, not additional repository facts.

| Disposition | What | Why / proposed replacement |
|---|---|---|
| **Keep** | A short AGENTS file with real setup/check commands, non-obvious invariants, forbidden areas and dependency policy. | Valuable across harnesses; mostly a one-time curation job. Use native init, then trim. Preserve context-manager as an optional audit template if its curation beats native output. |
| **Keep** | A short feature brief for nontrivial or ambiguous changes. | Combine intent, exclusions, observable acceptance outcomes and a short approach in one document when separate documents buy nothing. This preserves 201's useful thinking without requiring IDs or an extra planning repository. |
| **Keep, selectively** | Domain/product/data-model/UI design skills. | These record decisions absent from code. Invoke only the one needed. Keep 103.5 only if its diagram is used; do not maintain two conceptual models. |
| **Keep as short rules** | Search/extend existing owners; approve dependencies; add a failing regression test for bugs; preserve business assertions; stop on ambiguous intent; show commands/results. | These are specific useful guardrails that can live in AGENTS or a small focused skill, without the entire principles glossary. |
| **Shrink** | 202/Gherkin. | Keep executable BDD or human-reviewed examples when a real reader/tool benefits. Otherwise write acceptance examples in the brief or the automated test itself; avoid a second manually synchronized behavior representation. |
| **Shrink** | 203/204. | For risky work, explore once, write a short file-change plan and review correctness against it. Do not require 2–3 invented alternatives or a separate artifact-consistency review for every change. |
| **Shrink** | 302/402. | Preserve the task boundaries and three-way triage, but let the main local agent inspect, edit and run checks directly unless discovery/output is large enough to justify delegation. |
| **Shrink** | 401/900. | One optional diff-focused cleanup or independent correctness review at a meaningful boundary. Separate tests/source when it prevents assertion laundering, not as a universal two-run ritual. Cap review cycles and defer low-impact taste findings. |
| **Retire as default** | 301's mandatory four-worker coding phases and ten-worker validation choreography. | Use a native end-to-end agent loop with a defined target and verification surface. Red/green evidence matters; a new worker per shell command does not inherently strengthen it. |
| **Retire for ordinary solo work** | 901, automatic decision voting, stage commits and automatic merge defaults. | Costs and ownership risks are disproportionate. A working branch/worktree, scoped task, tests/checks and one reviewed result usually supply the actual safety. Retain only as an explicit experiment with measured benefit. |
| **Retire unless actively consumed** | Stable F/TS/TSM IDs, status-tag lifecycle, per-stage JSONL bookkeeping, duplicate design/site explanations. | Their value is traceability for another consumer. If the only reader is the same developer and the native session already tracks progress, upkeep competes with product work. |

#### Minimal replacement contract

A solo developer can preserve most of the useful intent with an ordinary local-agent request:

> Understand the requested outcome and existing owner first. Ask only about genuine ambiguities. Reuse current patterns; no new dependency without approval. For a bug, reproduce it with a failing test before fixing it. Make the smallest coherent change, run the relevant checks, inspect the diff, and report the commands/results and remaining risks. Do not commit or merge unless requested. If a test and plausible product intent disagree, stop and explain both interpretations.

This is a proposed prompt, not a guarantee of adherence. If a rule truly cannot have exceptions, enforce the boundary or check with the host's permission controls, sandbox or deterministic hooks rather than adding stronger wording to a skill. [Native deterministic controls](https://code.claude.com/docs/en/best-practices#enforce-the-rules-that-cant-have-exceptions); [native specific failing-test prompt](https://code.claude.com/docs/en/best-practices#write-a-specific-prompt); [SpecFlow ambiguity protection](../../skills/402-test-correction/SKILL.md#L90-L105).

#### Fair test before deleting the library

- Run a small paired trial on representative local work: a bug fix, a test-only gap, a modest feature and one cross-layer/risky feature. Compare native+short-guidance against the present workflow. Measure elapsed time, token/usage cost, developer interventions, verification commands actually run, useful versus rejected review findings, reviewable diff size, and defects caught after completion. Do not declare victory from shorter prompts alone. This is a proposed evaluation design; the current repository provides no such comparison in the inspected sources.
- Keep quality gates constant between arms. Otherwise, a faster native arm with fewer checks or a slower SpecFlow arm doing extra product/design work is not a fair comparison. Distinguish documented intent quality from implementation correctness and from operational cost. This follows the repository's separation of scope, behavior and code-change plan and the native guidance to judge by runnable checks. [`skills/204-feature-validation/SKILL.md:14-18`](../../skills/204-feature-validation/SKILL.md#L14-L18); [native check-driven verification](https://code.claude.com/docs/en/best-practices#give-claude-a-check-to-run).
- For an immediate low-risk move, **stop invoking 901 and stop making standalone 401 mandatory**, while leaving the files available. Then test direct native implementation with a small brief and concrete checks. This is consistent with SpecFlow's own smallest-workflow advice and with the FAQ's explanation that 301 already includes cleanup. [`README.md:341-354`](../../README.md#L341-L354); [`site/src/content/docs/faq.mdx:69-72`](../../site/src/content/docs/faq.mdx#L69-L72).

### Gaps

- Native product documentation is authoritative about documented features, but it is vendor-authored advice, not independent evidence that default agents always follow TDD, preserve scope or catch defects. No numerical reliability or productivity advantage is claimed here.
- No specific local Claude Code/Codex/OpenCode versions, subscriptions, usage limits, effective model aliases or other installed guidance were audited. The replacement must be tested in the user's actual harness, especially for instruction loading, automatic delegation, nested skill forks and permissions.
- The parent's adjacent research should supply broader independent/industry evidence. This note intentionally prioritizes what the actual SpecFlow source does and the small set of primary native documentation needed to identify functional overlap, without importing PR automation or hosted coding products into the comparison.
