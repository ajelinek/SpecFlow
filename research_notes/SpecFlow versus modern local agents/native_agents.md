# Native local agentic-development workflows: Claude Code, Codex, and Cursor

Scope: developer-driven work against a local checkout, including local CLI, IDE, and desktop sessions. Hosted PR reviewers, GitHub issue agents, cloud coding pipelines, and cloud coordinators are excluded from the comparison. Research access date: **2026-10-28**. Dates below come from fetched source pages or release metadata, not from the environment date alone. Documentation without a visible publication date is marked **undated; verified on access**, not represented as newly released. No repository audit or product testing was performed. OpenCode was omitted to keep the primary comparison focused.

## 1. What daily loop do the vendors recommend, and how much up-front specification?

### Takeaway

All three support a short, adaptive local loop: give the agent the outcome and constraints, investigate or plan when warranted, implement, run checks, review the result, and steer. Written specs, TDD, and longer execution plans remain supported practices, but the reviewed guidance does not prescribe an elaborate staged document pipeline for every change. [Claude best practices](https://code.claude.com/docs/en/best-practices); [Codex best practices](https://learn.chatgpt.com/guides/best-practices); [Cursor best practices](https://cursor.com/blog/agent-best-practices)

### Cited Findings

**Claude Code: start with a plain prompt; add project knowledge and observable checks.**

- The current, undated best-practices page opens: **“your first plain prompt in a fresh session already does the right thing, without any setup on your part.”** Its structure is now “Tell Claude what it can't see,” “Give Claude a check to run,” and “Enforce the rules that can't have exceptions.” This is vendor guidance about intended usage, not measured proof that defaults are always adequate. [Source](https://code.claude.com/docs/en/best-practices)
- Claude recommends supplying concrete behavior, scope, examples, and verification. Its bug-fix example asks for a failing regression test followed by the fix. When requirements are unclear, the suggested prompt is **“Interview me until you could write the spec, then write it to SPEC.md.”** It then suggests building in a fresh session from that spec. This is explicit support for specification when useful, without requiring separate overview, behavior-spec, and implementation-design artifacts. [Source](https://code.claude.com/docs/en/best-practices)
- Native Plan mode reads the repository and proposes changes before source edits. A human can edit the plan in their editor, request revisions, or approve and choose an execution permission mode. Plan mode is not an absolute read-only security boundary in every configuration: the documentation explicitly describes exceptions when bypass permissions are available. [Source, undated](https://code.claude.com/docs/en/permission-modes.md)
- The preferred verification loop is **“makes the change, runs the check ... fixes it before running the check again.”** Checks can be tests, typechecking, lint, build exit codes, fixture diffs, or browser evidence. Claude recommends requesting the exact command and output, not accepting “all tests pass” as sufficient evidence. It also documents `/verify` and a local `/code-review` fresh-subagent review. [Source](https://code.claude.com/docs/en/best-practices)
- The same page recommends review against `SPEC.md`, but explicitly says to focus on correctness and **“skip style”** because a reviewer asked to find problems will keep finding something. For steering, it recommends interrupting drift early and, after two unsuccessful corrections, starting fresh with a better prompt. [Source](https://code.claude.com/docs/en/best-practices)

**OpenAI Codex CLI/app/IDE: one coherent outcome per chat; plan difficult work; test and review before acceptance.**

- The current, undated cross-surface best-practices guide suggests four prompt elements: **Goal, Context, Constraints, Done when**. It says Codex can be useful with minimal setup, but clear context improves reliability on larger or higher-stakes tasks. [Source](https://learn.chatgpt.com/guides/best-practices)
- Its planning recommendation is conditional: **“If the task is complex, ambiguous, or hard to describe well, ask Codex to plan before it starts coding.”** Plan mode (`/plan` or Shift+Tab) is described as the easiest option for most users. Alternatives are an agent interview or, for advanced long-running work, a `PLANS.md` execution-plan template. [Source](https://learn.chatgpt.com/guides/best-practices)
- The guide says to ask Codex to write or update tests, run relevant suites and lint/type checks, confirm requested behavior, and review the diff before acceptance. `/review` can inspect uncommitted changes, a commit, or a base-branch diff, with custom review instructions. This is local review, distinct from the hosted GitHub review feature also mentioned on that page. [Source](https://learn.chatgpt.com/guides/best-practices)
- The concrete local bug-fix workflow supplies reproduction steps, constraints, and **“Keep the fix minimal and add a regression test if feasible.”** It asks for local reproduction, a patch, rerunning the reproduction, and lint plus the smallest relevant test suite. The UI workflow explicitly encourages small focused iterations and browser inspection. [Source: `/codex/workflows` currently resolves to the expanded Prompting guide](https://developers.openai.com/codex/workflows)
- The CLI documentation describes the loop directly: explore, plan, edit, run local development tools, inspect commands/diffs, and steer the current turn. Codex supports saved-chat resumption; the best-practices guide recommends **“one chat per coherent unit of work,”** retaining a chat for the same problem and forking only when work genuinely branches. [CLI](https://developers.openai.com/codex/cli/features.md); [best practices](https://learn.chatgpt.com/guides/best-practices)
- The official ExecPlan recipe is a real example of heavier specification: self-contained living documents with progress, discoveries, decisions, acceptance evidence, milestones, and recovery instructions. It says **“Milestones are narrative, not bureaucracy”** and requires updates as discoveries change the plan. **Important qualification:** the fetched recipe now carries **“This recipe is archived and may reference outdated models or APIs.”** The current best-practices guide still links it as an advanced option. Thus neither “OpenAI rejects specs” nor “OpenAI recommends this archived template as the universal daily loop” is accurate. [Archived recipe](https://developers.openai.com/cookbook/articles/codex_exec_plans); [current guide](https://learn.chatgpt.com/guides/best-practices)

**Cursor: plan before complex work; use explicit TDD where desired; keep customization small.**

- Lee Robinson's official **2026-01-09** guide calls planning the most impactful change and documents Plan mode: research the codebase, ask clarifying questions, produce a plan with file paths/references, and wait for approval. But it also says: **“Not every task needs a detailed plan. For quick changes ... jumping straight to the agent is fine.”** Editable plans can be saved under `.cursor/plans/`. [Source](https://cursor.com/blog/agent-best-practices)
- Cursor explicitly recommends a five-step TDD workflow: write tests from expected behavior; run and confirm failure without implementation; commit tests; implement without changing the tests; commit implementation after review. This is a documented workflow the agent can follow, not evidence that every default run automatically enforces tests-first. [Source](https://cursor.com/blog/agent-best-practices)
- The guide recommends letting the agent discover context with search instead of tagging every file; starting a new chat for a different task, repeated confusion, or a completed logical unit; and referencing previous chats rather than copying their entire contents. [Source](https://cursor.com/blog/agent-best-practices)
- Its customization advice is **“Start simple. Add rules only when you notice the agent making the same mistake repeatedly.”** It recommends focused commands, test/build/typecheck commands, canonical code examples, careful diff review, and verifiable goals. It also offers Debug mode: hypotheses, instrumentation, user reproduction, runtime evidence, then a targeted fix. [Source](https://cursor.com/blog/agent-best-practices)

### Inferences

- **For the SpecFlow decision:** vendor guidance supports retaining a compact, reusable method for ambiguous or risky work, but not requiring the full staged library on routine fixes. A risk-sized entry point could choose direct change, short plan, or full spec/TDD workflow. This is a synthesis, not a vendor claim or a verdict on the actual repository. [Basis: Claude](https://code.claude.com/docs/en/best-practices), [Codex](https://learn.chatgpt.com/guides/best-practices), [Cursor](https://cursor.com/blog/agent-best-practices)
- The useful distinction is **structured intent and acceptance evidence versus prescribed paperwork**. Current docs support the first strongly. Their conditional planning and living-document recommendations do not support freezing detailed implementation decisions before discovery. [Basis: Codex planning](https://learn.chatgpt.com/guides/best-practices), [ExecPlans](https://developers.openai.com/cookbook/articles/codex_exec_plans), [Cursor planning](https://cursor.com/blog/agent-best-practices)

### Gaps

- These sources do not establish that any vendor's workflow is more productive than SpecFlow, or that dropping SpecFlow improves outcomes. No controlled comparison against this library was found or attempted. Vendor assertions about better results, speed, or the best defaults should not be reported as independent productivity evidence.
- The current Claude page differs substantially from familiar older “explore, plan, code, commit” summaries, but the page has no visible revision date. Its exact rewrite date was not established.

## 2. Which capabilities are native, and what work remains for a framework?

### Takeaway

The basic machinery is native across the three products: persistent guidance, on-demand skills, planning, file/terminal execution, test iteration, context controls, delegated agents, and parallel checkout workflows. A framework's remaining value is the team's specific method: what to specify, which risks to test, how to accept work, and which artifacts or approvals must exist. Prompted process is not the same as enforced policy. [Claude](https://code.claude.com/docs/en/best-practices); [Codex](https://learn.chatgpt.com/guides/best-practices); [Cursor](https://cursor.com/blog/agent-best-practices)

### Cited Findings

[Docs](https://developers.openai.com/codex/guides/agents-md.md) | `.cursor/rules/` for durable guidance; keep essentials and code pointers. [Guide](https://cursor.com/blog/agent-best-practices) |

**Important operational details and limits:**

- Claude distinguishes **non-deterministic** prompt/`CLAUDE.md`/skill instructions from **deterministic** hooks, permission rules, and managed settings. Its explicit advice is **“If something has to happen every time, make it a hook, a deny rule, or a managed setting.”** Even Stop-hook completion enforcement has a documented block cap; it is not an unlimited correctness guarantee. [Source](https://code.claude.com/docs/en/best-practices)
- Codex hooks are enabled by default in the fetched current docs. They support command/MCP handlers at tool, prompt, compaction, subagent, and session lifecycle events. Non-managed hooks require review and trust of the exact definition. A `Stop` hook can create a continuation prompt, but hooks are described as **“a useful guardrail, not a complete enforcement boundary.”** MCP callback errors can fail open; background hooks cannot block or approve the action. [Source](https://developers.openai.com/codex/hooks.md)
- Codex's skills list has a context budget: by default at most 2% of the model window, or 8,000 characters when unknown; it can shorten descriptions and omit skills with a warning. This creates a concrete reason to test discoverability of a large skill library, rather than assuming that progressive loading makes catalog size free. [Source](https://developers.openai.com/codex/skills.md)
- Codex's local subagents inherit the parent's sandbox and approval policy. Custom instructions that ask an agent to be read-only **do not create a separate read-only sandbox**. Current local Codex delegates on a direct user request or applicable project/skill instruction, rather than assuming unrestricted proactive delegation. The docs recommend read-heavy parallel work first and warn that parallel writes add conflicts and coordination costs. [Source](https://developers.openai.com/codex/subagents.md)
- Cursor's current custom subagent schema includes `readonly: true`, documented to restrict edits and state-changing shell commands. Its native orchestrator example already describes **Planner → Implementer → Verifier** with structured handoffs. The docs recommend starting with 2–3 focused agents and warn against dozens of vague ones. This overlaps directly with generic framework orchestration, while leaving the team's actual criteria and prompts to configure. [Source](https://cursor.com/docs/subagents)
- Worktree separation is not automatic resource isolation: the Codex worktree docs explicitly discuss dependencies/setup and ignored environment files, while Cursor says subagents share a checkout by default. A process still needs to account for shared ports, databases, credentials, and external side effects; the latter is an engineering inference from checkout-level rather than full-machine isolation. [Codex](https://developers.openai.com/codex/app/worktrees.md); [Cursor](https://cursor.com/docs/subagents)

**Human approval is native, but its meaning differs by surface and setting.**

- Claude's main-session Plan mode offers human approve/revise controls. Its current interactive CLI/VS Code default is Auto mode on supported versions, where a classifier replaces routine human permission prompts; Manual mode remains available. The docs warn Auto mode is not a safety guarantee. **Agent-team plan approval is different:** a teammate spawned while the lead is planning can have its plan automatically approved, without lead review. Other cases can be lead-model approved rather than human approved. Do not count “teammate plan approval” as a human gate. [Modes](https://code.claude.com/docs/en/permission-modes.md); [teams](https://code.claude.com/docs/en/agent-teams.md)
- Codex separates approval policy from OS-level sandboxing. The current best-practices guide recommends default permissions first, loosening only for trusted workflows, and reviewing changes before acceptance. [Source](https://learn.chatgpt.com/guides/best-practices)
- Cursor's current security docs say source edits save immediately without approval, except protected configuration cases; terminal commands require approval by default, with configurable Run Modes and Auto-review. They warn that auto-reload may execute changes before review and that run-mode guardrails are best-effort, not hard security boundaries. [Source](https://cursor.com/docs/agent/security)

### Inferences

- **Already commoditized:** a framework is not needed merely to provide a planning phase, run tests, isolate an independent reviewer, preserve a compacted conversation, or open separate worktrees. All three already document these primitives. [Basis: capability sources in table above]
- **Still worth preserving if demonstrated useful:** domain/business acceptance criteria; risk-specific tests and failure triage; definitions of done; the choice of task size and planning depth; evidence requirements; decision records; project-specific architecture constraints; and human approval policy. Native tools execute and store such procedures but cannot infer the team's unstated intent. [Basis: Claude “what it can't see”](https://code.claude.com/docs/en/best-practices), [Codex durable guidance](https://learn.chatgpt.com/guides/best-practices), [Cursor verifiable goals](https://cursor.com/blog/agent-best-practices)
- A plausible direction is **a thin, portable skills/policy library on top of native tools**, rather than a competing agent runtime or mandatory document waterfall. Keep an optional full-design route for high-risk changes. This is a recommendation to validate, not a claim that SpecFlow already does or fails to do it. [Basis: native skill support in Claude](https://code.claude.com/docs/en/best-practices), [Codex](https://developers.openai.com/codex/skills.md), [Cursor](https://cursor.com/docs/skills)
- Native support for a procedure does not prove automatic execution. Asking for TDD, creating a reviewer role, or saving a plan still differs from deterministic test/order enforcement and a recorded human acceptance step. [Basis: Claude instruction distinction](https://code.claude.com/docs/en/best-practices), [Codex hook limits](https://developers.openai.com/codex/hooks.md), [Cursor TDD recipe](https://cursor.com/blog/agent-best-practices)

### Gaps

- Native documentation does not establish that all desired SpecFlow artifact formats, Gherkin conventions, stage transitions, or approval records are provided out of the box. Their value requires the separate repository audit and actual usage evidence.
- Portability of `SKILL.md` does not imply identical semantics for tool permissions, hooks, custom agent schemas, or explicit-invocation policy. The fetched schemas show different mechanisms; a shared library needs adapter testing.
- No local performance/cost experiment was run. Subagent benefits and token-cost warnings are vendor documentation, not a benchmark for this project.

## 3. What changed recently, on what verified dates, and what is production versus preview?

### Takeaway

The comparison must use current docs and versioned releases, not early-2025 assumptions or old preview labels. We verified October 2026 releases directly, but not every feature has an independently dated launch or a formal GA declaration. Experimental team coordination and hosted coordinator products should not be conflated with ordinary local-agent capabilities. ### Cited Findings

**Claude Code**

- Latest release fetched from the official repository API: **v2.1.312**, published **2026-10-27T20:24:20Z**, with `prerelease: false`. This establishes a dated release, not blanket GA status for every feature inside it. [Machine-readable metadata](https://api.github.com/repos/anthropics/claude-code/releases/latest); [pinned release](https://github.com/anthropics/claude-code/releases/tag/v2.1.312)

Its release notes also change subagent compaction-window behavior. These are concrete, current maintenance changes relevant to large guidance libraries and agent context. [Release](https://github.com/anthropics/claude-code/releases/tag/v2.1.312); [fetched official changelog](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)

### Inferences

- **Do not discard SpecFlow merely because a vendor now has a Plan button or subagents.** Those changes weaken the case for maintaining duplicate orchestration, but not the case for project-specific acceptance and risk management. Conversely, a library should not justify its cost by capabilities native products already supply. [Basis: current capability comparison and vendor workflow guides above]
- The sensible evaluation is a matched local trial: native workflow plus minimal guidance versus the optional SpecFlow path, on comparable bug fixes and feature changes. Track accepted behavior, escaped defects, human steering/review time, token cost, and artifact maintenance. This is a proposed experiment, not an observed result.
- Prefer normal documented local primitives for the default path. Make experimental teams, preview consoles, or custom runtime APIs optional adapters rather than architectural requirements. [Basis: Claude team status](https://code.claude.com/docs/en/agent-teams.md), [Codex maturity definitions](https://developers.openai.com/codex/feature-maturity.md), [Codex app-server warning](https://developers.openai.com/codex/changelog)

### Gaps

- No exact introduction dates were verified for every current Claude/Codex skill, hook, Plan-mode, or local-subagent feature. Current documentation establishes availability on the access date; the notes deliberately do not manufacture launch dates.
- Cursor's current docs and dated blog use different historical feature descriptions. Where available, dated release notes and current docs take precedence for current availability; the older guide remains evidence of workflow recommendations at publication, not all present defaults.
- Some Cursor `.md` documentation URLs returned 404 even though the corresponding normal HTML URLs loaded successfully. Cited Cursor docs here were fetched through working normal URLs. Several old Codex paths redirect into its expanded ChatGPT/Codex documentation. Quotes refer to the fetched destination content.
- Official docs establish supported actions and recommendations, not independent evidence that adopting the newest product features improves this user's delivered software. A decision on whether SpecFlow is “better” still needs repo-specific assessment and the local comparison proposed above.
