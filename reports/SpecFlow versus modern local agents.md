# Retire SpecFlow’s default loop, preserve judgment

**Verdict: retire `301`/`901` as your default local coding orchestration. Do not discard the useful methods or the earlier design skills.** SpecFlow is partly out of date in where it spends effort, not in its belief that requirements, tests, and review matter. Native agents now supply much of its execution machinery, while its prescribed worker choreography adds overhead that has not demonstrated an incremental benefit over a competent native workflow. SpecFlow is neither uniquely capable nor proven superior to the alternatives. Its strongest remaining value is your accumulated judgment about product intent, scope, domain rules, reuse, and acceptance. **Confidence is high about the capability overlap and structural overhead; moderate about the net benefit of switching your own work**, because no comparative task dataset establishes that result. Make native-first development the candidate replacement, then run a fair 12–20-task trial before irreversible deletion.

**Scope and evidence date.** This report covers developer-directed work in local checkouts, including agents using remote model APIs. It excludes hosted issue-to-code systems, PR review bots, and cloud repository automation. Independent review of a local diff remains in scope. The repository snapshot is `3dfc0662dd317d4a772af005259ce87af1a600b5`, inspected October 28, 2026. All four supplied research notes were read; critical recent claims were spot-checked against original papers, tagged source, official documentation, and GitHub release metadata. Live documentation establishes what was documented on that date, not a verified launch date or successful installation. No coding benchmark or framework installation was performed. Recommendations below are synthesis, not measured productivity results.

## SpecFlow’s judgment remains useful; its default choreography needs justification

It would be unfair to describe this repository as a waterfall that requires every architecture and product document before every edit. Its README explicitly makes the 100-series optional, recommends the smallest suitable workflow, and reserves `301` for substantial implementation. The problem is more specific: **choosing a modular entry point can still activate a rigid internal process**. The advertised minimum feature path includes `201`, `202`, `301`, and cleanup; `301` itself loads or synthesizes missing overview, scenario, implementation-design, and validation work. “Only three or four commands” does not describe the work performed underneath. ([`README.md:121–178`](../README.md#L121-L178); [`README.md:346–354`](../README.md#L346-L354); [`skills/301-spec-implementation/SKILL.md:65–85`](../skills/301-spec-implementation/SKILL.md#L65-L85))

`301` requires all edits through a coding worker and all test, lint, and build execution through a validator. It separates test creation, production implementation, test cleanup, and production cleanup into four coding passes. **A literal clean run entails four coder calls and ten validator calls**, before discovery, design consultation, missing-artifact synthesis, or repairs: three baseline checks, four intermediate test checks, and three final checks. That is arithmetic from the instructions, not an observed token bill. The guards have legitimate purposes: establish a baseline, observe the right failure, prevent assertion weakening, and verify the result. A fresh worker for every phase and command is a separate implementation choice, not a requirement of those purposes. ([`skills/301-spec-implementation/SKILL.md:40–59`](../skills/301-spec-implementation/SKILL.md#L40-L59); [`skills/301-spec-implementation/SKILL.md:89–145`](../skills/301-spec-implementation/SKILL.md#L89-L145))

`901` compounds this by running a full `301` for each scenario, adding module checks, artifact reviews, aggregate source/test cleanup, another coverage round by default, and final validation. Its own README warns of roughly a hundred or more subagent invocations for a feature with several scenarios across two rounds. That estimate is the author’s warning, not an independently reproduced measurement. The workflow’s durable JSONL ledger and module commits address real continuity problems. But the round-level cleanup does not remove the cleanup already performed inside each scenario’s `301`. ([`README.md:331–344`](../README.md#L331-L344); [`skills/901-feature-loop/SKILL.md:142–163`](../skills/901-feature-loop/SKILL.md#L142-L163); [`skills/901-feature-loop/SKILL.md:213–259`](../skills/901-feature-loop/SKILL.md#L213-L259))

There is also an ownership issue. `901` converts every blocking question into an agent decision, defaults to stashing dirty work, repairs the baseline before creating the feature branch, and merges automatically, favoring feature changes when resolving conflicts. These are local operations, but they still affect your work. The decider’s three stance-framed votes provide alternative reasoning, not three independent observations of your unstated intent. Its rule that unanimity always means high confidence is especially weak when all voters share the same incomplete brief. For developer-driven work, asking you one meaningful product question can be more valuable than manufacturing consensus. ([`skills/901-feature-loop/SKILL.md:42–87`](../skills/901-feature-loop/SKILL.md#L42-L87); [`skills/901-feature-loop/SKILL.md:169–193`](../skills/901-feature-loop/SKILL.md#L169-L193); [`skills/901-feature-loop/SKILL.md:264–268`](../skills/901-feature-loop/SKILL.md#L264-L268); [`agents/decider.md:28–96`](../agents/decider.md#L28-L96))

The valuable parts deserve equal specificity. `201` distinguishes scope from acceptance: “the capability exists” is not evidence that it behaves correctly under timing, failure, and cross-feature conditions. `402` distinguishes a stale test, a source defect, and ambiguous intended behavior, then stops rather than changing either side when the business decision is unresolved. The reuse ladder asks the agent to identify existing owners before creating new code or dependencies. These are useful standards, even though none is an exclusive invention. ([`skills/201-high-level-design/SKILL.md:55–77`](../skills/201-high-level-design/SKILL.md#L55-L77); [`skills/402-test-correction/SKILL.md:47–108`](../skills/402-test-correction/SKILL.md#L47-L108); [`skills/engineering-principles/SKILL.md:19–54`](../skills/engineering-principles/SKILL.md#L19-L54))

The earlier design skills solve a different problem from orchestration. Domain research, product framing, conceptual modeling, architectural decisions, and visual direction capture information a coding agent cannot recover from existing code. Keep them when those decisions are genuinely open. Still, preserve these tools selectively: `106` mandates three design directions even when the direction seems obvious. An optional skill can contain unnecessary mandatory work. ([`README.md:163–178`](../README.md#L163-L178); [`skills/106-ui-design/SKILL.md:42–58`](../skills/106-ui-design/SKILL.md#L42-L58))

## Native agents now supply the machinery, not your acceptance judgment

The relevant comparison is **SpecFlow plus a modern agent versus that same agent used competently**, not SpecFlow versus a bare model asked to “build it.” Current Claude Code guidance centers on supplying missing project knowledge, giving the agent an observable check, and enforcing genuinely non-negotiable boundaries. It explicitly supports interviewing the developer, writing a `SPEC.md`, implementing in a fresh session, and reviewing against the spec. It also documents native compaction, resume, worktrees, skills, and fresh-context local review. Those mechanisms no longer justify a separate framework on their own. Vendor guidance establishes intended capabilities, not independent proof that the defaults always work. ([Claude Code best practices](https://code.claude.com/docs/en/best-practices))

Codex recommends Goal, Context, Constraints, and Done when; planning is conditional on complexity or ambiguity. Its local `/review` can inspect uncommitted changes, a commit, or a base-branch diff. Current local subagent workflows are enabled by default, but delegation follows a direct request or applicable project/skill instruction. Subagents inherit the parent’s sandbox and approval policy; calling a role “read-only” in its prose does not create another security boundary. These details matter when translating SpecFlow workers rather than assuming Markdown portability guarantees equivalent behavior. ([Codex best practices](https://learn.chatgpt.com/guides/best-practices); [Codex subagents](https://developers.openai.com/codex/subagents.md))

Cursor’s guidance likewise allows direct execution for small changes and planning for substantial ones. Its January 22, 2026 release introduced skills and subagents in both editor and CLI, superseding the nightly-only skills warning in its earlier January guide. Current subagent documentation includes specialist roles, isolated contexts, and optional local isolation. A planner/implementer/verifier arrangement is therefore not unique to an external library. ([Cursor workflow guidance](https://cursor.com/blog/agent-best-practices); [Cursor 2.4 release](https://cursor.com/changelog/2-4); [Cursor subagents](https://cursor.com/docs/subagents))

Availability needs precision. Claude’s ordinary subagents are distinct from **agent teams, which remain experimental and disabled by default**. Its background-agent overview is described as a research preview. Current Codex documentation does not label normal local subagents experimental, but that does not establish a formal GA date for every surrounding feature. Use the documented primitives available in your installed version; do not make preview coordination a dependency of the replacement loop. This review directly checked Claude Code, Codex, and Cursor, not every OpenCode adapter or your installed configuration. ([Claude agent teams](https://code.claude.com/docs/en/agent-teams.md); [Claude current guidance](https://code.claude.com/docs/en/best-practices); [Codex availability](https://developers.openai.com/codex/subagents.md))

Native support does not guarantee correct execution. A plan button cannot determine your product priorities, and a successful test command cannot establish that the right behavior was tested. SpecFlow’s worker boundaries are also largely instructions, not an executable workflow engine. For rules that truly cannot bend, prefer tested permission, sandbox, or command-based controls over stronger wording. Hooks themselves need failure handling and bounded retries; an LLM judging a hook condition is still model judgment. Keep independent local review where risk warrants it, focused on correctness, security, and missed requirements rather than an endless search for improvements. ([Claude instruction/enforcement distinction and local review](https://code.claude.com/docs/en/best-practices); [`agents/reviewer.md:20–40`](../agents/reviewer.md#L20-L40))

## Evidence favors proportional process, not a universal framework winner

**No verified study here establishes that SpecFlow, or any listed alternative, improves this developer’s outcomes over a current native local loop.** AI-versus-no-AI findings cannot answer that incremental question. METR’s early-2025 randomized study found 16 experienced maintainers took 19% longer across 246 tasks with AI allowed, despite believing they were faster. That is useful evidence against trusting impressions, but METR now explicitly labels those historical results out of date. Its February 2026 follow-up suggests improvement while reporting selection problems, unreliable time accounting with concurrent agents, and estimates whose confidence intervals include no effect. Neither “AI makes developers slower” nor a precise late-2026 speedup follows. ([METR original experiment](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [METR follow-up](https://metr.org/blog/2026-02-24-uplift-update/))

The repository-instruction evidence also needs reconciliation. The personally checked September 29, 2026 revision of *Evaluating AGENTS.md* uses **CTXbench**, renamed from the earlier version’s AGENTbench. It evaluates 138 tasks in twelve Python repositories, plus 300 SWE-bench Lite tasks. Generated instructions produced small, statistically nonsignificant success declines and raised average inference cost by 20% and 23% on the two datasets. Developer-committed instructions had a small, nonsignificant average gain over no instructions and significantly outperformed generated instructions. **That does not establish that all human repo guidance is useless.** ([Gloaguen et al., v3, sections 3–4](https://arxiv.org/html/2602.11988v3))

The study measures autonomous, test-scored task resolution, not stakeholder clarification, human review effort, or long-term architectural consistency. Its Python-only tasks were comparatively well specified; some descriptions and tests were generated using reference changes and then reviewed. Developer-committed does not necessarily mean wholly human-authored. Agents generally followed instructions, including tool choices, but repository overviews did not speed relevant-file discovery. Length ablations did not establish an optimal instruction size. The defensible action is to remove redundant summaries and evaluate useful instructions, while preserving non-obvious invariants, verified commands, and operational constraints. SpecFlow’s warning that old feature snapshots can be stale is consistent with that information policy. ([Paper limitations and ablations](https://arxiv.org/html/2602.11988v3); [`skills/context-manager/examples/specflow-AGENTS.md:5–16`](../skills/context-manager/examples/specflow-AGENTS.md#L5-L16))

Anthropic’s March 2026 engineering account supplies a particularly relevant mechanism: harness components encode assumptions about what the model cannot do. After model improvements, the author removed forced resets and then sprint decomposition; evaluator passes remained useful near the model’s capability boundary but became overhead on easier work. The original illustrated comparison cost $200 and six hours versus $9 and twenty minutes for a solo run, with substantially different output scope. That is not an equal-budget productivity experiment. It does show why freezing a workflow around an older model’s weaknesses is a maintenance liability, and why stripping everything at once can lose something useful. ([Anthropic’s harness-design account](https://www.anthropic.com/engineering/harness-design-long-running-apps))

A recent, directly checked October 13 experiment reinforces the conditional conclusion. Naresh Jain compared an executable behavioral harness with an unharnessed Codex condition on one greenfield Java service, ten runs per condition per model, using 178 external acceptance checks. GPT-6 Sol passed all ten either way; GPT-6 Luna passed three without the harness and ten with it. Extra machinery added substantial runtime and token use. **Both conditions already received an unusually detailed brief**. This is not evidence that requirements are dispensable or that a SpecFlow-style orchestration wins: the harness bundled contracts, examples, tools, and feedback, and its author founded Specmatic, the implementation used. Authoring and maintaining that material was excluded from costs. ([Experiment, methods, and limitations](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html))

The combined lesson is to separate **clear intent, executable feedback, fresh review, and worker count**. They are different interventions. An implementer, test writer, and reviewer can all share the same mistaken assumption and agree on an incorrect result. Independent acceptance checks and human product judgment are stronger evidence than unanimous agent approval. None of this argues against tests-first work: reproduce bugs before fixing them, and use TDD where it improves the design or protects behavior. It argues against equating TDD with a universal four-worker ritual.

**Is SpecFlow unique or superior? No demonstrated general superiority, and little exclusivity in its mechanisms.** Its combination of concise product/design templates, Gherkin conventions, failure triage, reuse policy, and your familiarity is a legitimate personal advantage. Replacing that with an unfamiliar framework can cost more than keeping it. Conversely, replacing `901` with GSD or all of BMAD can simply relocate the orchestration burden. OpenSpec deserves a trial for durable behavior-spec maintenance; Superpowers inline deserves one for execution discipline. Neither is an obligatory next purchase or migration.

## Replace the default with a small loop, then test what earns its place

The real bill includes human clarification, document review, monitoring, diff review, repair, model usage, waiting, and maintaining the process itself. More agent time can still save human attention, so optimize accepted work per unit of your effort rather than raw runtime alone. SpecFlow also has inspectable consistency costs: its README includes cleanup in the minimum path, while its FAQ calls `401` optional, and `301` already cleans both source and tests. Such drift makes the agent responsible for reconciling process documents before doing product work. ([`README.md:121–127`](../README.md#L121-L127); [`site/src/content/docs/faq.mdx:13–22`](../site/src/content/docs/faq.mdx#L13-L22); [`skills/301-spec-implementation/SKILL.md:114–129`](../skills/301-spec-implementation/SKILL.md#L114-L129))

The proposed replacement is deliberately small. Start with an outcome, exclusions, constraints, and observable acceptance examples. Let the agent inspect the existing implementation and ask only genuine unresolved questions. Use native plan mode for ambiguous or cross-cutting work; save one short living brief when a decision must survive the session. Implement the smallest coherent slice, reproduce bugs before fixing them, and run targeted checks while working plus the relevant regression/build/type/lint checks before acceptance. Exercise changed UI flows in a browser. Inspect the diff yourself and request one fresh, local correctness/security review when risk warrants it. Stop for material intent questions, report actual commands and results, and leave commit/merge decisions with you unless explicitly delegated.

A reusable request can preserve most of the useful policy without another framework:

> Understand the outcome and existing owner first. Reuse current patterns; no new dependency without approval. For a bug, show a failing reproduction before fixing it. Make the smallest coherent change, run relevant checks, and inspect the diff. If a test and plausible product intent disagree, stop and explain both interpretations. Report commands, results, and remaining risks. Do not commit or merge unless requested.

This is an instruction, not enforcement. Add a specific automated boundary only after identifying a real failure that warrants it. Keep multi-session notes to current decisions, completed work, blockers, and the next check. Do not recreate `901` under a new name.

| Disposition | SpecFlow material | Practical policy |
|---|---|---|
| **Keep** | `201`’s scope/acceptance distinction; reuse/dependency rules; `402`’s three-way triage | Preserve the judgment as concise rules or focused skills. No numbering system is needed to retain it. |
| **Keep selectively** | `100`–`110` discovery/design skills | Use for genuine domain/product/design decisions. Keep artifacts people consult; do not regenerate the entire stack for routine work. |
| **Keep, curated** | Context-manager’s evidence policy and stale-snapshot warning | Maintain verified commands, non-obvious constraints, and links. Check the installed harness actually loads them. Avoid duplicate repository narration. |
| **Optional** | `202` Gherkin; `203` implementation design; `204` consistency review | Use when a reader, executable BDD tool, risky decision, or cross-session handoff benefits. Otherwise combine acceptance examples and approach in one brief. |
| **Optional** | `302`, `401`, `501`/`502`, `900`, worker roles | Keep focused coverage, cleanup, exploratory QA, triage, and independent review where useful. Use bounded, severity-aware review; do not automatically add every pass. |
| **Retire as default** | `301`’s mandatory worker/validation choreography | Preserve baseline and red/green evidence without requiring a fresh worker per edit phase or check. Retain full `301` as an explicit treatment for work where it earns its cost. |
| **Retire for ordinary local work** | `901`, automated intent voting, automatic stash/merge, duplicate cleanup, unconsumed IDs/status ledgers | Archive rather than delete initially. Reintroduce only for a demonstrated traceability or unattended-continuity requirement. |

### Run a 12–20-task trial before deleting anything

Treat this as a practical screening trial, **not a statistically powered proof**. Select consecutive eligible real tasks before assignment, spanning small fixes, coverage/refactoring, normal brownfield features, and several ambiguous or cross-cutting changes. Pair roughly comparable tasks by size, risk, and familiarity, then randomize one in each pair to native-first and one to the SpecFlow workflow you would genuinely choose. Balance order and allow unscored familiarization. Do not make yourself implement the same task twice as the main comparison: the second attempt inherits the first solution.

Pin the model, reasoning setting, agent version, tools, permissions, repository base, and SpecFlow commit. Both arms receive equivalent initial information, existing domain knowledge, and acceptance standards. Native can ask questions, plan, test, and use normally available local review; it is not a deliberately weak one-shot baseline. Charge SpecFlow for generating and reviewing its extra artifacts. Use fresh conversations and isolated worktrees to prevent leakage. If the repository already benefits from years of SpecFlow documentation, disclose that this measures the **incremental execution workflow on a SpecFlow-prepared repo**, not the lifetime value of the earlier design work.

Make **human active minutes to accepted output** the primary metric, including clarification, artifact review, monitoring, manual edits, rescue, and final review. Separately record elapsed time, agent waiting, usage/cost, out-of-scope changes, incomplete attempts, and later rework. Apply the same independent acceptance gate: existing regressions, task-specific behavior checks, appropriate static/build checks, and human product/diff review. Agent-generated tests are part of the deliverable, not the only grading oracle. Use comparable budget caps and record failures rather than dropping them. Include a fresh-session resumption and a changed requirement in the task mix. Follow defects and rework for another week or two. This design addresses the perception, selection, and concurrent-time problems exposed by METR. ([Measurement lessons](https://metr.org/blog/2026-02-24-uplift-update/))

Before starting, choose what improvement would justify carrying the process, and what quality failures are unacceptable. Report per-task outcomes, total and median human effort, spend, rescues, and uncertainty. If results are noisy, collect more tasks rather than declare a winner. If SpecFlow helps only complex work, retain that path. If native wins, remove stages one at a time while keeping the guardrails that prevented observed failures. Trial at most one external alternative afterward, aimed at a demonstrated gap. Repeat the comparison after a meaningful model or agent upgrade.

## Conclusion

Your experience with SpecFlow is an asset, but it is evidence of familiarity, not proof that every layer still pays. The next useful version of the library is probably smaller: a few high-value decision aids, explicit acceptance standards, and focused procedures on top of a native agent. The burden of proof should sit with each recurring stage, not with the developer proposing to skip it.

Archive the full workflow so the decision stays reversible. If the trial shows that a particular design skill, strict test boundary, or independent review saves real effort or prevents meaningful defects, keep it without apology. If it only produces more artifacts, votes, and green labels, stop maintaining it. The goal is to stop paying for structure whose benefit you cannot observe while retaining the judgment that makes the work good.
