# Keep SpecFlow’s knowledge, retire default orchestration

**Stop using the heavy SpecFlow flow by default. Keep the useful skills, and use a native local agent loop as the baseline.** SpecFlow is not abandoned, and its emphasis on intent, reuse, tests, and independent verification remains sound. What has weakened is the case for adding a mandatory orchestration layer around capabilities that current coding agents already provide. `301` carries meaningful fixed overhead; `901` compounds that overhead and makes consequential local decisions without human confirmation. None of the research reviewed establishes that SpecFlow, a replacement framework, or native-only development is universally more productive. The practical decision is to simplify usage now, preserve specialized capabilities, and measure whether the remaining process earns its cost. Replacing SpecFlow wholesale with another fashionable framework would answer the wrong question.

*Assessment date: October 28, 2026. Scope: agents working against a developer’s local checkout, tools, and application. “Local” does not mean offline inference. Hosted repository agents, issue-to-PR systems, and hosted PR-review automation require a separate assessment.*

## SpecFlow’s useful safeguards do not require its full choreography

This assessment concerns your AI-workflow library, not the .NET SpecFlow product. The repository audit examined commit `3dfc0662dd317d4a772af005259ce87af1a600b5`. It found ongoing maintenance, optional project setup, adaptive feature preparation, and real site tests. Describing the library as an abandoned waterfall process with mandatory architecture documents would be unfair. The README explicitly makes the 100-series optional, and `301` can synthesize missing design artifacts **in memory** rather than persist them. Tiny isolated edits are already outside its intended scope. ([1: `README.md:121–178,346–354`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L121-L178); [`skills/301-spec-implementation/SKILL.md:65–76`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/301-spec-implementation/SKILL.md#L65-L76))

Several practices deserve to survive any workflow change. `201` limits scope and clarifies the user journey. `202` sizes behavioral coverage and prefers observable business outcomes. `203` investigates existing code and demands concrete reuse candidates before proposing additions. The shared engineering principles prefer no change, configuration, reuse, and deletion before new code, with approval before new dependencies. These instructions address recurring agent failure modes more directly than generic “be a senior engineer” prompting. ([1: `skills/201-high-level-design/SKILL.md:47–77`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/201-high-level-design/SKILL.md#L47-L77); [`skills/203-implementation-design/SKILL.md:62–76`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/203-implementation-design/SKILL.md#L62-L76); [`skills/engineering-principles/SKILL.md:19–54`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/engineering-principles/SKILL.md#L19-L54))

Verification is another strength. The validator must return actual command output and exit status. `402` distinguishes a faulty test, a production defect, and unclear product intent rather than weakening assertions to manufacture green tests. `900` requires explicit criteria, fresh reviewer/fixer contexts, bounded iterations, and findings tied to locations and failed requirements. These are useful local quality contracts, separable from branch automation or a numbered delivery pipeline. ([1: `agents/validator.md:21–68`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/agents/validator.md#L21-L68); [`skills/402-test-correction/SKILL.md:90–108`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/402-test-correction/SKILL.md#L90-L108); [`skills/900-feedback-loop/SKILL.md:14–63`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/900-feedback-loop/SKILL.md#L14-L63))

**The hidden cost is execution structure, not just document volume.** The advertised minimum, `201 → 202 → 301 → 401`, looks short. But `301` synthesizes missing overview/specification/implementation work and validation through upstream skills. It mandates delegated edits, validator-only command execution, baseline checks, red-before-green implementation, separate test/source cleanup, and final full checks. Skipping standalone `203` or `204` therefore need not eliminate their work. Conversely, the instructions do not establish that every run with existing artifacts repeats every upstream activity. The extra standalone `401` can overlap cleanup already inside `301`. ([1: `skills/301-spec-implementation/SKILL.md:40–138`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/301-spec-implementation/SKILL.md#L40-L138))

`901` magnifies this composition. It runs a full `301` per scenario, then adds module checks, aggregate cleanup, coverage rounds, and final checks. The README itself estimates **a hundred or more subagent invocations** for several scenarios across two rounds. That is a repository estimate, not measured consumption for your work. Local caps and cheaper-model routing exist, but the audited flow declares no run-wide time or spending ceiling. ([1: `README.md:337–344`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L337-L344); [`skills/901-feature-loop/SKILL.md:93–136,213–268`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L93-L268))

Its autonomy also deserves scrutiny. `901` replaces blocking questions with model consultation, permits stashing a dirty tree, pre-authorizes some scope expansion, and resolves merge conflicts under its own rules. A multi-model vote does not establish product intent or human authorization. These actions remain consequential even without pushing remotely. **Retire `901` from routine use**, retaining it only as an expressly chosen experiment for well-bounded work. ([1: `skills/901-feature-loop/SKILL.md:44–87,171–173,246–268`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/skills/901-feature-loop/SKILL.md#L44-L87); [`agents/decider.md:41–108`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/agents/decider.md#L41-L108))

There are compatibility ambiguities, not demonstrated failures: optional workers coexist with validator-dependent contracts, and context loading depends on harness/version configuration. Current Claude documentation now supports nested agents, so the old blanket objection that subagents cannot spawn subagents is obsolete. Some literal SpecFlow nesting paths nevertheless exceed its documented default depth. That calls for a version-specific smoke test before unattended use, not a claim that the workflow is generally broken. ([1: `README.md:83–117`](https://github.com/ajelinek/SpecFlow/blob/3dfc066/README.md#L83-L117); [2: current nested-agent documentation](https://code.claude.com/docs/en/sub-agents#let-subagents-spawn-their-own-subagents))

## Current agents reduce orchestration’s value, not intent’s value

The important industry shift is toward **native orchestration, selective context, direct tool feedback, and mechanically checked constraints**. Current Claude Code, Codex, and Cursor guidance already covers repository exploration, optional planning, editing, tests, local review, skills, context continuation, and isolated worktrees. Claude’s current advice explicitly says an ordinary first prompt often suffices and discourages redundant context management or delegation merely to obtain a supposedly smarter answer. Codex recommends goal, context, constraints, and “done when.” Cursor recommends detailed plans for difficult work, not every familiar edit. These are vendor recommendations, not comparative productivity experiments. ([2](https://code.claude.com/docs/en/best-practices); [3](https://learn.chatgpt.com/guides/best-practices); [4](https://cursor.com/blog/agent-best-practices))

This is an October 2026 assessment, not an October 2025 snapshot. The live documentation was accessed October 28; it establishes currently documented behavior, not when every feature shipped. Dated evidence includes Cursor’s January 22 release of skills/subagents and February 17 asynchronous-subagent release, and Codex’s February 2 desktop launch with local worktrees. Codex’s changelog extends through October 27. Current Codex configuration labels hooks, goals, and multi-agent support stable, while memories remain experimental. Claude’s aggregate agents view is a research preview; it is unnecessary to the recommendation. Installed versions, client capabilities, and permissions still need checking locally. ([4: release record](https://cursor.com/changelog/page/12); [3: app launch](https://openai.com/index/introducing-the-codex-app/), [current configuration](https://developers.openai.com/codex/config-basic), [changelog](https://developers.openai.com/codex/changelog))

The strongest practical improvement is often a better feedback environment. An agent that can start the application, reproduce a failure, inspect browser state and logs, and run meaningful acceptance checks has evidence that a planning document cannot supply. OpenAI’s February engineering case study describes worktree-local applications, browser access, observability, concise knowledge maps, and custom structural checks. It is a repository-specific experience report, not proof of its claimed speedup elsewhere. Its lesson is to improve the environment and verification, not simply remove all process. ([19](https://openai.com/index/harness-engineering/))

**Instructions express policy; permissions and checks enforce particular boundaries.** Native hooks differ in coverage and failure behavior, and model-evaluated hooks are still judgment calls. Cursor hooks can fail open; Codex documents unsupported and nongating paths. Neither a skill’s “must” nor a model’s “done” is equivalent to a successful command, sandbox restriction, or human approval. Preserve project-specific domain knowledge, fixtures, browser journeys, test oracles, and known traps. Let native tools supply the generic execution machinery. ([2](https://code.claude.com/docs/en/best-practices); [3: hooks](https://developers.openai.com/codex/hooks); [4: hooks](https://cursor.com/docs/hooks))

## Alternatives solve different problems, often with comparable ceremony

There is no documented winner that makes a migration obvious. The comparison below assesses intended local behavior and operating burden, **not measured superiority**. Release labels were checked October 28; several workflow descriptions come from mutable current documentation.

| Approach | Useful distinction | Cost and fit for this decision |
|---|---|---|
| **Native baseline** | Goal/constraints/acceptance, exploration, selective planning, implementation/checks, risk-sized local review | Least additional process surface. Still needs good requirements and verification. Best control condition, not guaranteed best outcome. [2–4] |
| **SpecFlow** | Reuse-first guidance, behavioral slicing, failure triage, explicit validation and isolated review | Valuable selectable skills; `301` imposes phase/delegation overhead and `901` compounds it. Keep capabilities without making the whole chain compulsory. [1] |
| **OpenSpec, v1.15.0** | Maintained current specifications plus proposed change deltas; archive synchronizes changes back | Default propose/apply/archive still produces proposal, specs, design, and tasks. Strong candidate when living requirements are the missing capability. [6] |
| **Superpowers, v7.0.1** | Prescriptive design/TDD/execution discipline; released inline execution avoids per-task agent dispatch | Still detailed planning, progress state, testing, and final review. A discipline choice, not automatically a lighter workflow. [8] |
| **Spec Kit, v1.2.5** | Reusable organizational processes and durable feature artifacts; now a composable toolkit | Standard SDD remains specify/plan/tasks/implement/converge, with optional gates and extensions. Useful for process standardization, not demonstrated attention savings. [5] |
| **BMAD, stable v6.12.4** | Investigation selects same-session minimal-spec work or fuller planning; broader product/architecture paths available | Stable already supports smaller changes, trivial bypasses, and review opt-out. Wider installation/process surface remains. v7 is preview, not the stable recommendation. [7] |
| **GSD Core, v1.19.0** | Durable phase/state management and fresh-context execution; quick and trivial inline paths exist | Normal path retains substantial planning/state and orchestration. Evaluate only if cross-session coordination is the actual problem. Its PR shipping step is outside scope. [9] |

Two distinctions matter more than command counts. First, OpenSpec’s maintained current-behavior baseline differs from a folder of point-in-time feature snapshots. SpecFlow’s overview/specs/implementation artifacts can explain a change, but do not by themselves establish a continuously synchronized whole-system specification. If revisiting business rules is costly, a living specification could justify extra maintenance. If tests and concise decisions already provide that continuity, another archive lifecycle adds little. OpenSpec’s fewer commands do not eliminate its four artifact types; removing artifacts can require a custom schema. ([6](https://github.com/Fission-AI/OpenSpec/blob/main/README.md), [customization](https://openspec.dev/docs/customize))

Second, compare installed releases rather than attractive main-branch descriptions. Superpowers’ current main README allows small designs to remain in chat, but released v7.0.1 normally requires a short written design for ordinary nontrivial changes. Its released inline executor does offer a bounded final review/fix policy rather than endless re-review. BMAD’s main documentation still labels v7 preview alpha despite a past ETA; stable v6.12.4 already supplies the adaptive build path. These differences affect daily burden without requiring a catalog of prerelease details. ([8: released brainstorming](https://github.com/obra/superpowers/blob/v7.0.1/skills/brainstorming/SKILL.md), [inline execution](https://github.com/obra/superpowers/blob/v7.0.1/skills/executing-plans/SKILL.md); [7: stable build guide](https://github.com/bmad-code-org/BMAD-METHOD/blob/v6.12.4/docs/build/build-a-change.md), [current README](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/README.md))

Adopt a framework only for a missing capability. Popularity, fewer slash commands, and more generated documentation do not establish better outcomes. Stacking a specification framework, execution framework, and SpecFlow review loops would make attribution and maintenance harder before proving any benefit.

## Evidence favors selective help, but cannot declare a winner

**No direct controlled comparison of this SpecFlow library against current native workflows was found in the reviewed sources.** That is a bounded research finding, not a claim that no such evidence exists anywhere. The studies below test different interventions and cannot supply a productivity multiplier for your workflow.

METR’s widely cited July 2025 randomized study found experienced developers slower with the then-current tools. Its original page now explicitly calls that result outdated. Its enduring relevance is the gap between perceived and measured speed. February 2026’s follow-up leaned toward speedup but called the size estimate unreliable because of participation bias, withheld tasks, and difficult concurrent-agent time accounting. May’s survey reports substantial perceived gains, but convenience sampling, low response, and counterfactual self-report prevent causal interpretation. These results concern AI versus no AI, not the marginal value of SpecFlow on top of an agent. ([10](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/); [11](https://metr.org/blog/2026-02-24-uplift-update/); [12](https://metr.org/blog/2026-05-11-ai-usage-survey/))

An October 13 practitioner experiment is more directly relevant to added process. Across ten paired runs per model on one greenfield Java API service, an independent acceptance suite found that a behavioral testing harness increased reliability for one model but added time and inference cost without improving the other model’s already perfect observed pass count. This supports a **model-dependent process trade-off**, not a universal anti-process verdict. The author founded the company implementing the harness; the experiment did not measure authoring/maintenance, human repair, long-term quality, or a final-acceptance-gate-only alternative. Ten successes also do not establish perfect future reliability. ([13](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html))

Context-file evidence needs version discipline. *Evaluating AGENTS.md*, **September 29 v3**, found no statistically significant task-resolution improvement across its tested context conditions, with added cost for generated repository summaries. Developer-provided context had a small positive mean, not a demonstrated general harm. The study covered Python issue-resolution benchmarks, not long-term maintainability, security, or undocumented organizational intent. Its redundancy findings argue against copying discoverable repository descriptions into standing instructions, not against keeping useful project knowledge. ([14](https://arxiv.org/html/2602.11988v3))

SkillsBench points in a different, compatible direction. **June 14 v4 / SkillsBench 1.1** tested 87 tasks across eight domains and 18 model–agent configurations. Curated skills improved aggregate pass rate by 16.6 percentage points, but its software-engineering subset contained only 16 tasks. The intervention was task-relevant expertise, sometimes with scripts and references, not ownership of a complete development lifecycle framework. Some tasks worsened, and the benchmark does not measure developer attention or ongoing skill maintenance. Repository summaries and focused procedural expertise are different treatments; these papers do not cancel each other out. ([15: pinned paper](https://arxiv.org/abs/2602.12670v4), [release analysis](https://www.skillsbench.ai/blogs/skillsbench-1-1))

Multi-agent evidence also resists slogans. The **April 8 v3** scaling paper adds coding benchmarks beyond the January article’s noncoding examples. Its small SWE-bench samples show lower mean resolution for the tested multi-agent configurations, but individual comparisons are underpowered; terminal-task outcomes are mixed. Coordination overhead and diminishing returns are credible mechanisms. They do not prove that a fresh local reviewer is wasteful or that SpecFlow’s particular workers fail. Results from decomposable finance tasks cannot be imported as coding-productivity gains. ([16](https://arxiv.org/html/2512.08296v3))

Practitioner accounts support both disciplined specifications and restraint. April 2026’s structured-prompt-driven development report makes a plausible case for versioned intent and repeated domain logic while acknowledging overhead and poor fit for spikes and hotfixes. The October 2025 SDD critique documents repetitive artifacts and disproportionate small-change process, but is historical experience with then-current tools, not the latest industry state. **The defensible synthesis is risk-sized specification and verification, not “specs are dead.”** ([17](https://martinfowler.com/articles/structured-prompt-driven); [18](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html))

## Simplify usage now, then test the remaining value

The recommended standard local loop is small: **goal, constraints, and acceptance → explore and reuse → short plan only if needed → implementation and test feedback → targeted independent review where risk warrants it → evidence**. Keep ordinary changes in the main agent’s context. Delegate genuinely separable investigation, noisy validation, or an independent review when that separation serves a purpose. Report what ran, what passed, what remains uncertain, and any scope changes. This is an operating recommendation, not a new mandatory SpecFlow 2 project.

Preserve the small capabilities that encode something useful: domain research and decisions, reuse guidance, behavioral examples, test-defect triage, repository-specific conventions, and browser verification procedures. Native browser access cannot tell the agent which customer roles, states, or failure paths matter. Similarly, a native review command still needs acceptance criteria and a severity threshold. Keep existing files; stop invoking unnecessary layers before considering migration or deletion.

Full BDD is justified when stakeholders consume the scenarios, domain combinations are difficult to communicate otherwise, or executable scenarios provide traceability and regression protection. Gherkin is not waste merely because a native agent can write tests. Durable architecture/specification work earns its place on multiday changes, shared interfaces, migrations, regulated decisions, and features repeatedly maintained by different people. For those cases, retain intent and decisions, define who updates them, and avoid parallel documents that silently diverge. For a familiar small fix, a regression test and short acceptance statement can be sufficient.

Local autonomy needs explicit stop conditions. Pause for ambiguous product intent, new dependencies, scope expansion, dirty-tree manipulation, destructive operations, and unresolved merge conflicts unless specifically authorized. Choose a run-wide time/cost budget before unattended work. Use one focused fresh review for material correctness, security, regression, and acceptance gaps; fix meaningful findings and verify. Escalate repeated or disputed findings rather than treating model agreement as completion. Configure permissions, sandboxing, and tested checks where enforcement matters. None of this requires hosted automation.

Run a **reversible 2–4-week comparison**, after brief native-workflow familiarization. Use comparable real tasks rather than sequentially implementing the same task twice. Match by task type, size, risk, and familiarity; assign the workflow prospectively. Hold model, reasoning settings, environment, tool access, acceptance criteria, and essential project/domain guidance constant. The treatment is native baseline plus the selected SpecFlow coordination, not a well-specified framework against a deliberately vague native prompt. Freeze versions and record all delegated model use; test cheaper-model routing separately.

Measure active human attention, elapsed time to an accepted correct change, actual usage/cost, interventions, and rework. Include clarification, reading generated artifacts, framework debugging, failed/abandoned runs, and document synchronization. Follow accepted tasks for another 7–14 days for regressions and repair time. Do not count parallel agent runtime as human labor or infer billed dollars from token counts alone. Revisit at least one feature later if persistent specifications are supposed to provide the payoff.

Set materiality thresholds in advance. **Proposed choices, not research facts:** retain substantial coordination where it repeatedly saves roughly 15% of human attention or materially reduces consequential rework at acceptable cost. Retire it as a default where it repeatedly consumes roughly 15–20% more attention without offsetting quality or reuse benefits. Simplify where benefits concentrate in a few steps or complex task classes. With a small sample, report task-level results and uncertainty; no observed defects does not establish safety equivalence. A serious workflow-attributable safety failure warrants pausing either approach.

This assessment did not execute repository workflows, tests, builds, or installers, and did not analyze your development telemetry. Site tests demonstrate maintenance effort, not agent compliance or productivity. The native capability research covered Claude Code, Codex, and Cursor; it did not establish identical behavior in OpenCode. The session’s separately requested global OpenCode model-pin repair is not evidence of a SpecFlow defect. No implementation, migration, or configuration change follows from this report without authorization.

## Conclusion

The asset worth protecting is your accumulated understanding of how good changes are specified and verified. The execution choreography is replaceable. Treat each extra artifact, worker, and review round as a cost with a specific job, then retain it only where that job matters.

The next decision is therefore a usage change, not a framework replacement: native execution by default, selected SpecFlow capabilities when they resolve real uncertainty, and explicit evidence before restoring heavier coordination. That preserves what you have learned without making past investment dictate future operating cost.
