## What this skill is for

`401-cleanup` performs a deliberate cleanup pass on an already-changed scope. It reduces duplication, improves naming and structure, and fixes obvious in-scope robustness issues — without turning the work into a broad rewrite. For test cleanup, this is still cleanup-only: no net-new coverage.

**Output**: Cleaner source files or cleaner test files. Validation proving the cleanup stayed safe.

## When to use it

- As the final steps of the Comprehensive and Conservative paths, once for source and once for tests
- After `301-spec-implementation` on any path, when the changed code warrants a separate cleanup pass
- When you want cleanup to be a distinct, reviewable operation

## When NOT to use it

- Before implementation, since there is nothing to clean
- Without a scope: `401` needs staged changes, a file set, or a diff range
- To add behavior or test coverage; that belongs in `301` or `302`

<Callout tone="core" title="One target type per run">
  Source and test cleanup are separate runs. If the changed set includes both, `401` stops and asks you to choose one side. This keeps each pass small and easy to review.
</Callout>

## What it produces

- Cleaner source or test files, depending on the target type
- Test, lint, and build output showing the cleanup is safe
- A list of out-of-scope opportunities that were noted but not acted on

## Required inputs

- A cleanup scope anchor: staged changes, a file set, or a diff range
- Exactly one cleanup target type: source code or test code

## Common prompts

<PromptBlock title="Prompt" text={`Run 401-cleanup on the changed source files.`} />

<PromptBlock title="Prompt" text={`Run 401-cleanup on the changed test files.`} />

## What usually comes next

After a source pass, run `401-cleanup` again with the test target type.

## Practical guidance

- The changed set is the boundary; ask before expanding it.
- Fix obvious in-scope risks, but do not disguise feature or architectural changes as cleanup.
- Test cleanup adds no coverage, scenarios, or test files.

## Common mistakes

- Cleaning up source and tests in one pass
- Using `401` to deliver new feature work
- Treating out-of-scope duplication as permission to refactor broadly
- Skipping validation

<Callout tone="tip" title="Out-of-scope is a list, not a permission">
  `401` lists out-of-scope opportunities instead of acting on them. Pursue them with your approval, usually as a separate run with a new scope.
</Callout>
