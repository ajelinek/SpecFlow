Use the `100` series when the project is missing domain clarity, product framing, or architectural decisions.

## Typical sequence

1. `100-domain-knowledge`
2. `101-project-overview`
3. `102-system-architecture`
4. `103-common-data-model`
5. `104-backend-architecture`
6. `105-frontend-architecture`
7. `106-ui-design`
8. `107-ui-experience`
9. Optional page-mockup step: `108-ui-page-design` (per page or related page family that needs a detailed layout reference; refreshes the shared route index each run)
10. `110-feature-overview`
11. Then move into `201 → 202 → 301` for the first real feature

`106` (Visual Design) and `107` (UX & Navigation) are independently optional and can run in either order. Use only the one whose decisions need work, or both when both are unresolved.

`110` creates the capability map and stable `F-ID`s that later feature docs can reuse for folders like `.specflow/features/F003-invoice-approval/`.

`301` keeps its implementation design in memory; `201` and `202` remain the persisted feature artifacts. On the Comprehensive and Conservative paths, finish with `401`, once for source and once for tests.

## Why this is different

Use planning skills only when the project would otherwise rest on unclear assumptions. For unfamiliar products, `100-domain-knowledge` is a live-research step, not a brainstorm.
