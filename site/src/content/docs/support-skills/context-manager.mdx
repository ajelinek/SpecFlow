## What this skill is for

`context-manager` creates or refreshes the project's `AGENTS.md` guidance from actual repository evidence. `AGENTS.md` is the tool-agnostic file for shared project guidance. The goal is to give agents a concise, trustworthy map of the codebase: where to look first, which commands are real, which architectural boundaries matter, and where local overrides apply.

This skill works from repository evidence, not assumptions — it uses `@explore` to discover the actual structure, verified commands, and architectural patterns before writing anything.

**Output paths**:
- `AGENTS.md` at the project root
- Optional nested `AGENTS.md` files in subtrees with materially different conventions
- `.specflow/AGENTS.md`, when `.specflow/` exists — describes the `context/`/`docs/`/`features/` layout and states the feature isolation rule (don't read a sibling feature's folder unless asked)

<Callout tone="tip" title="`initialize` mode">
  Besides `generate`/`refresh`, `context-manager` has a fast `initialize` mode: it only checks whether `.specflow/AGENTS.md` exists and writes it from a fixed template if not — no repo research. [`specflow-setup`](../specflow-setup/) reuses it when you approve project initialization, and you can also run it yourself once after installing the skills — see [Getting Started](../../getting-started/). No other skill calls it automatically, so the feature isolation rule stays in place without re-checking on every feature.
</Callout>

<Callout tone="tip" title="Discovery of AGENTS.md varies by tool">
  The filename is always `AGENTS.md`, but whether a tool loads it automatically, and whether nested files apply by subtree, varies by agent. Claude Code, for one, does not read a bare `AGENTS.md` on its own. `context-manager` does not create `CLAUDE.md` or other tool-specific files unless you explicitly ask. Use [`specflow-setup`](../specflow-setup/) to make sure each tool you use can find the guidance.
</Callout>

## Legacy CLAUDE.md files

If a `CLAUDE.md` already exists, its applicable project guidance is carried into `AGENTS.md` at the same scope, resolving conflicts rather than copying contradictions. The legacy file is left unchanged unless you authorize migration cleanup. In that case shared content is replaced with an `@AGENTS.md` import, or the file is removed as agreed.

## When to use it

- When setting up a repository for agent-assisted work for the first time
- When `AGENTS.md` guidance is stale or no longer reflects the actual codebase
- When a repo has only a legacy `CLAUDE.md` whose guidance should become shared across tools
- When a monorepo has packages or apps with significantly different tooling or conventions that need local overrides
- When agents are consistently making wrong decisions that accurate guidance would prevent

## When NOT to use it

- When `AGENTS.md` guidance is current and working well
- For projects where agent guidance has not been needed
- When only the root guidance needs an update — a scoped refresh is faster than a full run

<Callout tone="bonus" title="High value on first project setup">
  Getting `AGENTS.md` right early prevents a class of errors that accumulates over time — wrong commands, wrong file locations, wrong architectural assumptions. The investment in a good initial run pays off across every subsequent session.
</Callout>

## What it produces

- `AGENTS.md` at the project root with:
  - Project overview and directory structure
  - Canonical commands for setup, testing, linting, building, and local development
  - Key architectural boundaries and invariants
  - References to deeper architecture or domain docs, as relative Markdown links instead of pasted content
  - Collaboration preferences that improve agent usefulness
- Optional nested `AGENTS.md` files in subtrees with materially different conventions (local package commands, different test stacks, distinct runtime requirements), linked from the root so agents find them even without automatic discovery
- Rules that span scattered paths (for example, everything under `**/migrations/**`) are stated with explicit scope in the nearest common `AGENTS.md`

## Required inputs

1. Operation mode — generate, refresh, or initialize
2. Scope policy — root only, or nested `AGENTS.md` overlays where justified
3. Excluded paths — any directories that must not be analyzed?
4. Project-specific constraints — sensitive areas, forbidden commands, or deployment-critical paths

## What usually comes next

Returning to whatever workflow was in progress — domain research, architecture work, or the feature design loop. `context-manager` is a setup or maintenance task, not a stage in the feature lifecycle.

## Practical guidance

- Default to root-only unless there is clear evidence that a subtree has materially different tooling, commands, or conventions.
- Nested `AGENTS.md` files should be override layers, not copies of the root. Only include content that is genuinely different from the root guidance.
- Keep every `AGENTS.md` well under ~200 lines so agents can load it without crowding out task context.
- The root file should be concise — it is not a full architecture document. Link to where detailed docs live; do not duplicate them.
- Collaboration preferences (how to ask clarifying questions, response format expectations) belong in the root file only, not in nested overlays.

## Common mistakes

- Writing `AGENTS.md` without reading the actual codebase first
- Copying a legacy `CLAUDE.md` verbatim instead of reconciling it with current evidence
- Creating nested overlays that repeat root content instead of only overriding what differs
- Including inaccurate commands that fail when an agent tries to use them — verify every command before including it
- Making the root file so long that agents cannot extract the key guidance quickly

<Callout tone="tip" title="Verify commands before including them">
  Every command listed in `AGENTS.md` should be verified as working. An agent that runs a wrong command from trusted guidance is harder to diagnose than one that simply does not know which command to run.
</Callout>
