## What this skill is for

`301-spec-implementation` is the main implementation workflow for substantial features or feature chunks. It prepares feature context, builds a compact implementation design in memory, and requires two independent reviews before coding. One coder implements tests-first, a fresh coder reviews and refines the actual diff, and one validator runs the final checks.

**Output**: Updated source and test files in the codebase. An existing `overview.md` stays `implementing` for partial scope, which is reported as scope complete, not feature done. `301` marks it `done` only when the explicit run scope represents the whole feature and all acceptance gates pass. Under `901`, the caller owns whole-feature completion at its final gate instead.

## When to use it

- For a substantial feature or implementation chunk
- When the work should be driven by a spec rather than by ad hoc prompting
- When you want tests, lint, and build results to be the ground truth for completion
- As the default implementation path for most feature work

## When NOT to use it

- For test-only work — use `302-test-implementation` instead
- For tiny, obviously-scoped changes (single field rename, small bug fix) where the overhead of a phased workflow exceeds the benefit
- When you want to add or repair tests for already-implemented behavior

<Callout tone="core" title="301 is an orchestration workflow">
  `301` separates design review, implementation, independent refinement, and final validation. Two fresh, read-only `reviewer` assignments assess the same complete design brief before implementation starts. The implementation coder owns baseline and red/green checks; a fresh coder owns refinement; `validator` owns final acceptance checks. UI-affecting work should consult `designer` during preparation. Checkpoints within an assignment do not require separate worker calls.
</Callout>

## If feature artifacts are missing

If `overview.md` or `specs.feature` is missing, `301` uses inline guided generation for the missing `201` overview or `202` scenario context. It resolves the necessary scope and behavior without writing files unless you ask. Running `201` and `202` directly still produces their normal persisted artifacts.

The implementation design stays in memory unless you explicitly ask to persist it. It is versioned working context for the run, not a required feature artifact.

## The phases

### Phase 0: Prepare

Read the `201` overview and `202` scenarios, or generate missing context inline. Inspect the current code, project guidance, architecture, standards, and existing tests. Search for reuse candidates before choosing an approach, and record the paths checked.

### Phase 1: Design in memory

Build a compact, versioned design covering the approach, modules and responsibility boundaries, contracts, state and data flow, scenario-to-change/test mapping, validation checks, and assumptions. Explain alternatives only where a real choice needs resolving. Name what will be reused or extended, and justify anything new against the existing candidates.

### Phase 2: Review readiness

Dispatch two fresh, independent, read-only reviewers with the **same complete brief revision**, full scoped scenarios, constraints, readiness criteria, and exact source/doc/standards references. Neither relies on inherited memory or sees the other's conclusions:

- **Walkthrough review** follows the scenarios end to end, checking integration, reuse, and completeness.
- **Adversarial review** challenges assumptions and applicable risks, such as authorization, data integrity, concurrency, failure handling, compatibility, and accessibility. It skips risks that do not apply.

The orchestrator resolves findings against code and scenario evidence, not by counting votes. Reviewers return `CHANGES_REQUIRED` whenever a required readiness criterion fails:

- Scope, outcomes, scenarios, and design agree without missing behavior or unjustified scope.
- Every scoped scenario has a feasible end-to-end change path and observable checks.
- Module ownership, integration, boundaries, contracts, and state/failure handling are explicit and compatible.
- Reuse decisions are code-grounded, project/standards/UI constraints are satisfied, and any new dependency is explicitly approved.
- Material assumptions and questions affecting correctness, safety, or feasibility are resolved by evidence.

Allow at most **two repair rounds** after the initial reviews. Recheck affected roles in fresh contexts with the complete revised brief and their own findings' resolution evidence, never sibling conclusions. Recheck both roles when shared assumptions, scope, contracts, or scenario mappings change. Retain an unaffected review only where its criteria and evidence are unchanged. Normal acceptance requires both applicable reviews clean and every required criterion resolved.

At the cap, return a **`review_limit` decision packet**, not a terminal design blocker: the complete current brief and reviewed revision, consumed budget, actual verdicts, findings and evidence, concrete options, and a lowest-risk feasible recommendation. Under `901`, the existing decider selects the best evidence-backed way forward. Otherwise the caller decides. Re-enter at the pending phase with the caller's explicit resolution, not a fresh review budget.

The resolution names the chosen approach, per-finding accepted/rejected/deferred dispositions, evidence, and any bounded corrections. Verify those corrections without another review cycle, then continue tests-first. Confirmed correctness/security defects and missing required behavior must be addressed, not deferred. Caller authorization never changes a reviewer verdict to `CLEAN`. A genuine inability to implement safely remains a substantive blocker; exhausting the review budget alone does not.

### Phase 3: Implement tests-first

Assign one coder the approved design and scope. In one assignment, establish the baseline, write or extend tests, demonstrate the intended red failure, and implement the minimum source change to reach green. Keep baseline, red, and green evidence distinct.

Material design discoveries during implementation, refinement, or validation repair return to readiness before more implementation. They use the same repair budget, not a new cap; when exhausted, obtain an explicit caller resolution against the changed evidence.

### Phase 4: Independently review and refine

Assign a fresh coder the approved design, scoped scenarios, and actual diff. Check the implementation against the design with distinct test-quality and source-quality checkpoints. Refine within scope and rerun affected checks. Preserve assertions, coverage, intended behavior, and public contracts; never weaken a test to make the implementation pass.

### Phase 5: Validate and close

Use one final validator assignment for the required test, lint, and build checks, with separate results for each. Close with verification evidence, review resolutions, remaining risks, and status updates when the feature artifacts exist. A failed required check is not a completed run.

## What it produces

- Updated source and test files
- Status updates in `overview.md` (when it exists)
- In-memory overview and scenarios when feature context is missing
- A versioned in-memory implementation design and two independent readiness reviews
- Baseline and red/green evidence, plus independent review findings and refinements
- Final validation through test, lint, and build checks in one validator assignment

## Required inputs

- A change request or spec reference
- A clear scope: one `@TS###` scenario, one `TSM###` module, a full `.feature` file, or a tightly scoped plain-language description

Existing selected scenarios need no coverage-level classification. Synthesizing or materially revising scenarios requires an explicit coverage choice from the specs, request, or context. If none is supplied, `301` returns a blocking question rather than choosing a default.

## What usually comes next

On Comprehensive and Conservative paths, `401-cleanup` runs next: once for source, once for tests. Otherwise often nothing, since `301` already reviews and refines its own diff; run `401` only if the changed set warrants it.

## Practical guidance

- Use `301` for substantial work, not tiny naming edits. The phase structure provides value on changes that would otherwise sprawl.
- Let tests, lint, and build results decide whether the workflow is done — not conversation sentiment.
- Give the fresh coder distinct test-quality and source-quality checkpoints in one assignment. Preserve assertions, coverage, intended behavior, and public contracts.
- Let coders run assigned development checks. Bundle final test, lint, and build checks into one validator assignment with separate results for each.
- Keep both pre-implementation reviewers on the same complete brief revision. Resolve findings with evidence before assigning implementation.
- On an interrupted run, rebuild the in-memory brief and design from current artifacts and code. Recheck both readiness roles while budget remains; otherwise obtain an evidence-matched caller resolution. Preserve consumed rounds; missing history counts as an exhausted budget, not a fresh cap.

## Common mistakes

- Starting `301` without a real scope boundary — scope creep inside an implementation run is harder to reverse
- Using `301` for test-only work that belongs in `302`
- Trying to revise Gherkin inside `301` instead of routing that work back through `202-spec-design`
- Weakening tests during refinement to match the implementation
- Starting implementation without either clean readiness reviews or an explicit evidence-backed caller resolution, or resetting the review budget to avoid making a decision
- Treating the bounded refinement pass as a substitute for `401` on complex changes that genuinely benefit from a dedicated cleanup pass

<Callout tone="warning" title="The independent context is intentional">
  `301` is strict about phase order: prepare, design in memory, independently review readiness, implement tests-first, independently refine, validate and close. Keep the red-before-green checkpoint, but do not create a worker handoff for every step. Reviewers assess the complete design brief; the fresh coder checks the actual diff, not just the implementer's summary.
</Callout>
