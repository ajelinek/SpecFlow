The `900` series is not a phase you move through once per feature. These skills wrap *around* other skills: reviewing and converging on their output, or composing several into one automated run. Both are user-invoked.

## The split

- `900-feedback-loop`: a bounded review/apply-fix cycle around work that already happened, with isolated subagents for each role
- `901-feature-loop`: runs one feature end-to-end, headless, on its own branch: baseline gate → `201` → `202` → per-scenario `301` → aggregate `401` cleanup → optional expanded coverage → final validation → merge

<Callout tone="core" title="901 is built on 900">
  Every persisted design or spec artifact, and every aggregate cleanup pass, is checked by `900-feedback-loop` before the run advances. `301` keeps its own in-memory design and readiness reviews. At any exhausted review budget, `901` uses the decider to select an evidence-backed way forward, records dispositions and risks, and continues. Required validation and confirmed defects remain blocking.
</Callout>

<Callout tone="optional" title="901 is heavy by design">
  A feature with several scenarios across two coverage rounds can involve a hundred or more subagent invocations. Use `901` when a feature warrants full BDD rigor and branch-level traceability. Use `301` for substantial chunks, `401` for already-changed cleanup scopes, and direct edits for quick fixes.
</Callout>

## Skills in this series

- **[900 Feedback Loop](./900-feedback-loop/)** — bounded review/apply-fix convergence cycle around a specific artifact or change set
- **[901 Feature Loop](./901-feature-loop/)** — run one feature end-to-end through the full pipeline as a single git-tracked run
