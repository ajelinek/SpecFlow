<details>
<summary>Is this heavyweight?</summary>

No. The core path is `201 → 202 → 301`. Add the rest only when it solves a real problem.

</details>

<details>
<summary>Do I need the 100-series first?</summary>

Not always, but it often helps. Use it when the project still needs domain, product, architecture, UX, or feature-set definition, on new or existing projects. If that context already exists, begin with `201`.

</details>

<details>
<summary>What is with the numbers?</summary>

They make the catalog easy to scan and reference in prompts: `100` project context, `200` feature design, `300` implementation, `400` cleanup and test triage, `500` QA, `900` orchestration. You can write "follow `201` to define this feature" without remembering full skill names.

</details>

<details>
<summary>How is this different from plain prompting?</summary>

It separates feature intent, expected behavior, implementation, and cleanup, and keeps each as a reviewable artifact.

</details>

<details>
<summary>Does `npx skills add` install the worker agents too?</summary>

No. It installs the skills only. Run `specflow-setup` afterward to configure the worker agents and models, or copy the agent files by hand with [Custom Agents](../getting-started/custom-agents/).

</details>

<details>
<summary>Which coding tools does `specflow-setup` support?</summary>

Claude Code, GitHub Copilot CLI, OpenCode, and Codex CLI — one or several. It configures SpecFlow files only; it does not install the tools or manage credentials. See [SpecFlow Setup](../support-skills/specflow-setup/).

</details>

<details>
<summary>When should I use 302 instead of 301?</summary>

Use `302` when the behavior already exists and only tests are missing. If the behavior is missing or disagrees with the scenarios, use `301` or fix the spec first.

</details>

<details>
<summary>Why is 401 separate from 301?</summary>

`301` already includes independent review and bounded refinement. `401` is a deeper cleanup-only pass with a strict source-versus-test boundary, so each run stays small. The Comprehensive and Conservative paths include it; on Minimal it is optional.

</details>

<details>
<summary>When should I use 402 instead of 302?</summary>

Use `402` when a test is failing and you don't yet know whether the defect is in the test, the production code, or the intended behavior. Use `302` when the behavior is believed correct and you only need test coverage or a test-side repair.

</details>

<details>
<summary>Where does implementation design happen?</summary>

Inside `301`, before coding. The design is compact and kept in memory. Two independent, read-only reviewers assess it, and readiness criteria must pass. If they still fail after two repair rounds, the run blocks without implementing; nothing, including a `901` Decision Consult, can bypass that gate.

</details>

<details>
<summary>Can I skip 201 and go straight to 202?</summary>

Run `201` first to keep the feature scope clear. If you start with `301` and that context is missing, it generates the overview and scenarios inline without writing files unless asked.

</details>

<Callout tone="tip" title="Still unsure where to start?">
  Read [Getting Started](../getting-started/) and start with `201 → 202 → 301`.
</Callout>
