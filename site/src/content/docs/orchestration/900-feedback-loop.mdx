## What this skill is for

`900-feedback-loop` runs a two-role convergence loop around work that already happened: a Step 1 agent reviews the work against explicit criteria, a Step 2 agent fixes exactly what Step 1 flagged, and the cycle repeats — review, fix, review — until Step 1 reports clean or a safety cap is hit. It does not perform the original work itself — the caller supplies the review criteria and how to apply fixes.

**Output**: A convergence report in chat, nothing else. This skill creates no artifacts of its own — no tracking docs, no `.specflow/` files, no scratch reports. Step 2 only edits files already in scope, touching anything outside it solely when a specific Step 1 finding requires it.

## When to use it

- When another workflow needs a reusable review-and-converge step around a specific artifact or change set — this is how `901-feature-loop` checks every design/spec artifact and cleanup pass
- To review something and keep fixing it until it passes explicit criteria, without doing the review/apply-fix cycling by hand
- Whenever a Step 1 review brief and a Step 2 apply-fix brief can both be stated concretely

## When NOT to use it

- When the original creation work has not happened yet — this skill only wraps around work that already exists
- When review criteria cannot be stated concretely — a vague brief produces a vague, unreliable loop
- For one-off review with no intent to iterate — a direct `@reviewer` call is simpler

<Callout tone="core" title="Step 1's review is the sole authority on convergence">
  This skill never overrides a `CHANGES_REQUIRED` verdict just because iterating further is expensive or slow. If the cap is hit, it escalates with the full iteration history instead of force-accepting the current state.
</Callout>

## What it produces

- A convergence report: total iterations run, what changed across them, and the final verdict
- On cap escalation instead: the iteration history, what feedback recurred, and the final outstanding items — handed back to the caller rather than silently given up on

## Required inputs

- **Step 1 brief (review)** — the exact artifact/scope to review, already completed, and the criteria to judge it against. If the work isn't done yet, send the caller back to finish it first.
- **Step 2 brief (apply-fix)** — which files are in scope and any constraints on how fixes should be made. Every fix pass is driven entirely by Step 1's latest feedback, never a general "improve this."
- **Agents** *(optional)* — defaults to `@reviewer` for Step 1 and `general-purpose` for Step 2. Override either when the work needs a specialist (e.g. `@coder` for real code fixes).
- **Iteration cap** *(optional)* — defaults to 5 review/apply-fix pairs

## Practical guidance

- Step 1 and Step 2 always run in separate, freshly spawned subagent contexts — never reuse one subagent's context for the other role, and never reuse a subagent across iterations
- Keep the loop's own working state small: the two briefs, the iteration count, and the latest verdict — do not accumulate subagent transcripts turn over turn
- From iteration 2 on, Step 1 also gets a summary of the last fix pass so it checks resolution instead of re-reviewing from a blank slate

## Common mistakes

- Handing Step 2 a vague brief instead of exactly Step 1's latest feedback items
- Letting the loop run past the iteration cap by silently resetting the counter instead of escalating
- Reusing one subagent context across both roles, which lets the "reviewer" see its own fix reasoning instead of judging fresh

<Callout tone="tip" title="Default agents can be overridden">
  Step 1 defaults to `@reviewer` and Step 2 defaults to `general-purpose`, but the caller may name a different agent for either role — for example `@coder` for Step 2 when the fix is a real code change.
</Callout>
