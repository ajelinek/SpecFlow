## What this skill is for

`104-backend-architecture` records the backend decisions needed to place the next change correctly: responsibilities, interface conventions, runtime data access, rule enforcement, security, and relevant operations. It builds on D01-D03 without repeating their product, stack, or data definitions. The result is a concise, skimmable reference, not an endpoint catalog or implementation plan.

**Output path**: `.specflow/docs/D04-backend-architecture.md`

## When to use it

- When the backend needs concrete implementation conventions before feature work begins
- When the team needs to agree on API conventions, error handling, and auth patterns
- On existing projects where backend patterns exist but have never been documented
- Before feature design work that will specify API endpoints and data access requirements

## When NOT to use it

- When clear, current backend documentation already exists and is trusted by the team
- For a purely frontend project with no custom backend
- When all backend behavior is third-party managed and there are no team-owned integration or access decisions to document

<Callout tone="optional" title="Just enough backend structure">
  No default stack, authentication scheme, or service/repository layers. Document the actual or confirmed backend shape, whether framework handlers, serverless functions, services, or another structure. Keep real constraints specific and leave implementation details open where consistency doesn't depend on them.
</Callout>

## What it produces

- `.specflow/docs/D04-backend-architecture.md` covering:
  - Backend structure: owners, code locations, responsibilities, and dependency boundaries
  - API and boundary conventions: applicable contracts, validation, and errors
  - Data access and rule enforcement: runtime access patterns and where important rules are enforced
  - Security: trust boundaries, access enforcement, secrets, and sensitive-data safeguards
  - Operations: diagnostics, recovery, jobs, and integrations only when relevant
  - Open questions only when unresolved decisions remain

D03 may be DBML, Markdown, or both. It owns the data definitions; D04 references them and explains runtime access and enforcement. Rule notes in a model are not proof that a database or application enforces them. D04 does not require a separate future data-access document.

## Required inputs

1. Runtime and execution environment — language, framework, and hosting constraints from D02
2. Interfaces — APIs, events, or other entry points and their consumers
3. Access model — authentication and authorization needs, including public or unauthenticated access
4. Data and rules — storage, relevant D03 definitions, and rules needing runtime enforcement
5. Security and operational constraints — sensitive data, compliance, and known reliability or scale needs

Load existing docs and code before asking questions. Use `gap-check` only for unresolved inputs that block decisions; record non-blocking uncertainty under Open Questions. Confirm material new choices rather than treating proposals as settled decisions.

## What usually comes next

`105-frontend-architecture` if frontend integration decisions need clarification; otherwise move to feature design as needed.

## Practical guidance

- Ground decisions in project guidance, D01-D03, and relevant code or configuration. Use `@explore` when useful, not as a mandatory extra step.
- Respect confirmed choices and binding project rules. Use relevant installed skills for unresolved choices, surface conflicts, and label proposals separately from existing patterns.
- Record enough ownership and convention detail for an engineer to extend the right code without prescribing every implementation.
- Include versioning, pagination, pooling, caching, and background jobs only when applicable. Don't invent thresholds or infrastructure to fill the template.
- Keep Security explicit even for public interfaces. Public access does not remove input, secret, or sensitive-data protections.
- Remove template instructions, examples, placeholders, and empty optional sections from generated output.

## Common mistakes

- Copying an example stack, auth scheme, or layered architecture into a project that doesn't need it
- Repeating D03 schemas or D02 stack choices rather than documenting backend-specific usage
- Naming a rule without identifying its enforcement owner, or claiming model notes enforce it
- Omitting relevant validation, error handling, or access decisions while filling irrelevant sections
