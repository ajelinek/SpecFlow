## What this skill is for

`105-frontend-architecture` records the project's frontend structure and core rules so an engineer or AI can place the next change correctly. It checks project conventions before describing folder organization, rendering, component boundaries, state ownership, integration, styling, and verification. The result is a concise reference, not a preset stack or implementation plan.

**Output path**: `.specflow/docs/D05-frontend-architecture.md`

## When to use it

- When the frontend needs clear architectural rules before page or feature design begins
- When the team needs to agree on state management, component boundaries, and routing conventions
- On existing projects where frontend patterns exist but have never been documented
- Before `106-ui-design` or `107-ui-experience`, which both depend on knowing the component and styling approach

## When NOT to use it

- When clear, current frontend architecture documentation already exists and is trusted by the team
- For a purely backend service with no frontend
- When the frontend is a simple static site with no meaningful component or state architecture to document

<Callout tone="optional" title="Optional but foundational for UI work">
  Check project guidance, frontend standards, and existing code before proposing the overall frontend design. D05 keeps the project folder structure and core rules explicit, while leaving room for implementation judgment. No default libraries, directory tree, or mandatory architectural layers.
</Callout>

## What it produces

- `.specflow/docs/D05-frontend-architecture.md` covering:
  - Governing convention sources and an annotated project folder tree showing responsibilities and where new code belongs
  - Component boundaries and Core rules for naming, imports, dependency direction, reuse, and logic/data ownership
  - Rendering and routing responsibilities, including server/client boundaries where relevant
  - Ownership and lifetime of applicable state, using native or framework facilities when sufficient
  - Data integration, relevant access safeguards, and loading/error handling
  - Styling organization, token consumption, and accessibility requirements and checks
  - Frontend-specific verification, with references to D02 rather than a repeated testing strategy
  - Open questions and clearly labeled proposals, only when needed

Real-time, localization, SEO, offline support, and other specialist concerns appear only when they materially affect the architecture.

## Required inputs

1. Project conventions — governing guidance, established folders, and core frontend rules
2. Framework and execution model — confirmed framework, rendering approach, and deployment constraints
3. Data and interaction needs — content sources, integrations, and state that needs ownership
4. Audience and constraints — access, accessibility, device support, and known performance needs

Existing guidance, documents, and code can supply these inputs. The skill asks only about unresolved choices that block the design; non-blocking uncertainty stays in Open Questions. Upstream documents are not required when the relevant decisions are already known.

## Practical guidance

- Read project guidance and frontend conventions first. Respect confirmed decisions and binding rules; use relevant installed skills for unresolved choices, not to override the project. Surface conflicts between guidance and code instead of silently choosing a new design.
- Keep the annotated folder tree focused on meaningful code locations, including tests. Preserve established paths and label proposed additions; don't reproduce every file or invent empty layers.
- Record a short set of core rules that explains placement, naming, allowed imports, shared component reuse, and where logic and external access belong. Link to detailed standards instead of copying their full rulebooks.
- Consider component, URL, global, and remote state without requiring four libraries. Native primitives, framework loaders, or "not needed" can be the right answer.
- Reference D02 for stack and system-level testing decisions and D04 for backend contracts and enforcement. D05 describes their frontend application, including protection of secrets and server-only work where relevant.
- Keep styling organization in D05, visual direction in D06, and product navigation and page inventory in D07. Technical routing ownership remains in D05.

## Common mistakes

- Choosing a familiar stack or folder scheme instead of checking the project's conventions
- Omitting the folder structure or core rules in the name of brevity
- Adding global state, caching libraries, or service layers just to fill template sections
- Presenting a proposed architecture as if it already exists or has been approved
- Repeating upstream documents or leaving template examples and irrelevant sections in the output
