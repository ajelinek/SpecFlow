## What this skill is for

`107-ui-experience` records how users accomplish their tasks: entry points, navigation, shared interaction behavior, recovery, and pages/routes. It produces a short experience model and page table rather than a screen-by-screen script.

`107` owns user-facing behavior. `106` owns visual presentation; D05 owns routing, state, and component implementation conventions. Access expectations here describe the experience, not security enforcement. `108` applies the model to a particular page.

**Output path**: `.specflow/docs/D07-ui-experience.md`

## When to use it

- When the product needs a coherent UX model before designing specific pages
- When navigation structure, user flows, and page boundaries need to be agreed on
- When a new product area changes the existing navigation or shared interaction behavior
- On existing products where navigation and interaction patterns are implicit or inconsistent

## When NOT to use it

- When the product has only one or two pages with obvious navigation
- When the UX is already explicitly documented and current
- For a standalone tool with no meaningful navigation structure

<Callout tone="optional" title="Independent of visual design">
  `106` and `107` are independently optional and can run in either order. A visual system is useful context, not a prerequisite for deciding navigation. Reuse current project guidance rather than generate missing documents automatically.
</Callout>

## What it produces

- `.specflow/docs/D07-ui-experience.md` with applicable decisions:
  - Experience Model — scope, primary tasks, and short entry-to-outcome paths
  - Navigation — hierarchy, entry/exit relationships, role differences, and device/history behavior
  - Interaction & Recovery — shared feedback, loading/empty/error behavior, and interaction accessibility
  - Pages & Routes — named view, route, purpose/primary action, and access
  - Alternatives Considered and Open Questions only when meaningful

Cover the agreed scope, not every possible future capability. Preserve unaffected inventory entries on updates and distinguish existing routes from proposed or unresolved ones. The template supplies no default pages, navigation structure, or error patterns.

## Required inputs

1. Users and tasks — primary goals, relevant roles/access expectations, and workflows in scope
2. Current structure — known pages, routes, entry points, or a rough initial inventory
3. Constraints — device/accessibility needs and established navigation or routing conventions

Read `.specflow/context/domain-knowledge.md` when available before asking about gaps. Use its roles, real workflows, decision points, friction, terminology, and constraints to focus the experience model. Ask only about remaining blocking gaps; uncertain or outdated research is not a confirmed requirement. New research and competitor comparisons are optional.

## What usually comes next

Use `108-ui-page-design` when a named page needs detailed layout and interaction design, `106-ui-design` if visual decisions remain open, or move directly to feature work. `108` checks the page against D07 or asks for confirmation before adding it; a new `107` run is not required when the context is already current.

## Practical guidance

- Keep the page inventory specific and complete for the agreed scope: route, purpose/primary action, and access.
- Ground task priorities and experience gaps in relevant domain findings. Reference them briefly in Experience Model and use domain terminology in navigation, without copying the research or expanding confirmed scope.
- Compare alternatives only for meaningful unresolved choices. There is no fixed direction count or required worker call.
- Navigation philosophy should explain the structural choice (why top nav over sidebar, why tabs over a drawer) in terms of user goals and device support.
- Shared interaction and recovery patterns belong here; individual page designs document their local application and exceptions.
- Reference D06 for established appearance and the project's accessibility standard for shared requirements. Record interaction-specific decisions without duplicating those sources.
- Surface conflicts before changing established behavior. Navigation visibility never substitutes for access enforcement.

## Common mistakes

- Producing a navigation structure without explaining the reasoning behind it
- Inventing future pages or roles to make the inventory look complete
- Treating accessibility as a checklist item rather than a set of specific commitments
- Designing for desktop without specifying what degrades or changes on smaller screens
