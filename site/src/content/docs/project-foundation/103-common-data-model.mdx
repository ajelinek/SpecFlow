## What this skill is for

`103-common-data-model` defines data structures, relationships, and business rules. Relational projects get concrete schema design in DBML; non-relational projects keep domain-level Markdown modeling. It does not generate migrations, enforcement code, ORM models, or API contracts.

## When to use it

- When data structures or business rules are implicit, disputed, or changing
- Before backend or frontend design needs a shared data reference
- On existing projects with a missing or stale model

## When NOT to use it

- When an accurate, current model already answers the task's questions
- When the data is trivial and a separate model would add no useful context
- When you need executable migrations or application code rather than a design

## What it produces

| Storage | Output |
|---|---|
| Relational | `.specflow/docs/D03-common-data-model.dbml` |
| Non-relational | `.specflow/docs/D03-common-data-model.md` |
| Mixed | Both, each defining only its own data and cross-referencing the other |

**Relational:** One DBML file for the whole project, with concrete types, keys, nullability, justified constraints and indexes, and concise notes. Business rules and open questions stay in that file; no companion Markdown model or separate ERD.

Related tables sit under prominent comment headings, each with a group purpose/rules note. Local enums stay beside their tables; global enums go at the bottom.

**Non-relational:** Entity purposes, logical attributes, requiredness, relationships, a relationship-focused ERD, and business rules. Identify value objects and enums without inventing IDs; include lifecycle and storage annotations only when meaningful.

Both formats mark sensitive data and handling requirements. Notes describe intent, not enforced behavior.

## Required inputs

1. Storage approach: relational, non-relational, or mixed; confirmed database engine for relational data
2. Core entities and relationships, including cardinality and ownership
3. Key attributes, types, requiredness, and identity
4. Business rules and meaningful lifecycle transitions
5. Sensitive data and known handling requirements

The skill reads project context first, then asks about blocking gaps. Non-blocking uncertainties remain visible as open questions.

## What usually comes next

`104-backend-architecture` for API, service, and data-access patterns, or `105-frontend-architecture` if the backend is already established.

## Practical guidance

- Reuse the existing model. Confirm before replacing older Markdown, GraphQL, or split DBML models; preserve their rules and open questions.
- Follow confirmed project conventions. Template tables, fields, and types illustrate syntax, not required design choices.
- Add indexes for known access patterns rather than speculative optimization.
- Use an available compatible parser to check DBML. If none is available, review manually and report that parser validation was not run. No bundled tooling, dependency installation, or automatic uploads are required.
- Update the model when structures or rules change; keep notes short and omit empty sections.

## Common mistakes

- Splitting relational definitions across files or duplicating them in Markdown
- Presenting cross-store references as database-enforced foreign keys
- Treating DBML notes as implemented authorization, triggers, or partial indexes
- Copying template examples instead of modeling the project's actual data
