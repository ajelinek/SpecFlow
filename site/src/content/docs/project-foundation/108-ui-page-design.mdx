## What this skill is for

`108-ui-page-design` designs or refines one page or closely related page family for one solution. It preserves high-fidelity HTML as the primary visual reference, makes views and states easy to explore, and maintains a complete page/route catalog after every run.

Related routes can share the same mockup. For example, several settings sections can appear in one diagram, but each route stays separately discoverable in the index and links directly to its own preview. Unrelated pages remain separate designs.

**Output paths**:
- `.specflow/docs/D08-ui-pages/index.html` — stable browser entry point for all known pages/routes
- `.specflow/docs/D08-ui-pages/<page-name>/mockup.html` — high-fidelity visual reference with preview controls
- `.specflow/docs/D08-ui-pages/<page-name>/overview.md` — concise route, parameter, data, and behavior notes

Each touched mockup and overview links back to **All page designs**. Revisions update the same index; they do not create a new catalog per run.

## When to use it

- When a page or related set of views needs a detailed layout and interaction reference
- Before implementing a page where the layout, responsive behavior, or interaction flows are non-trivial
- When a design review is needed before development begins on a page
- When the page index needs reconciling without redesigning existing pages

## When NOT to use it

- For pages that are already well-understood or trivially simple
- For every page by default — use it selectively where the design complexity justifies the investment
- For production implementation or a redesign of the whole visual/navigation system

## What it produces

### Stateful HTML preview

Three independent design subagents receive the same confirmed brief, with different layout approaches: content-led, spatial/layout-led, and action-led. The invoking skill evaluates all three for task completion, hierarchy, state coverage, role differences, responsive usability, accessibility, consistency, and reuse. It selects the strongest approach and briefly explains the decision and useful elements borrowed from the others. Color swaps alone do not count as unique designs. If independent workers are unavailable, it reports the limitation rather than pretending this comparison occurred.

The mockup includes a top preview toolbar, clearly separate from the product UI. Reviewers can select designed views and meaningful states, including relevant loading, empty, error, success, validation, permission, and overlay states. Role, theme, or data controls appear where useful, without requiring every possible combination.

Every documented state is rendered and selectable in the HTML, not just described in Markdown. Applicable dialogs, drawers, sheets, menus, and confirmations remain part of the preview. Existing distinct state views cannot be removed or merged without user approval. Simplifying documentation does not reduce mockup coverage.

Local JavaScript simulates primary actions. Responsive resizing, a viewport selector, or side-by-side frames show important device layouts. Stable preview links open the intended route/state on a fresh load and work with browser Back/Forward. The displayed application URL is separate from mockup-only hash presets and controls.

The HTML runs without backend calls, build steps, or CDN/runtime dependencies. Inline styles/scripts and realistic synthetic data are appropriate here. It remains a **design artifact**, not production code or evidence of accessibility compliance.

### Complete route index

Every run reconciles **every known page/route**, including pages not yet designed, against D07, existing D08 designs, and actual app routes when present. The index lists:

- Page/view name and purpose, with each distinct route individually visible
- Application URL/route pattern, path parameters, and search/query parameters with known meanings/defaults
- Access expectations and current/planned/proposed distinctions where relevant
- Design coverage and direct links to the right mockup view/state and overview

The index uses stacked route entries with labeled details and expandable parameter notes instead of a wide table. Known finite section routes are listed individually; dynamic IDs stay as route patterns. URL-addressable overlays are labeled variants under their owning page. Ordinary filter values do not multiply into endless entries. Unknown parameters remain marked unknown rather than silently treated as absent.

Unchanged entries and working links are preserved. Undesigned pages stay visible without fake preview links. The index summarizes existing route decisions rather than becoming another competing specification.

## Required inputs

1. Scope: page/family, known routes, purpose, and primary actions; or index-only maintenance
2. Users and data: access differences and what users see, enter, or change
3. Design constraints: established presentation/interaction patterns and relevant device needs

Read relevant `.specflow/context/domain-knowledge.md`, project decisions, existing designs, and routes before asking about gaps. D06/D07 are useful when available, not mandatory prerequisites. Confirm material new routes or behavior rather than silently invent them; update an existing D07 for approved navigation changes.

## What usually comes next

Use the stable index link to review designs and choose what needs attention next. Move to feature planning or implementation when the relevant decisions are clear; there is no requirement to design every listed page first.

## Practical guidance

- Keep `overview.md` skimmable with headings and labeled bullets: context, routes/parameters, key data, state/interaction outcomes, and short reasons for the design selection. Omit empty open questions; don't describe pixels already visible in the mockup.
- Check index links, fresh preview presets, return links, toolbar controls, every documented state, primary transitions, error recovery, overlay opening/closing, role differences, and narrow/wide layouts in a browser when available. Report checks not performed, including unavailable browser verification.
- Reuse D08 patterns and confirmed decisions. Each of the three subagents proposes one distinct design; the invoking skill compares them and writes the selected artifacts. Three full HTML mockups are not required.

## Common mistakes

- Listing one entry per mockup file instead of one per navigable route/view
- Dropping known but undesigned pages, or confusing unknown parameters with no parameters
- Linking every route to the mockup's default view instead of its matching preview preset
- Updating the mockup without refreshing the shared index and return links
- Using the HTML mockup as the starting point for production code — it is a design reference, not implementation
