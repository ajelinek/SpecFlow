## What this skill is for

`102-system-architecture` produces the system architecture document: the technology stack, major components, deployment topology, integration points, and testing strategy. It is the technical baseline that every downstream SpecFlow document — backend architecture, frontend architecture, data model — references rather than re-establishing.

**Output path**: `.specflow/docs/D02-system-architecture.md`

## When to use it

- When the project needs a shared technical baseline before backend or frontend design begins
- When the team has technology decisions to make explicit and record
- On existing projects where the architecture has never been fully written down
- Before `103`, `104`, or `105`, which all depend on understanding the system shape

## When NOT to use it

- When a clear, current architecture document already exists and is trusted by the team
- For a tiny prototype where a full architecture document would be premature overhead

<Callout tone="optional" title="Optional but important">
  On projects where the technology choices are still being made, `102` is the
  right moment to make those decisions explicit and reviewable. Running feature
  design against an undocumented or misunderstood architecture is one of the
  more common sources of rework.
</Callout>

## What it produces

- `.specflow/docs/D02-system-architecture.md` covering:
  - System overview and architectural style
  - Technology stack decisions with rationale
  - Major components and their responsibilities
  - Deployment topology and environment model
  - Key integration points and external dependencies
  - Testing strategy and tooling
  - Relevant constraints and architectural decisions

The template uses the title **D02 — System Architecture**. Keep it skimmable: include only applicable
components, technologies, and checks, with no fixed counts or required testing layers. Generated
documents omit authoring instructions, placeholders, and empty optional sections.

## Required inputs

1. Application components — known system parts and external integrations
2. Traffic and scale — expected demand; estimates or targets when known
3. Deployment environment — where the system runs or is intended to run
4. Architecture drivers — constraints or goals such as team size, cost, compliance, or time

Existing D02, D01, and relevant code/config are read first. Confirmed stack choices are reused rather
than asked from scratch; unresolved choices follow the guidance below.

<Callout tone="tip" title="Ground stack choices in the project">
  Confirmed user decisions and binding project rules take priority. Current docs and code provide
  evidence; installed skills guide unresolved choices rather than override project constraints.
  Conflicts are surfaced for resolution. New choices are recommended with a tradeoff and confirmed
  before being recorded as settled. Non-blocking decisions can remain open questions.
</Callout>

## What usually comes next

`103-common-data-model` — define the entities and relationships the system must manage, using the architecture as context.

## Practical guidance

- Include the rationale for key technology choices. Downstream work benefits from knowing _why_ decisions were made, not just _what_ was decided.
- If the project already has code, tell it to run 102 on the existing codebase and it will create the documentation for you.
- Reference D01 for user goals and business requirements — D02 should not re-state what D01 already captured.
- Keep backend, frontend, and data detail in D03-D05. Record material risks and safeguards without turning D02 into an implementation plan.

## Common mistakes

- Leaving the testing strategy section as "we will write tests" without specifying tooling or approach
- Describing the ideal architecture rather than the actual one on existing projects
- Adding a backend, database, or testing layer just to fill the template
