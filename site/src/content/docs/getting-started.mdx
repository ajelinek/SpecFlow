SpecFlow is a lightweight, spec-driven workflow for building software with AI. It is a catalog of skills and optional worker agents covering project setup, feature design, implementation, cleanup, and defect resolution, without replacing your coding standards or framework rules.

## 1. Install the skills

Install interactively and choose only the skills you want:

```bash
npx skills add ajelinek/SpecFlow
```

Install the full catalog:

```bash
npx skills add ajelinek/SpecFlow --skill '*'
```

Add `--list` to preview the available skills first.

<Callout tone="tip" title="Skills install versus tool setup">
  `npx skills add ...` only installs the SpecFlow skills. Step 2 configures them, along with the worker agents and model routing, for your coding tools.
</Callout>

## 2. Run `specflow-setup`

After installing the skills, run the setup skill from your coding tool:

<PromptBlock title="Run this" text={`Run specflow-setup.`} />

It configures SpecFlow for **Claude Code, GitHub Copilot CLI, OpenCode, and Codex CLI** — one or several. You choose project-local or user-wide scope and confirm the model for each worker role (`coder`, `validator`, `designer`, `reviewer`, `decider`). Existing settings are preserved, and conflicts need your approval. It does not install coding tools or manage credentials. See **[SpecFlow Setup](../support-skills/specflow-setup/)** for details.

<Callout tone="tip" title="When the workers matter most">
  Full `301`, `302`, `401`, and `402` runs are designed around these workers. You can start without them. To copy the Claude-format agent files by hand, use **[Custom Agents](./custom-agents/)**.
</Callout>

## 3. Initialize `.specflow/` guidance

Setup asks about this separately. If you skipped it, run it yourself:

<PromptBlock title="Run this" text={`Run context-manager in initialize mode.`} />

This creates `.specflow/AGENTS.md`, a short guide to how `.specflow/context/`, `.specflow/docs/`, and `.specflow/features/` are organized. It also states the isolation rule: each feature folder is a point-in-time snapshot, and the agent won't read a sibling feature's folder unless you ask. It is a one-time step.

## 4. Run the minimal feature path

If the repo already has enough context, start with the Minimal path. Skill numbers work as prompt shorthand:

<PromptBlock
  title="Run this"
  text={`Run 201 for invoice approval.
Use 202 for invoice approval with balanced coverage.
Run 301 for the invoice approval feature.`}
/>

The Comprehensive and Conservative paths finish with `401-cleanup`, run once for source and once for tests. On Minimal it is optional.

## 5. Compare the other paths

- Read **[Project Foundation](../project-foundation/)** for the larger lifecycle and why the `100` series helps on new and existing projects.
- Compare the Comprehensive, Conservative, Minimal, and Lean paths on the homepage. Lean starts directly at `301`.

<Callout tone="tip" title="What 301 does when artifacts are missing">
  `301` generates missing `201` overview or `202` scenario context inline and writes no files unless asked. Every run builds an implementation design in memory and sends it to two independent, read-only reviewers before coding. After two repair rounds, remaining findings return for an explicit caller resolution; under `901`, the decider chooses how to continue rather than stopping at the review limit.
</Callout>

<Callout tone="tip" title="What the worker agents are for">
  `coder` makes scoped code changes, `validator` runs test, lint, and build checks, and `designer` gives UI design direction. `reviewer` does independent review in `301` and `900-feedback-loop`. `decider` handles decisions in the headless `901-feature-loop`, including exhausted review budgets, without waiving validation or confirmed defects.
</Callout>
