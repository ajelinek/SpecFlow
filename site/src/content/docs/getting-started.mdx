SpecFlow is a lightweight, spec-driven workflow for building software with AI. It provides a structured catalog of skills (100-402 series, the 500-series quality assurance skills, plus the 900-series orchestration loops) and optional worker agents that guide you through project setup, feature design, implementation, correction, cleanup, and defect resolution without replacing your coding standards or framework rules.

## 1. Install the skills

Install interactively and choose only the skills you want:

```bash
npx skills add ajelinek/SpecFlow
```

Install the full catalog:

```bash
npx skills add ajelinek/SpecFlow --skill '*'
```

Use `npx skills add ajelinek/SpecFlow --list` if you want to preview the available skills first.

<Callout tone="tip" title="Skills install versus tool setup">
  `npx skills add ...` only installs the SpecFlow skills. Step 2 configures them, along with the worker agents and model routing, for your coding tools.
</Callout>

## 2. Run `specflow-setup`

After installing the skills, run the setup skill from your coding tool:

<PromptBlock title="Run this" text={`Run specflow-setup.`} />

It configures SpecFlow for **Claude Code, GitHub Copilot CLI, OpenCode, and Codex CLI** — one or several. It asks whether you want project-local or user-wide scope, confirms which tools to configure, and checks current official documentation against your installed tool versions. It then configures the full skill catalog, the `coder`, `validator`, `designer`, `reviewer`, and `decider` workers, and the model for each role. You confirm each role's model; setup does not make that choice for you.

Existing settings and customizations are preserved, and conflicts need your approval. At the end it asks whether to run short live checks, which may use model tokens. It does not install coding applications or manage credentials. See **[SpecFlow Setup](../support-skills/specflow-setup/)** for the full behavior.

<Callout tone="tip" title="When the workers matter most">
  The workers are the intended support structure for full `301`, `302`, `401`, and `402` runs. You can start without them, but stronger orchestration comes from configuring them. If you only want a plain copy of the Claude-format agent files, use **[Custom Agents](./custom-agents/)** instead.
</Callout>

## 3. Initialize `.specflow/` guidance

Setup asks about this separately when it configures a project — a user-wide run does not change your current project unless you say so. If you skipped it, or want to run it yourself:

<PromptBlock title="Run this" text={`Run context-manager in initialize mode.`} />

This creates `.specflow/AGENTS.md`, a short guidance file that tells your agent how `.specflow/context/`, `.specflow/docs/`, and `.specflow/features/` are organized, and states the feature isolation rule: each `.specflow/features/<F-ID>-<slug>/` folder is a point-in-time snapshot, and the agent should not read a sibling feature's folder unless you explicitly ask it to. It's a one-time step — no other skill runs it for you, so it does not add overhead to every feature.

## 4. Run the minimal feature path

If the repo already has enough context, start with the minimal feature path. You can use the skill numbers as a shorthand in your prompts (e.g., saying "Run 301" instead of the full name):

<PromptBlock
  title="Run this"
  text={`Run 201 for invoice approval.
Use 202 for invoice approval with balanced coverage.
Run 301 for the invoice approval feature.`}
/>

Add `401-cleanup` only when the changed set warrants deeper cleanup. Scope source and test cleanup as separate runs.

## 5. Compare the other paths

- Read **[Project Foundation](../project-foundation/)** for the larger lifecycle, groupings, and why the `100` series helps on both new and existing projects.
- Use the homepage flow visualization to compare Comprehensive, Conservative, Minimal, and Lean paths side by side. Lean starts directly with `301`, synthesizing missing feature context inline.

<Callout tone="tip" title="What 301 does when artifacts are missing">
  `301` uses inline guided generation for missing `201` overview or `202` scenario context without writing files unless requested. Those skills still produce normal persisted artifacts when run directly. Every `301` run builds a versioned implementation design in memory and sends the same complete brief to two fresh, independent, read-only reviewers before coding. Any failed readiness criterion blocks implementation immediately. If readiness remains unresolved after at most two repair rounds, the run ends with a terminal design blocker.
</Callout>

<Callout tone="tip" title="What the worker agents are for">
  Full `301`, `302`, `401`, and `402` runs are designed around separate workers: `coder` for scoped code changes, `validator` for test/lint/build validation, and `designer` for UI-affecting design direction. `reviewer` handles independent pre-implementation review in `301` and the Review role in `900-feedback-loop`. `decider` handles the headless Decision Consult in `901-feature-loop`, but cannot waive `301`'s readiness gate or repair cap.
</Callout>
