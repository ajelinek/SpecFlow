The `300` series turns design artifacts into running code. If the problem is a failing test and the right fix is unclear, start with `402-test-correction` from the `400` series.

## The two paths

| Skill | When to use it |
|---|---|
| `301-spec-implementation` | The main implementation workflow — for substantial changes driven by a spec |
| `302-test-implementation` | The test-only path — for adding or repairing automated tests for behavior that already exists |

<Callout tone="core" title="301 is the primary implementation skill">
  Most feature work goes through `301`. Use `302` only when the production behavior already exists and the gap is test coverage.
</Callout>

## What 301 does internally

`301` is a phased workflow, not a longer coding prompt:

0. Gathers the `201` overview, `202` scenarios, codebase context, standards, and reuse candidates; generates missing context inline
1. Builds a compact implementation design in memory
2. Sends the design to two independent, read-only reviewers (walkthrough and adversarial); accepts clean readiness reviews or an explicit caller resolution at the cap
3. Has one coder write failing tests, then the implementation, with red/green evidence
4. Has a fresh coder review the diff against the design and refine tests and source without weakening assertions
5. Runs final test, lint, and build checks, then closes with evidence and status updates

Readiness repair is capped at two rounds. Remaining findings return to the caller for an explicit evidence-backed resolution; under `901`, the decider selects how to continue without a fresh review budget. Confirmed defects and missing required behavior cannot be waived. See the [phase-by-phase workflow](./301-spec-implementation/#the-phases).

Because of the refinement pass, a separate `401-cleanup` run is optional on Minimal and Lean paths.
