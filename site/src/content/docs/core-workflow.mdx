For most substantial feature work, use the explicit `201 → 202 → 301` loop shown by **Minimal** on the [homepage path picker](../). Reach for it when the product and architecture are clear enough to skip the full `100` series. **Lean** starts directly with `301`, which generates missing overview and scenario context inline without skipping design review, refinement, or validation.

## The loop

| Step | Does | Output |
|---|---|---|
| [`201-high-level-design`](../feature-design/201-high-level-design/) | Define the feature in plain language: scope and user journey | `overview.md` |
| [`202-spec-design`](../feature-design/202-spec-design/) | Write the Gherkin scenarios that describe expected behavior | `specs.feature` |
| [`301-spec-implementation`](../implementation/301-spec-implementation/) | Design and review in memory, build tests-first, then independently refine and validate | Working, tested code |

<Callout tone="core" title="This is the minimum viable loop">
  `201 → 202 → 301` is the core delivery path with explicit feature-definition artifacts. `301` already includes independent review and bounded refinement. Use `401` as a deliberate follow-up when the changed set warrants deeper cleanup, not as a required fourth step.
</Callout>

[`401-cleanup`](../cleanup/401-cleanup/) is optional deeper cleanup, scoped separately to changed source or test files. It is not part of the core minimum.

<Callout tone="tip" title="Need more upfront context?">
  If the product, architecture, or UX is still unclear, run the [Project Foundation](../project-foundation/) series first. If the missing work is only test coverage for behavior that already exists, use [`302-test-implementation`](../implementation/302-test-implementation/) instead of `301`.
</Callout>
