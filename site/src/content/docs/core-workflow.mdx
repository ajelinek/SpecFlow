For most feature work, use the `201 → 202 → 301` loop shown as **Minimal** on the [homepage](../). It fits when the product and architecture are clear enough to skip the `100` series. **Lean** starts directly at `301`, which generates missing overview and scenario context inline.

## The loop

| Step | Does | Output |
|---|---|---|
| [`201-high-level-design`](../feature-design/201-high-level-design/) | Define the feature: scope and user journey | `overview.md` |
| [`202-spec-design`](../feature-design/202-spec-design/) | Write the Gherkin scenarios for expected behavior | `specs.feature` |
| [`301-spec-implementation`](../implementation/301-spec-implementation/) | Design and review in memory, build tests-first, then refine and validate | Working, tested code |

<Callout tone="core" title="Cleanup is part of the larger paths">
  The **Comprehensive** and **Conservative** paths finish with [`401-cleanup`](../cleanup/401-cleanup/), run twice: once for changed source, once for changed tests. On **Minimal** and **Lean** it is optional, because `301` already includes independent review and bounded refinement.
</Callout>

<Callout tone="tip" title="Need more context first?">
  If the product, architecture, or UX is unclear, run the [Project Foundation](../project-foundation/) series first. If the only gap is tests for behavior that already exists, use [`302-test-implementation`](../implementation/302-test-implementation/) instead of `301`.
</Callout>
